Chapter 3 — Item 10: equals — Geçişlilik İhlali
↩ Önceki sayfadan devam — Madde 10: ColorPoint "renk-kör" karşılaştırma girişimi

Sorunu, ColorPoint.equals'ın "karışık karşılaştırmalar" (mixed comparisons) yaparken rengi göz ardı etmesiyle düzeltmeyi deneyebilirsiniz:

You might try to fix the problem by having ColorPoint.equals ignore color when doing "mixed comparisons":

// Hatalı — geçişliliği ihlal eder! // Broken - violates transitivity! @Override public boolean equals(Object o) { if (!(o instanceof Point)) return false; // o normal bir Point ise, renk-kör karşılaştırma yap if (!(o instanceof ColorPoint)) return o.equals(this); // o bir ColorPoint; tam karşılaştırma yap return super.equals(o) && ((ColorPoint) o).color == color; }

Bu yaklaşım simetri sağlar, ancak geçişlilik pahasına:

This approach does provide symmetry, but at the expense of transitivity:

ColorPoint p1 = new ColorPoint(1, 2, Color.RED); Point p2 = new Point(1, 2); ColorPoint p3 = new ColorPoint(1, 2, Color.BLUE); // p1.equals(p2) → true (renk-kör) // p2.equals(p3) → true (renk-kör) // p1.equals(p3) → false (renk dahil!) // GEÇİŞLİLİK İHLALİ!

İlk iki karşılaştırma "renk-kör" iken üçüncüsü rengi hesaba katar. Ayrıca bu yaklaşım sonsuz özyinelemeye (infinite recursion) de neden olabilir: İkisi de bu tarz equals metoduna sahip ColorPoint ve SmellPoint gibi iki Point alt sınıfı olduğunu varsayın. O zaman myColorPoint.equals(mySmellPoint) çağrısı bir StackOverflowError fırlatacaktır.

Peki çözüm nedir? Bunun, nesne yönelimli dillerdeki denklik ilişkilerinin temel bir sorunu olduğu ortaya çıkar. Örneklendirilebilen (instantiable) bir sınıfı genişletip bir değer bileşeni eklerken equals sözleşmesini korumanın bir yolu yoktur — tabii ki nesne yönelimli soyutlamanın faydalarından vazgeçmeye istekli değilseniz.

Bunu, equals metodundaki instanceof testi yerine getClass testi kullanarak yapabileceğinizi duymuş olabilirsiniz:

The first two comparisons are "color-blind," while the third takes color into account. Also, this approach can cause infinite recursion: Suppose there are two subclasses of Point, say ColorPoint and SmellPoint, each with this sort of equals method. Then a call to myColorPoint.equals(mySmellPoint) will throw a StackOverflowError.

So what's the solution? It turns out that this is a fundamental problem of equivalence relations in object-oriented languages. There is no way to extend an instantiable class and add a value component while preserving the equals contract, unless you're willing to forgo the benefits of object-oriented abstraction.

You may hear it said that you can extend an instantiable class and add a value component while preserving the equals contract by using a getClass test in place of the instanceof test in the equals method:

// Hatalı — Liskov İkame Prensibini ihlal eder! // Broken - violates Liskov substitution principle! @Override public boolean equals(Object o) { if (o == null || o.getClass() != getClass()) return false; Point p = (Point) o; return p.x == x && p.y == y; }

🔍 Kavramlar: 🔍 Concepts:

Renk-Kör Karşılaştırma Tuzağı

ColorPoint.equals metodunda, "karışık" karşılaştırmada rengi göz ardı etmek simetriyi kurtarır; ancak geçişliliği bozar: KIRMIZI(1,2) = (1,2) = MAVİ(1,2) → ama KIRMIZI(1,2) ≠ MAVİ(1,2).

Daha kötüsü: ColorPoint ve SmellPoint gibi iki alt sınıf birbiriyle karşılaştırılırsa, her ikisi de o.equals(this) çağırdığı için StackOverflowError oluşur — sonsuz ping-pong!

Ignoring color in "mixed" comparisons saves symmetry but breaks transitivity: RED(1,2) = (1,2) = BLUE(1,2) → but RED(1,2) ≠ BLUE(1,2).

Worse: if two subclasses like ColorPoint and SmellPoint compare, each calls o.equals(this) causing StackOverflowError — infinite ping-pong!

Temel OOP Sorunu

Bu sorun Java'ya özgü değildir — tüm nesne yönelimli dillerde denklik ilişkilerini kalıtımla birleştirmek zordur. Bu, matematiksel olarak kanıtlanabilir bir sınırlamadır.

Kural: Örneklendirilebilen bir sınıfı genişletip yeni bir değer bileşeni eklemek ve aynı zamanda equals sözleşmesini korumak imkansızdır.

This isn't Java-specific — combining equivalence relations with inheritance is hard in all OOP languages. It's a mathematically provable limitation.

Rule: It is impossible to extend an instantiable class with a new value component and preserve the equals contract.
