Chapter 2 — Item 7: Artık zamanını doldurmuş eski(ölü) nesne referanslarını tamamen silkeleyip temizleyin / Eliminate obsolete object references
↩ Önceki sayfadan devam — Madde 7 Memory Leak detayı

...Bu yığından (stack) pop ile dışarı atılıp (popped off) çıkarılmış gibi görünen öğeler aslında Çöp Toplayıcısı (garbage collected) tarafından asla toplanamayacaktır, hattâ yığını bizzat kullanan asıl programın o atılmış yığın öğelerine ilişkin hayatta kalan hiçbir aktif referansı (göstericisi) kalmamış olsa bile böyledir! Bunun sebebi oldukça basittir; yığının bizim silindiğini sandığımız kısımdaki kapasitesi aslen bu nesnelere ilişkin "tarihi geçmiş, ölü (obsolete)" referansları dizinin kendi içinde inatla muhafaza ediyor (maintains) olmasıdır. Tarihi geçmiş bir referans; programın bir daha hiçbir zaman asla işaret etmeyeceği (dereferenced) ölümlü bir referans demektir. Burada elements dizisinin içerisinde yalnızca programın şu an baktığı "aktif kısım (active portion)" boyutu içindeki objeler asıl hayatını sürdürenlerdir, fakat dizinin kapasitesinin geri kalan (ve artık görünmez olan) alanlarındaki tüm indeksler bütünüyle çöptür (obsolete). Aktif olan kısım, yalnızca indeksi size değerinden küçük olan öğeleri kapsar.

Hafıza yönetiminin Çöp Toplayıcılar'a bırakıldığı (garbage-collected) modern dillerdeki bellek sızıntıları (daha doğru bir deyişle, kasıtsız nesne alıkoyma — unintentional object retentions durumu) son derece sinsi ve tehlikelidir (insidious). Eğer tek bir nesne referansı bile yanlışlıkla (unintentionally) bellekte bu şekilde asılı kalık konursa (retained), yalnızca o asıl söz konusu nesnenin bizzat kendisinin Çöp Toplayıcısı tarafından yok edilmesini imkansızlaştırmakla kalmazzınız; silsile halinde o ilk nesnenin bellekte kendi kendine göstererek barındırdığı tüm diğer alt/yan nesneler (any objects referenced by that object) de, onların da barındırdıkları da ve ilh. (and so on) hepsi birden adeta "silinmez/dokunulmaz" bir zırha bürünürler. Uygulamanızda gayet masum gözüken sadece irili ufaklı birkaç adet ufacık nesne referansı bu şekilde kazara tutulmuş dahi olsa, arka planda birbirine zincirlenen (linked) yüz binlerce, hatta milyonlarca nesnenin zincirleme bir reaksiyonla (many, many objects) toplanılması (silinmesi) engellenmiş olabilir ki bu durum doğrudan performans üzerinde dehşet verici derecede feci sarsıcı etkilere yol açma potansiyeli taşır (potentially large effects).

Neyse ki bu tarz bir problemin çözümü de oldukça (is simple) basittir: Referanslar ne vakit kendi "ömürlerini doldurup (obsolete/geçersiz)" hurdaya çıkarsalar, onları elinizdeki dizide tutmak yerine doğrudan null değerine (null out) eşitleyerek ezin/silin. Bizim bu başbelası problemli Stack sınıfımızın özelindeki durumda, bir elemanın üzerine atanan yığın eleman referansı yığından çıkarıldığı (popped off) sanise boyunca tarihi geçmiş sayılarak silinmesi (obsolete) gereken bir hedeftir. Dolayısıyla pop() metodumuzun sağlığını geri kazanıp düzeltilmiş (The corrected version) yepyeni sızıntısız sürümü tam olarak şuna benzemelidir:

...that were popped off the stack will not be garbage collected, even if the program using the stack has no more references to them. This is because the stack maintains obsolete references to these objects. An obsolete reference is simply a reference that will never be dereferenced again. In this case, any references outside of the “active portion” of the element array are obsolete. The active portion consists of the elements whose index is less than size.

Memory leaks in garbage-collected languages (more properly known as unintentional object retentions) are insidious. If an object reference is unintentionally retained, not only is that object excluded from garbage collection, but so too are any objects referenced by that object, and so on. Even if only a few object references are unintentionally retained, many, many objects may be prevented from being garbage collected, with potentially large effects on performance.

The fix for this sort of problem is simple: null out references once they become obsolete. In the case of our Stack class, the reference to an item becomes obsolete as soon as it’s popped off the stack. The corrected version of the pop method looks like this:

public Object pop() { if (size == 0) throw new EmptyStackException(); Object result = elements[--size]; elements[size] = null; // Eski ölmek üzere olan referansı ezerek temizle (Eliminate obsolete reference) return result; }

Eski ve iptal edilmiş referansları elle tek tek null'a atayarak yok etmenin, sızıntıyı çözmek haricinde koda kattığı ekstra bir muazzam fayda da (added benefit); şayet o silinen eleman sonradan dışarılardan bir şekilde çağrılıp talep edilirse programın sahte verilerle (quietly doing the wrong thing) sessiz sessiz yoluna devam edip yanlış işleri körüklemesi yerine hiç vakit kaybetmeden pimi çekilmişçesine ani bir NullPointerException patlatarak hata vermesini (fail) sağlamasıdır. Bir programcının programındaki arızaları ne kadar tez bir şekilde bulursa çözmesinin de o kadar elverişli (beneficial) kalacağını sakın ama sakın unutmayın.

Geliştiriciler (bilhassa acemiler), başlarına ilk kez böylesi bir "memory leak (hafıza kaçağı)" belası musallat olup da şok olduklarında, korkudan aşırıya kaçma (overcompensate) huyu geliştirerek her kullandıkları nesneyi işi biter bitmez takıntılı gibi anında zorla null lamaya koyulurlar. Oysaki diller böyle yönetilsin diye kurgulanmamıştır; böylesi her nesnede agresif ve aşırı bir bellek sildirme çabası katiyen ne gereklidir ne de olması dahi istenir (desirable); zira yazılan kaynak kodu baştan sona anlamsız karmaşık kod satırlarına boğup (clutters up) kirli bırakır. Nesne referanslarını "elle, kendi kaba kuvvetinizle (nulling out)" null yapmak, kural/norm değil salt istisna (exception) düzeyinde sadece sınırlı anlarda uygulanacak özel müdahaleler olmalıdır.

Eskimiş (obsolete) nesne referanslarından kurtulabilmek (eliminate) ve yok olmalarını garantilemek için en güzel (garantili/best) yöntem, halihazırda o nesneye işaret eden ana değişkenin kapsamından (veya metodun küme parantezlerinden) çıkıp erişilemez alana kaymasını (fall out of scope) kendi haline sakin bir süreçte bırakmaktır. Eğer ki her bir yarattığınız değişkeni (variable) oluştururken mümkün olabilecek en az izin verilen menzil (kapsam - narrowest possible scope) çapında tanımlarsanız (Madde 57'de tartışacağız), kodunuz zaten doğal olarak bunu kendi kendine mükemmelen (naturally) çözecektir.

Pekâlâ, öyleyse bir referansı hakikaten de ne zaman acımasızca kendi el yordamımızla null'lamak zorunda hissetmeliyiz? Bu soruya cevap vermek adına az önceki Stack sınıfını tekrar düşünün; tam olarak bu sınıfı hafıza sızıntılarına (memory leaks) (susceptible) bu denli açık ve kırılgan yapan sinsi detay neydi? Gayet açık (Simply put): Bu sınıf; kendi hafızasını resmen kendi başına yönetmeye (manages its own memory) kalkışıyor! Bizim elements adını verdiğimiz o ucu bucağı meçhul uzun referans dizisi (array)... (Devamı sonraki sayfada)

An added benefit of nulling out obsolete references is that if they are subsequently dereferenced by mistake, the program will immediately fail with a NullPointerException, rather than quietly doing the wrong thing. It is always beneficial to detect programming errors as quickly as possible.

When programmers are first stung by this problem, they may overcompensate by nulling out every object reference as soon as the program is finished using it. This is neither necessary nor desirable; it clutters up the program unnecessarily. Nulling out object references should be the exception rather than the norm.

The best way to eliminate an obsolete reference is to let the variable that contained the reference fall out of scope. This occurs naturally if you define each variable in the narrowest possible scope (Item 57).

Unintentional Object Retention (Kasıtsız Nesne Alıkoyma)

Büyük bir nesne yarattığınızda ve onu bir listeye / array'e fırlattığınızda; diyelim ki mantıksal olarak o dizideki boyutu "Kestiniz" (örn size-- yaptınız) ve iş bitti sandınız. Gerçekte dizi indeksi hâlâ o kocaman eski objeyi bellek referansıyla haritaya mıhlanmış şekilde (pinned down) tutmaktadır. Çöp toplayıcı GC, mantık bilmez; o sadece o dizi hücresinin objeye bir bağlı oktan kilit ucu çıkardığını görür ve bu obje hâlâ lazımmış gibi onu silmekten çekinir.

Bir referans zinciri (Object Graph) varsa, atıl kalmış tek bir tepe nesnesi yüzünden ona bağlı diğer binlerce dev gibi nesne bellekten sökülemez.

Memory leaks in Java are usually "Unintentional Object Retention". Since Java uses references instead of direct memory addresses if a forgotten object is held within an array somewhere (even if the programmatic size ignores it), the GC is clueless about your logic and respects the fact that a pointer exists. This holds up not just that object, but its entire object subgraph as well.

Fall out of Scope (Kapsamdan Düşmek) ve Null'lama Fetişi

Deneyimsiz programcılar Java'daki bir objeyi kullanmayı bitirince hemen manuel obj = null; yazma takıntısına saplanır. Halbuki Java'da değişkenlerin çok spesifik "yaşam döngüleri (scopes)" vardır (örn: metot veya if/for bloğu içerisi gibi). Kapsam } parantezi ile bittiği anda zaten arka planda o referanslar yokedilir / GC'nin insafına bırakılır. Ekstra her metoda null satırlarıyla çorba karıştırmaya tevessül etmek çirkin ve antipattern'dir (kötü koddur).

Overzealous nulling means setting myVar = null; forcefully on the last line. This is a bad practice. The JVM's Garbage Collector relies on variable scope ({ /* ... */ }). The moment execution leaps out of the scope, local references naturally die. You only forcefully null objects when you are managing an underlying array/data block manually.

Fail Fast (Hemen Patlama / Hızlı Çökme Kuralı)

Kod yazarken eğer dışarıdan bir girdi sakatsa, mantık dışıysa veya tehlikeliyse veriyi hasıraltı (suppress) etmek, gizlice sahte data ile kandırmak çok büyük sistem facialarına gebedir. Kural basittir: Sistem hata mi gördü? O An, o milisaniyede (Quietly doing wrong thing) patlamalı/çökmeli ve bir Exception (İstisna) fırlatmalıdır. Biz buna yazılımda "Fail-fast (Anında Çöküş)" prensibi deriz. Hatayı daha oluştuğu an o satırda yakalamak, 2 saat sonra veritabanında patladığında izini aratmaktan evladır.

Fail Fast revolves around making your code fail as soon as possible with a fatal Exception when it encounters an invalid state or logically incorrect inputs. It's infinitely better for a system to crash right away with a stacktrace pinpointing the defective line than to silently use corrupt data (Obsolete Reference) only to ruin a database transaction an hour later.
