...referans hücreleri (reference cells), nesnelerin bizzat kendileri değildir). Dizinin aktif kısmındaki (daha önce tanımladığımız biçimiyle) elemanlar tahsis edilmiş (allocated) durumdadır ve geri kalan kısımdakiler ise boş (free) sayılır. Çöp Toplayıcı'nın (Garbage Collector) bunu bilmesinin hiçbir yolu yoktur; Çöp Toplayıcı'nın gözünden bakıldığında, elements dizisindeki tüm nesne referansları eşit derecede geçerlidir (equally valid). Yalnızca programcı, dizinin aktif olmayan kısmının artık önemsiz olduğunu bilir. Programcı bu gerçeği, dizi elemanlarını aktif olmayan kısmın parçası haline gelir gelmez elle null değerine eşitleyerek Çöp Toplayıcı'ya etkin bir biçimde iletir (effectively communicates).

Genel bir kural olarak söylemek gerekirse, bir sınıf ne zaman kendi belleğini bizzat kendisi yönetiyorsa (manages its own memory), programcının bellek sızıntıları konusunda uyanık olması şarttır. Bir eleman her serbest bırakıldığında (freed), o elemanın içerdiği tüm nesne referansları null değerine eşitlenmelidir.

Bellek sızıntılarının (memory leaks) bir diğer yaygın kaynağı ise önbelleklerdir (caches). Bir nesne referansını bir önbelleğe (cache) koyduğunuzda, onun orada köklenip yer kaplayarak durduğunu unutmanız ve onun artık çoktan alakasız hale gelmesinden çok sonra bile önbellekte asılı bırakmanız işten bile değildir. Bu problemin birkaç çözüm yolu vardır. Eğer şanslıysanız ve uyguladığınız önbellek yapısında bir girdinin (entry) geçerliliği, yalnızca ve yalnızca o girdinin anahtarına (key) önbelleğin dışından hâlâ aktif referanslar bulunduğu sürece anlamlıysa, önbelleği bir WeakHashMap olarak temsil edin; girdiler eskidiklerinde (obsolete) otomatik olarak silineceklerdir. Unutmayın ki WeakHashMap yalnızca, önbellek girdilerinin arzulanan yaşam süresinin (desired lifetime) değere (value) değil, anahtara (key) yapılan dış referanslarca (external references) belirlendiği durumlarda işe yarar.

Daha yaygın olan senaryoda ise, bir önbellek girdisinin kullanışlı ömrü o kadar net tanımlanmış değildir; girdiler zamanla giderek daha az değerli hale gelir. Bu gibi koşullarda, önbellek zaman zaman artık kullanılmayan (fallen into disuse) girdilerden arındırılmalıdır. Bu işlem bir arka plan iş parçacığı (background thread) tarafından (belki bir ScheduledThreadPoolExecutor ile) ya da önbelleğe yeni girdiler eklenirken bir yan etki (side effect) olarak yapılabilir. LinkedHashMap sınıfı, removeEldestEntry metoduyla ikinci yaklaşımı kolaylaştırarak bize sunar. Daha sofistike önbellekler için ise doğrudan java.lang.ref paketini kullanmanız gerekebilir.

Bellek sızıntılarının üçüncü yaygın kaynağı ise dinleyiciler (listeners) ve diğer geri çağırmalardır (callbacks). İstemcilerin (clients) geri çağırmaları kaydettiği (register) ancak bunları açıkça iptal/silme kaydı (deregister) yapmadığı bir API uyguluyorsanız, siz bir önlem almadığınız sürece bu geri çağırmalar birikecek ve birikecektir (accumulate). Geri çağırmaların derhal Çöp Toplayıcı tarafından toplanmasını garanti altına almanın bir yolu, onlara yalnızca zayıf referanslar (weak references) saklamaktır; örneğin, bunları yalnızca bir WeakHashMap içinde anahtar (key) olarak depolayarak bu amaca ulaşabilirsiniz.

Bellek sızıntıları genellikle kendilerini apaçık, gözle görülür hatalar olarak belli etmezler (manifest); bu yüzden bir sistemde yıllarca fark edilmeden varlıklarını sürdürebilirler. Bunlar tipik olarak yalnızca dikkatli bir kod incelemesi (careful code inspection) sonucunda veya yığın profil oluşturucu (heap profiler) olarak bilinen bir hata ayıklama aracının (debugging tool) yardımıyla keşfedilirler. Bu nedenle, bu tarz problemleri daha oluşmadan öncesinde sezinlemeyi (anticipate) ve önlemeyi öğrenmek son derece arzu edilen ve değerli bir yetenektir.

...reference cells, not the objects themselves). The elements in the active portion of the array (as defined earlier) are allocated, and those in the remainder of the array are free. The garbage collector has no way of knowing this; to the garbage collector, all of the object references in the elements array are equally valid. Only the programmer knows that the inactive portion of the array is unimportant. The programmer effectively communicates this fact to the garbage collector by manually nulling out array elements as soon as they become part of the inactive portion.

Generally speaking, whenever a class manages its own memory, the programmer should be alert for memory leaks. Whenever an element is freed, any object references contained in the element should be nulled out.

Another common source of memory leaks is caches. Once you put an object reference into a cache, it's easy to forget that it's there and leave it in the cache long after it becomes irrelevant. There are several solutions to this problem. If you're lucky enough to implement a cache for which an entry is relevant exactly so long as there are references to its key outside of the cache, represent the cache as a WeakHashMap; entries will be removed automatically after they become obsolete. Remember that WeakHashMap is useful only if the desired lifetime of cache entries is determined by external references to the key, not the value.

More commonly, the useful lifetime of a cache entry is less well defined, with entries becoming less valuable over time. Under these circumstances, the cache should occasionally be cleansed of entries that have fallen into disuse. This can be done by a background thread (perhaps a ScheduledThreadPoolExecutor) or as a side effect of adding new entries to the cache. The LinkedHashMap class facilitates the latter approach with its removeEldestEntry method. For more sophisticated caches, you may need to use java.lang.ref directly.

A third common source of memory leaks is listeners and other callbacks. If you implement an API where clients register callbacks but don't deregister them explicitly, they will accumulate unless you take some action. One way to ensure that callbacks are garbage collected promptly is to store only weak references to them, for instance, by storing them only as keys in a WeakHashMap.

Because memory leaks typically do not manifest themselves as obvious failures, they may remain present in a system for years. They are typically discovered only as a result of careful code inspection or with the aid of a debugging tool known as a heap profiler. Therefore, it is very desirable to learn to anticipate problems like this before they occur and prevent them from happening.

WeakHashMap & Zayıf Referans (Weak Reference)

Java'da normal bir referans (strong reference), bir nesneyi bellekte mutlaka canlı tutar; Çöp Toplayıcı ona asla dokunamaz. WeakReference ise nesneye "zayıf" bir şekilde tutunur: eğer o nesneye başka hiçbir güçlü (strong) referans kalmamışsa, GC onu gönül rahatlığıyla toplayabilir.

WeakHashMap bu prensibi bir Map yapısına uygular. Anahtarlara (keys) zayıf referanslar tutar; bir anahtar dışarıdan artık kullanılmıyorsa, o girdi haritadan otomatik silinir. Tipik kullanımı: önbellekler ve meta-veri haritaları.

In Java, a normal (strong) reference keeps an object alive in memory — GC cannot touch it. A WeakReference holds on "weakly": if no strong references remain, GC can freely collect it.

WeakHashMap applies this principle to a Map. It holds keys via weak references; when a key is no longer referenced externally, the entry is automatically removed. Typical use: caches and metadata maps.

❌ KÖTÜ ÖRNEK (Before)

// Önbellek hiçbir zaman temizlenmiyor — sınırsız büyüme (unbounded growth) private static final Map<String, HeavyResource> cache = new HashMap<>(); public static void loadResource(String key) { cache.put(key, new HeavyResource(key)); // key dışarıda kullanılmasa bile cache sonsuza dek tutar! }

✅ İYİ ÖRNEK (After)

// Anahtar dış referansını kaybedince girdi otomatik silinir private static final Map<String, HeavyResource> cache = new WeakHashMap<>(); public static void loadResource(String key) { cache.put(key, new HeavyResource(key)); // key'e dış referans kalmadığında GC tarafından otomatik temizlenir }
💡 WeakHashMap yalnızca anahtarlara zayıf referans tutar, değerlere değil. Eğer değer doğrudan veya dolaylı olarak kendi anahtarına referans veriyorsa, anahtar hiçbir zaman GC tarafından toplanamaz — bu, gizli bir döngüsel referans tuzağıdır.

Önbellek Sızıntısı (Cache Memory Leak)

Önbellek (cache), sık erişilen verileri hızla sunmak için bellekte saklayan bir mekanizmadır. Ancak önbelleğe bir nesne koyduğunuzda ve onu bir daha temizlemeyi unuttuğunuzda, bu nesne sonsuza dek bellekte kalır — klasik bir bellek sızıntısı.

Çözüm stratejileri: (1) WeakHashMap ile otomatik temizleme, (2) LinkedHashMap.removeEldestEntry ile boyut sınırlama, (3) ScheduledThreadPoolExecutor ile periyodik temizlik.

A cache stores frequently accessed data in memory for fast retrieval. But if you put an object into a cache and never clean it up, that object stays forever — a classic memory leak.

Solution strategies: (1) WeakHashMap for auto-cleanup, (2) LinkedHashMap.removeEldestEntry for size-bounded caches, (3) ScheduledThreadPoolExecutor for periodic cleanup.

❌ KÖTÜ ÖRNEK (Before)

// Hiçbir boyut limiti yok; cache sürekli büyüyor private final Map<Long, UserProfile> profileCache = new HashMap<>(); public UserProfile getProfile(long userId) { return profileCache.computeIfAbsent(userId, this::loadFromDb); // Girdiler asla silinmiyor → OOM kaçınılmaz! }

✅ İYİ ÖRNEK (After)

// Maksimum 500 girdi; en eski girdi otomatik atılır private final Map<Long, UserProfile> profileCache = new LinkedHashMap<>(16, 0.75f, true) { @Override protected boolean removeEldestEntry(Map.Entry eldest) { return size() > 500; } };
💡 Gerçek dünya projelerinde Guava'nın CacheBuilder veya Caffeine gibi kütüphaneler zaman bazlı eviction, boyut sınırı ve istatistik toplama gibi gelişmiş özellikler sunar.

Dinleyici/Callback Sızıntısı (Listener & Callback Leak)

Bir API'de istemciler (clients) olay dinleyicileri (event listeners) veya geri çağırmalar (callbacks) kaydeder ama bunları açıkça iptal etmez (deregister). Sonuç: kayıtlı dinleyiciler birikir, her olay tetiklendiğinde tümü çağrılır, bellekte kilometrelerce uzun zincirleme referans grafikleri oluşur.

In an API, clients register event listeners or callbacks but never explicitly deregister them. The result: registered listeners pile up, all of them are invoked on every event, and long chains of reference graphs accumulate in memory.

❌ KÖTÜ ÖRNEK (Before)

public class EventBus { private final List<EventListener> listeners = new ArrayList<>(); public void register(EventListener listener) { listeners.add(listener); // İstemciler kayıt olur ama hiç deregister çağırmaz! } public void fireEvent(Event e) { for (EventListener l : listeners) l.onEvent(e); // Her tetiklemede kalabalık artıyor... } }

✅ İYİ ÖRNEK (After)

public class EventBus { // Zayıf referanslar: dinleyici dışarıda artık kullanılmıyorsa GC toplar private final Set<EventListener> listeners = Collections.newSetFromMap(new WeakHashMap<>()); public void register(EventListener listener) { listeners.add(listener); } public void fireEvent(Event e) { for (EventListener l : listeners) l.onEvent(e); } }
💡 Android'de en meşhur sızıntı senaryolarından biri de budur: bir Activity, bir servise listener olarak kayıt olur ama onDestroy()'da kaydını silmez; Activity bellekten silinmez ve bütün View hiyerarşisi hafızada asılı kalır.

Heap Profiler (Yığın Profil Oluşturucu)

Heap profiler, JVM'in yığın (heap) belleğindeki nesnelerin anlık fotoğrafını (snapshot) çekmenize ve hangi nesnelerin ne kadar alan kapladığını, hangi referansların onları canlı tuttuğunu analiz etmenize olanak tanıyan bir hata ayıklama aracıdır (debugging tool). Bellek sızıntılarını tespit etmenin en güvenilir yöntemidir.

Popüler araçlar: VisualVM (ücretsiz, JDK ile gelir), Eclipse MAT (Memory Analyzer Tool), YourKit ve JProfiler (ticari).

A heap profiler is a debugging tool that lets you take a snapshot of JVM heap memory and analyze which objects consume how much space and which references keep them alive. It's the most reliable way to detect memory leaks.

Popular tools: VisualVM (free, bundled with JDK), Eclipse MAT (Memory Analyzer Tool), YourKit and JProfiler (commercial).

💡 Bellek sızıntısından şüphelendiğinizde ilk adım: jmap -dump:format=b,file=heap.hprof <pid> komutunu çalıştırarak heap dump alın, sonra Eclipse MAT ile açıp "Leak Suspects" raporunu inceleyin.
