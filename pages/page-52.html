Chapter 3 — Item 13: clone Sözleşmesi
↩ Önceki sayfadan devam — Madde 13: clone sözleşmesi ve PhoneNumber clone uygulaması

Spesifikasyon söylemese de, pratikte Cloneable'ı uygulayan bir sınıfın düzgün çalışan bir genel (public) clone metodu sağlaması beklenir. Bunu başarmak için, sınıf ve tüm üst sınıfları karmaşık, uygulanamaz, yetersiz belgelenmiş bir protokole uymalıdır. Ortaya çıkan mekanizma kırılgan, tehlikeli ve dil-dışıdır (extralinguistic): yapıcı (constructor) çağırmadan nesneler oluşturur.

Yalnızca ilkel alanlar veya değişmez nesnelere referanslar içeren bir sınıfı düşünün. PhoneNumber sınıfı için clone metodu şöyle görünür:

In practice, a class implementing Cloneable is expected to provide a working public clone method. The resulting mechanism is fragile, dangerous, and creates objects without calling a constructor.

For a class with only primitives or immutable references, the clone for PhoneNumber looks like:

@Override public PhoneNumber clone() { try { return (PhoneNumber) super.clone(); } catch (CloneNotSupportedException e) { throw new AssertionError(); // Asla gerçekleşmez } }

Bu yöntemin çalışması için PhoneNumber'ın sınıf bildiriminin implements Cloneable içermesi gerekir. Object'in clone metodu Object döndürse de, bu clone metodu PhoneNumber döndürür. Kovaryant dönüş türleri (covariant return types) sayesinde, ezilen bir metodun alt türünü döndürmesi hem yasal hem de arzu edilir.

super.clone() çağrısı bir try-catch bloğu içindedir çünkü Object, clone metodunu CloneNotSupportedException fırlatmak üzere bildirir — kontrollü (checked) bir istisna. PhoneNumber Cloneable'ı uyguladığı için çağrının başarılı olacağını biliyoruz. Bu gereksiz şablon kodu (boilerplate), CloneNotSupportedException'ın kontrollü değil kontrolsüz (unchecked) olması gerektiğini gösterir (Madde 71).

Peki nesne değişebilir (mutable) nesnelere referans içeren alanlar taşıyorsa? Daha önce gösterilen basit clone uygulaması felaket olabilir. Madde 7'deki Stack sınıfını düşünün:

This works because of covariant return types. The try-catch is needed because Object.clone() throws CloneNotSupportedException (a checked exception). But if the object contains mutable references, the simple clone can be disastrous. Consider the Stack class from Item 7:

public class Stack { private Object[] elements; private int size = 0; private static final int DEFAULT_INITIAL_CAPACITY = 16; public Stack() { this.elements = new Object[DEFAULT_INITIAL_CAPACITY]; } public void push(Object e) { ensureCapacity(); elements[size++] = e; } public Object pop() { if (size == 0) throw new EmptyStackException(); Object result = elements[--size]; elements[size] = null; // Eskimiş referansı temizle return result; } ... }

super.clone() çağrısıyla elde edilen Stack örneğinin size alanı doğru olacak; ancak elements alanı orijinal Stack ile aynı diziyi referans alacaktır. Orijinali değiştirmek klondaki değişmezleri bozar ve tersi de geçerlidir.

The cloned Stack's elements field will reference the same array as the original. Modifying one destroys invariants in the other.

🔍 Kavramlar: 🔍 Concepts:

Sığ Kopya Sorunu (Shallow Copy)

super.clone() yalnızca "sığ kopya" (shallow copy) yapar — ilkel alanları kopyalar, nesne referanslarını ise paylaşır. Değişebilir nesnelere referans alanları olan sınıflarda bu felaket demektir: klon ve orijinal aynı iç durumu (state) paylaşır.

Çözüm: Değişebilir her alanı ayrıca klonlayın — "derin kopya" (deep copy).

super.clone() is a shallow copy — primitives are copied, object references are shared. For mutable fields, clone each one separately for a deep copy.

Kovaryant Dönüş Türü

Java 5'ten beri, ezilen bir metot üst sınıfın dönüş türünün alt türünü döndürebilir. Bu nedenle PhoneNumber.clone() metodunun Object yerine PhoneNumber döndürmesi mümkün ve tercih edilir — istemcinin tür dönüştürme (cast) yapmasına gerek kalmaz.

Since Java 5, overriding methods can return a subtype of the superclass's return type. PhoneNumber.clone() can return PhoneNumber instead of Object.
