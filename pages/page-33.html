Bu kod fena görünmeyebilir, ancak ikinci bir kaynak eklediğinizde durum kötüleşir:

This may not look bad, but it gets worse when you add a second resource:

// try-finally birden fazla kaynakla kullanıldığında çirkinleşir! // try-finally is ugly when used with more than one resource! static void copy(String src, String dst) throws IOException { InputStream in = new FileInputStream(src); try { OutputStream out = new FileOutputStream(dst); try { byte[] buf = new byte[BUFFER_SIZE]; int n; while ((n = in.read(buf)) >= 0) out.write(buf, 0, n); } finally { out.close(); } } finally { in.close(); } }

İnanması zor olabilir; ancak iyi programcılar bile çoğu zaman bunu yanlış yapmıştır. Her şeyden önce, ben bunu Java Puzzlers [Bloch05] kitabının 88. sayfasında yanlış yapmıştım ve kimse yıllarca fark etmedi. Aslında, 2007'de Java kütüphanelerindeki close metodu kullanımlarının üçte ikisi hatalıydı.

Önceki iki kod örneğinde gösterildiği gibi, try-finally ifadeleriyle kaynakları kapatmak için doğru yazılmış kodun bile ince bir eksikliği (subtle deficiency) vardır. Hem try bloğundaki hem de finally bloğundaki kod istisna fırlatabilir niteliktedir. Örneğin, firstLineOfFile metodunda readLine çağrısı, alttaki fiziksel aygıttaki (physical device) bir arıza nedeniyle bir istisna fırlatabilir ve ardından close çağrısı da aynı nedenle başarısız olabilir. Bu koşullar altında, ikinci istisna birincisini tamamen yok eder (obliterates). İstisna yığın izinde (exception stack trace) birinci istisnanın hiçbir kaydı kalmaz; bu durum, gerçek sistemlerde hata ayıklamayı büyük ölçüde zorlaştırabilir — çünkü genellikle sorunu teşhis etmek için görmek isteyeceğiniz istisna birincisidir. İkinci istisnayı birincisi lehine bastırmak (suppress) üzere kod yazmak mümkün olsa da, bunu neredeyse hiç kimse yapmadı çünkü fazla ayrıntılı (verbose) idi.

Tüm bu sorunlar, Java 7'nin try-with-resources ifadesini [JLS, 14.20.3] tanıtmasıyla tek seferde çözüldü (solved in one fell swoop). Bu yapıyla kullanılabilmek için, bir kaynağın AutoCloseable arayüzünü uygulaması gerekir; bu arayüz, void döndüren tek bir close metodundan oluşur. Java kütüphanelerindeki ve üçüncü parti kütüphanelerdeki birçok sınıf ve arayüz artık AutoCloseable'ı uygular veya genişletir. Eğer kapatılması gereken bir kaynağı temsil eden bir sınıf yazıyorsanız, sınıfınız da AutoCloseable'ı uygulamalıdır.

It may be hard to believe, but even good programmers got this wrong most of the time. For starters, I got it wrong on page 88 of Java Puzzlers [Bloch05], and no one noticed for years. In fact, two-thirds of the uses of the close method in the Java libraries were wrong in 2007.

Even the correct code for closing resources with try-finally statements, as illustrated in the previous two code examples, has a subtle deficiency. The code in both the try block and the finally block is capable of throwing exceptions. For example, in the firstLineOfFile method, the call to readLine could throw an exception due to a failure in the underlying physical device, and the call to close could then fail for the same reason. Under these circumstances, the second exception completely obliterates the first one. There is no record of the first exception in the exception stack trace, which can greatly complicate debugging in real systems—usually it's the first exception that you want to see in order to diagnose the problem. While it is possible to write code to suppress the second exception in favor of the first, virtually no one did because it's just too verbose.

All of these problems were solved in one fell swoop when Java 7 introduced the try-with-resources statement [JLS, 14.20.3]. To be usable with this construct, a resource must implement the AutoCloseable interface, which consists of a single void-returning close method. Many classes and interfaces in the Java libraries and in third-party libraries now implement or extend AutoCloseable. If you write a class that represents a resource that must be closed, your class should implement AutoCloseable too.

İstisna Yutma (Exception Obliteration)

try-finally bloğunda hem try hem finally istisna fırlatırsa, finally'deki istisna try'dakini tamamen yok eder. Yığın izinde (stack trace) yalnızca finally istisnası görünür; asıl hatanın (try bloğundaki) izi kaybolur.

try-with-resources ise bu sorunu çözer: close() istisnası "bastırılmış (suppressed)" olarak işaretlenir ve asıl istisna korunur. Throwable.getSuppressed() ile bastırılmış istisnalara erişilebilir.

In a try-finally, if both blocks throw, the finally exception obliterates the try exception completely. Only the finally exception appears in the stack trace; the root cause is lost.

try-with-resources fixes this: the close() exception is marked "suppressed" and the primary exception is preserved. Access suppressed exceptions via Throwable.getSuppressed().

❌ try-finally — asıl istisna kaybolur

try { reader.readLine(); // → IOException (asıl hata) } finally { reader.close(); // → IOException (asıl hatayı YOK EDER!) } // Stack trace'de yalnızca close() istisnası görünür 😱

✅ try-with-resources — asıl istisna korunur

try (BufferedReader reader = ...) { reader.readLine(); // → IOException (asıl hata — KORUNUR) } // close() istisnası "Suppressed" olarak eklenir // Stack trace: asıl hata + [Suppressed: close hatası]
💡 Bastırılmış istisnalar sayesinde hem asıl hatayı hem de kaynak kapatma hatasını görebilirsiniz — hata ayıklama çok daha kolaylaşır.

try-finally Tuzakları

Tuzak 1: İki kaynak → iç içe geçmiş (nested) try-finally blokları. Kod okunmaz hale gelir.

Tuzak 2: finally bloğundaki istisna, try bloğundakini yok eder.

Tuzak 3: Joshua Bloch bile Java Puzzlers kitabında bunu yanlış yapmış ve kimse yıllarca fark etmemiş! 2007'de JDK'daki close() çağrılarının 2/3'ü hatalıydı.

Pitfall 1: Two resources → nested try-finally blocks. Code becomes unreadable.

Pitfall 2: finally exception obliterates try exception.

Pitfall 3: Even Joshua Bloch got this wrong in Java Puzzlers, and no one noticed for years! In 2007, 2/3 of close() calls in the JDK were wrong.

💡 try-with-resources bu tuzakların hepsini ortadan kaldırır. Java 7+ kullanan her projede, hiçbir istisna olmaksızın (pun intended), try-with-resources tercih edin.
