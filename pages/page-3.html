The examples are reasonably complete, but favor readability over completeness. They freely use classes from packages java.util and java.io. In order to compile examples, you may have to add one or more import declarations, or other such boilerplate. The book's website contains an expanded version of each example, which you can compile and run.

Bu kitap çoğunlukla teknik terimleri The Java Language Specification, Java SE 8 Edition [JLS]'de tanımlandığı şekliyle kullanmaktadır. Birkaç terim özel olarak belirtilmeyi hak etmektedir. Dil dört tür tip (type) destekler: arayüzler (interfaces — ek açıklamalar (annotations) dahil), sınıflar (classes — enum'lar dahil), diziler (arrays) ve ilkel tipler (primitives). İlk üçü referans tipleri (reference types) olarak bilinir. Sınıf örnekleri (class instances) ve diziler nesnedir (objects); ilkel değerler (primitive values) nesne değildir. Bir sınıfın üyeleri (members); alanlar (fields), metotlar (methods), üye sınıflar (member classes) ve üye arayüzlerden (member interfaces) oluşur. Bir metodun imzası (signature), adından ve biçimsel parametrelerinin tiplerinden oluşur; imza, metodun dönüş tipini içermez.

For the most part, this book uses technical terms as they are defined in The Java Language Specification, Java SE 8 Edition [JLS]. A few terms deserve special mention. The language supports four kinds of types: interfaces (including annotations), classes (including enums), arrays, and primitives. The first three are known as reference types. Class instances and arrays are objects; primitive values are not. A class's members consist of its fields, methods, member classes, and member interfaces. A method's signature consists of its name and the types of its formal parameters; the signature does not include the method's return type.

Bu kitap birkaç terimi The Java Language Specification'dan farklı kullanmaktadır. The Java Language Specification'ın aksine bu kitap, kalıtım (inheritance) terimini alt sınıflama (subclassing) ile eş anlamlı olarak kullanır. Arayüzler için kalıtım terimi yerine bu kitap basitçe bir sınıfın bir arayüzü uyguladığını (implements) veya bir arayüzün başka bir arayüzü genişlettiğini (extends) belirtir. Hiçbir erişim düzeyi belirtilmediğinde geçerli olan erişim düzeyini tanımlamak için bu kitap, teknik olarak doğru olan paket erişimi (package access) [JLS, 6.6.1] yerine geleneksel paket-özel (package-private) terimini kullanır.

This book uses a few terms differently from The Java Language Specification. Unlike The Java Language Specification, this book uses inheritance as a synonym for subclassing. Instead of using the term inheritance for interfaces, this book simply states that a class implements an interface or that one interface extends another. To describe the access level that applies when none is specified, this book uses the traditional package-private instead of the technically correct package access [JLS, 6.6.1].

Referans Tipleri Reference Types
Reference Types vs. Primitive Types
Java'da tipler iki ana kategoriye ayrılır: ilkel tipler (primitives) ve referans tipleri (reference types). İlkel tipler (int, boolean, double vb.) doğrudan değer taşır. Referans tipleri (arayüzler, sınıflar, diziler) ise bellekteki bir nesneye işaret eder. Bu ayrım, performans, null güvenliği ve jenerik kullanımı açısından kritik öneme sahiptir. In Java, types fall into two main categories: primitive types and reference types. Primitives (int, boolean, double, etc.) carry values directly. Reference types (interfaces, classes, arrays) point to an object in memory. This distinction is critical for performance, null safety, and generics usage.
Kötü Örnek (Before) Bad Example (Before) 
// Gereksiz kutulama — performans kaybı
public static long sumFirstMillion() {
    Long sum = 0L;  // kutulu tip (boxed type)
    for (long i = 0; i < 1_000_000; i++) {
        sum += i;  // her döngüde yeni Long nesnesi!
    }
    return sum;
}
Long (referans tipi) yerine long (ilkel tip) kullanılmalıydı. Her toplama işleminde otomatik kutulama (autoboxing) gerçekleşerek milyonlarca gereksiz nesne oluşturulur ve performans ciddi ölçüde düşer. Long (reference type) should have been long (primitive). Autoboxing at each addition creates millions of unnecessary objects, severely degrading performance.
İyi Örnek (After) Good Example (After) 
// İlkel tip kullanarak verimli toplama
public static long sumFirstMillion() {
    long sum = 0L;  // ilkel tip (primitive)
    for (long i = 0; i < 1_000_000; i++) {
        sum += i;  // kutulama yok, hızlı
    }
    return sum;
}
İlkel long kullanarak kutulama masrafından tamamen kaçınılır. Bu basit değişiklik, performansı büyük ölçüde artırır. Referans tipleri yalnızca jenerik koleksiyonlar veya null değer gerektiğinde tercih edilmelidir. Using primitive long completely avoids boxing overhead. This simple change dramatically improves performance. Reference types should be preferred only for generic collections or when null values are needed.
Pratik İpucu: İlkel tipler ile kutulu karşılıkları arasında seçim yaparken, varsayılan olarak ilkel tipleri tercih edin. Integer, Long, Double gibi kutulu tipleri yalnızca koleksiyonlarda (List<Integer>) veya null semantiğine ihtiyaç duyduğunuzda kullanın. Practical Tip: When choosing between primitives and their boxed counterparts, prefer primitives by default. Use boxed types like Integer, Long, Double only in collections (List<Integer>) or when you need null semantics.
Metot İmzası Method Signature
Method Signature
Bir metodun imzası (signature), adından ve biçimsel parametrelerinin tiplerinden oluşur. Önemli bir detay: dönüş tipi imzanın parçası değildir. Bu, Java'da aynı ada ve parametre tiplerine sahip ancak farklı dönüş tipli iki metot tanımlayamayacağınız anlamına gelir. Metot aşırı yükleme (overloading) yalnızca parametre tipleri farklı olduğunda mümkündür. A method's signature consists of its name and the types of its formal parameters. An important detail: the return type is not part of the signature. This means you cannot define two methods with the same name and parameter types but different return types in Java. Method overloading is only possible when parameter types differ.
Kötü Örnek (Before) Bad Example (Before) 
// Derleme hatası! Aynı imza, farklı dönüş tipi
public class DataFetcher {

    public String fetch(String url) {
        return "raw response";
    }

    // DERLEME HATASI: fetch(String) zaten tanımlanmış
    public byte[] fetch(String url) {
        return new byte[0];
    }
}
İki metot da fetch(String) imzasına sahip. Dönüş tipi farklı olsa bile (String vs. byte[]), Java bunu aynı imza olarak değerlendirir ve derleme hatası verir. Both methods have the signature fetch(String). Even though return types differ (String vs. byte[]), Java treats them as the same signature and raises a compilation error.
İyi Örnek (After) Good Example (After) 
// Açık, farklı metot isimleri ile ayrım
public class DataFetcher {

    public String fetchAsText(String url) {
        return "raw response";
    }

    public byte[] fetchAsBytes(String url) {
        return new byte[0];
    }
}
Farklı metot adları (fetchAsText, fetchAsBytes) kullanarak hem derleme hatasından kaçınılır hem de API kendini belgelemiş olur. Metot adı, dönüş tipini zaten ima etmektedir. Using different method names (fetchAsText, fetchAsBytes) avoids the compilation error and makes the API self-documenting. The method name already implies the return type.
Pratik İpucu: Metot aşırı yüklemesi (overloading) yaparken dikkatli olun. Aynı parametre sayısına sahip aşırı yüklemelerden kaçının — bunun yerine farklı, açıklayıcı metot isimleri tercih edin. Bu hem okunabilirliği artırır hem de gelecekteki bakımı kolaylaştırır. Practical Tip: Be careful with method overloading. Avoid overloads with the same number of parameters — prefer different, descriptive method names instead. This improves readability and future maintainability.
Kalıtım Inheritance
Inheritance / Subclassing
Effective Java'da kalıtım (inheritance) terimi, alt sınıflama (subclassing) ile eş anlamlı kullanılır — yani bir sınıfın başka bir sınıfı genişletmesi (extends). Arayüz uygulaması (implements) veya arayüz genişletmesi kalıtım olarak adlandırılmaz. Bu ayrım önemlidir çünkü sınıf kalıtımı güçlü bir bağımlılık yaratırken, arayüz uygulaması daha esnek bir yapı sağlar. In Effective Java, inheritance is used as a synonym for subclassing — meaning a class extending another class (extends). Interface implementation (implements) or interface extension is not called inheritance. This distinction matters because class inheritance creates strong coupling, while interface implementation provides more flexibility.
Kötü Örnek (Before) Bad Example (Before) 
// Kırılgan kalıtım - üst sınıf değişirse bozulur
public class LoggingList<E>
        extends ArrayList<E> {

    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
        // BUG: addAll içeride add'ı çağırır!
        // Sayaç iki kez artırılır.
    }
}
ArrayList.addAll() dahili olarak add()'ı çağırır. Bu nedenle addAll çağrıldığında sayaç hem addAll'da hem de her add çağrısında artırılır. Üst sınıfın iç uygulama detaylarına bağımlılık, kırılgan bir kalıtım yaratır. ArrayList.addAll() internally calls add(). So when addAll is called, the counter is incremented both in addAll and in each add call. Dependency on the superclass's internal implementation details creates fragile inheritance.
İyi Örnek (After) Good Example (After) 
// Bileşim (composition) ile güvenli sarmalama
public class LoggingList<E>
        implements List<E> {

    private final List<E> delegate;
    private int addCount = 0;

    public LoggingList(List<E> delegate) {
        this.delegate = delegate;
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return delegate.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);
    }
    // ... diğer List metotları delegate'e yönlendirilir
}
Kalıtım yerine bileşim (composition) kullanılarak, delegate nesnesinin iç uygulama detaylarından bağımsız hale gelindi. addAll doğrudan delegate'e yönlendirilir ve sayaç doğru çalışır. By using composition instead of inheritance, we become independent of the delegate object's internal implementation. addAll is forwarded directly to the delegate and the counter works correctly.
Pratik İpucu: "Kalıtım yerine bileşimi tercih edin" (Favor composition over inheritance) — Effective Java'nın en önemli tavsiyelerinden biridir (Madde 18). Kalıtımı yalnızca gerçek bir "A bir B'dir" (is-a) ilişkisi varsa kullanın; aksi halde bileşim ve yönlendirme (delegation) tercih edin. Practical Tip: "Favor composition over inheritance" — one of the most important recommendations in Effective Java (Item 18). Use inheritance only when there is a genuine "is-a" relationship; otherwise, prefer composition and delegation.
Paket-Özel Erişim Package-Private Access
Package-Private (Default Access)
Java'da bir sınıf üyesine hiçbir erişim belirleyicisi (access modifier) verilmezse, o üye paket-özel (package-private) erişim düzeyine sahip olur. Bu, üyenin yalnızca aynı paketteki sınıflar tarafından erişilebilir olduğu anlamına gelir. Effective Java bu terimi, JLS'deki teknik olarak doğru olan paket erişimi (package access) yerine tercih eder. In Java, when no access modifier is specified for a class member, it has package-private access level. This means the member is accessible only by classes in the same package. Effective Java uses this term in preference to the technically correct package access from JLS.
Kötü Örnek (Before) Bad Example (Before) 
// Her şey public — kapsülleme ihlali
public class Point {
    public double x;
    public double y;

    public double distanceTo(Point other) {
        return Math.sqrt(
            Math.pow(x - other.x, 2)
            + Math.pow(y - other.y, 2));
    }

    public String formatForDebug() {
        return "(" + x + ", " + y + ")";
    }
}
Tüm alanlar ve yardımcı metotlar public yapılmış. formatForDebug gibi yalnızca dahili olarak kullanılan metotlar dışa açılmamalıdır. Alanlar doğrudan erişime açık olduğu için gelecekte temsil değişikliği yapılamaz. All fields and helper methods are public. Methods like formatForDebug that are only used internally should not be exposed. Since fields are directly accessible, representation changes are impossible in the future.
İyi Örnek (After) Good Example (After) 
// Doğru erişim düzeyleri ile kapsülleme
public class Point {
    private final double x;
    private final double y;

    public Point(double x, double y) {
        this.x = x;
        this.y = y;
    }

    public double distanceTo(Point other) {
        return Math.hypot(x - other.x, y - other.y);
    }

    // paket-özel: yalnızca aynı paketteki testler kullanır
    String formatForDebug() {
        return "(" + x + ", " + y + ")";
    }
}
Alanlar private final yapılarak kapsülleme sağlandı. formatForDebug metodu paket-özel bırakılarak yalnızca aynı paketteki kodlar (testler gibi) tarafından erişilebilir hale getirildi. Kamusal API sadece gerçekten gerekli olanları içeriyor. Fields are private final for encapsulation. formatForDebug is left package-private, accessible only to code in the same package (like tests). The public API contains only what is truly necessary.
Pratik İpucu: Erişim düzeylerini mümkün olan en kısıtlayıcı düzeyde tutun. Bir üyeyi public yapmadan önce kendinize sorun: "Bu üyeye paketin dışından erişilmesi gerçekten gerekli mi?" Paket-özel erişim, private ile public arasında güçlü bir ara seçenektir. Practical Tip: Keep access levels as restrictive as possible. Before making a member public, ask yourself: "Does this member really need to be accessed from outside the package?" Package-private access is a powerful middle ground between private and public.
