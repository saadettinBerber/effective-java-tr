Chapter 1: Introduction Bölüm 1: Giriş

bir programcının bir sınıfa, arayüze veya pakete erişmek için kullandığı sınıflar, arayüzler, yapıcı metotlar (constructors), üyeler ve serileştirilmiş formları (serialized forms) ifade eder. (API terimi, Application Programming Interface'in kısaltması olup, dil yapısı olan interface (arayüz) terimiyle karışıklığı önlemek amacıyla tercih edilen application programming interface ifadesi yerine kullanılmaktadır.) API kullanan bir program yazan programcıya, API'nin kullanıcısı (user) denir. Uygulaması bir API kullanan sınıf ise API'nin istemcisi (client) olarak adlandırılır.

classes, interfaces, constructors, members, and serialized forms by which a programmer accesses a class, interface, or package. (The term API, which is short for application programming interface, is used in preference to the otherwise preferable term interface to avoid confusion with the language construct of that name.) A programmer who writes a program that uses an API is referred to as a user of the API. A class whose implementation uses an API is a client of the API.

Sınıflar, arayüzler, yapıcı metotlar, üyeler ve serileştirilmiş formlar topluca API elemanları (API elements) olarak bilinir. Dışa aktarılan bir API (exported API), API'yi tanımlayan paketin dışından erişilebilen API elemanlarından oluşur. Bunlar, herhangi bir istemcinin kullanabileceği ve API yazarının desteklemeyi taahhüt ettiği API elemanlarıdır. Tesadüf değildir ki, bunlar aynı zamanda Javadoc yardımcı programının varsayılan çalışma modunda belgeleme oluşturduğu elemanlardır. Genel bir ifadeyle, bir paketin dışa aktarılan API'si, paketteki her kamusal (public) sınıf veya arayüzün kamusal ve korumalı (protected) üyeleri ile yapıcı metotlarından oluşur.

Classes, interfaces, constructors, members, and serialized forms are collectively known as API elements. An exported API consists of the API elements that are accessible outside of the package that defines the API. These are the API elements that any client can use and the author of the API commits to support. Not coincidentally, they are also the elements for which the Javadoc utility generates documentation in its default mode of operation. Loosely speaking, the exported API of a package consists of the public and protected members and constructors of every public class or interface in the package.

Java 9'da platforma bir modül sistemi (module system) eklendi. Bir kütüphane modül sistemini kullanıyorsa, dışa aktarılan API'si, kütüphanenin modül bildiriminin (module declaration) dışa aktardığı tüm paketlerin dışa aktarılan API'lerinin birleşimidir.

In Java 9, a module system was added to the platform. If a library makes use of the module system, its exported API is the union of the exported APIs of all the packages exported by the library's module declaration.

Dışa Aktarılan API Exported API
Exported API / Public API
Dışa aktarılan API (Exported API), bir paketin dışından erişilebilen API elemanlarının tamamıdır. Kamusal (public) sınıfların kamusal ve korumalı (protected) üyeleri bu kapsamdadır. Bir API'yi tasarlarken, dışa aktarılan kısmı mümkün olduğunca küçük tutmak önemlidir — çünkü bir kez yayımlandığında, geriye dönük uyumluluğu korumak için süresiz desteklenmelidir. An Exported API consists of all API elements accessible from outside a package. This includes public and protected members of public classes. When designing an API, keeping the exported part as small as possible is important — once published, it must be supported indefinitely for backward compatibility.
Kötü Örnek (Before) Bad Example (Before) 
// Çok geniş bir exported API — her şey public
public class HttpClient {
    public Socket socket;
    public int retryCount;
    public Map<String, String> headers;

    public void openSocket() { /* ... */ }
    public void writeHeaders() { /* ... */ }
    public void parseResponse() { /* ... */ }
    public String get(String url) { /* ... */ }
    public String post(String url, String body) { /* ... */ }
}
Dahili uygulama detayları (socket, openSocket, writeHeaders, parseResponse) kamusal API'nin bir parçası haline gelmiş. İstemciler bu detaylara bağımlı hale gelir ve gelecekte iç yapıyı değiştirmek imkansızlaşır. Internal implementation details (socket, openSocket, writeHeaders, parseResponse) have become part of the public API. Clients depend on these details, making future internal changes impossible.
İyi Örnek (After) Good Example (After) 
// Minimal exported API — yalnızca gerekli olanlar public
public class HttpClient {
    private Socket socket;
    private int retryCount;
    private Map<String, String> headers;

    public HttpClient(HttpClientConfig config) {
        /* yapılandırma ile başlatma */
    }

    public HttpResponse get(String url) { /* ... */ }
    public HttpResponse post(String url, String body) { /* ... */ }

    // Dahili metotlar — private
    private void openSocket() { /* ... */ }
    private void writeHeaders() { /* ... */ }
    private HttpResponse parseResponse() { /* ... */ }
}
Yalnızca get ve post metotları kamusal API'de yer alıyor. Dahili detaylar private yapılarak gizlendi. Dönüş tipi olarak tip-güvenli HttpResponse nesnesi kullanıldı. İç yapı serbestçe değiştirilebilir. Only get and post methods are in the public API. Internal details are hidden as private. A type-safe HttpResponse object is used as the return type. Internal structure can be freely changed.
Pratik İpucu: API tasarımında "şüpheye düşersen gizle" kuralını uygulayın. Bir üyeyi public yapmak kolaydır, ancak bir kez public yaptığınızda geri almak çok zordur — istemcileriniz ona bağımlı hale gelmiştir. Her zaman en kısıtlayıcı erişim düzeyinden başlayın. Practical Tip: Apply the "when in doubt, hide it" rule in API design. Making a member public is easy, but once it's public, taking it back is very hard — your clients have become dependent on it. Always start with the most restrictive access level.
API Elemanları API Elements
API Elements
API elemanları (API Elements), sınıflar, arayüzler, yapıcı metotlar (constructors), üyeler ve serileştirilmiş formların (serialized forms) tümünü kapsayan genel terimdir. Javadoc aracı varsayılan olarak bu elemanlar için belgeleme oluşturur. İyi belgelenmiş API elemanları, kütüphanenizin kullanılabilirliğini doğrudan etkiler. API Elements is the collective term covering classes, interfaces, constructors, members, and serialized forms. The Javadoc tool generates documentation for these elements by default. Well-documented API elements directly affect the usability of your library.
Kötü Örnek (Before) Bad Example (Before) 
// Belgelenmemiş API elemanları
public class CacheManager {
    public void put(String k, Object v, long t) {
        /* ... */
    }

    public Object get(String k, boolean f) {
        /* ... */
    }
}
Parametreler (k, v, t, f) hiçbir anlam ifade etmiyor. Javadoc yok. Dönüş tipi Object. Boolean parametre ne işe yarıyor belli değil. İstemci bu API'yi anlamak için kaynak kodu okumak zorunda. Parameters (k, v, t, f) convey no meaning. No Javadoc. Return type is Object. The boolean parameter's purpose is unclear. A client must read source code to understand this API.
İyi Örnek (After) Good Example (After) 
/**
 * İş parçacığı güvenli (thread-safe) önbellek yöneticisi.
 * Girişlerin belirli bir süre sonra otomatik süresi dolar.
 */
public class CacheManager<V> {

    /**
     * Verilen anahtar ile değeri önbelleğe ekler.
     *
     * @param key   önbellek anahtarı, null olamaz
     * @param value saklanacak değer
     * @param ttl   yaşam süresi (time-to-live)
     * @param unit  zaman birimi
     */
    public void put(String key, V value,
                     long ttl, TimeUnit unit) {
        /* ... */
    }

    /**
     * Verilen anahtar ile ilişkili değeri döndürür.
     *
     * @return değer, veya anahtar bulunamazsa boş Optional
     */
    public Optional<V> get(String key) {
        /* ... */
    }
}
Sınıf jenerik yapılarak tip güvenliği sağlandı. Parametreler açıklayıcı isimler taşıyor. Javadoc ile her elemanın ne yaptığı belgelenmiş. Optional dönüş tipiyle null döndürme anti-kalıbından kaçınılmış. Boolean parametre kaldırılıp yerine daha anlamlı bir API sunulmuş. The class is made generic for type safety. Parameters have descriptive names. Javadoc documents each element. Optional return type avoids the null-return antipattern. The boolean parameter was removed in favor of a more meaningful API.
Pratik İpucu: Kamusal (public) API elemanlarınızın her biri için Javadoc yazın. Bu sadece belgeleme değildir — Javadoc yazmak sizi API'nizi dışarıdan bir gözle değerlendirmeye zorlar. Eğer bir metodu Javadoc'ta açıklamakta zorlanıyorsanız, muhtemelen API tasarımınız iyileştirilmelidir. Practical Tip: Write Javadoc for every public API element. This is not just documentation — writing Javadoc forces you to evaluate your API from an outside perspective. If you struggle to explain a method in Javadoc, your API design probably needs improvement.
Modül Sistemi Module System
Java Platform Module System (JPMS) — Java 9
Java 9 ile birlikte gelen modül sistemi (Java Platform Module System / JPMS), paketlerin ötesinde ek bir kapsülleme katmanı sağlar. Bir modül, module-info.java dosyasında hangi paketleri dışa aktardığını ve hangi modüllere bağımlı olduğunu bildirir. Bu sayede, public olan sınıflar bile modül tarafından dışa aktarılmadığı sürece dış dünyaya görünür olmaz. The module system introduced in Java 9 (Java Platform Module System / JPMS) provides an additional layer of encapsulation beyond packages. A module declares which packages it exports and which modules it depends on in a module-info.java file. This way, even public classes are not visible to the outside world unless exported by the module.
Kötü Örnek (Before) Bad Example (Before) 
// Modül kullanmadan — tüm public sınıflar herkese açık
// com/mylib/internal/DatabaseHelper.java
package com.mylib.internal;

public class DatabaseHelper {
    public static Connection getRawConnection() {
        // Dahili kullanım için tasarlanmış
        // ama public olduğu için herkes erişebilir!
        return DriverManager.getConnection("...");
    }
}
internal paketindeki sınıf kamusal olduğu için, modül sistemi olmadan kütüphane kullanıcıları bu dahili sınıfa erişebilir ve ona bağımlı hale gelebilir. Paket adında "internal" yazması hiçbir şeyi zorlamaz. Since the class in the internal package is public, without the module system, library users can access and depend on this internal class. Having "internal" in the package name enforces nothing.
İyi Örnek (After) Good Example (After) 
// module-info.java — yalnızca API paketini dışa aktar
module com.mylib {
    exports com.mylib.api;
    // com.mylib.internal dışa aktarılMAZ
    // → DatabaseHelper dışarıdan erişilemez
}

// com/mylib/api/DatabaseService.java — kamusal API
package com.mylib.api;

public class DatabaseService {
    public QueryResult execute(String query) {
        // İç detayları gizleyerek güvenli erişim sağlar
    }
}
module-info.java dosyası yalnızca com.mylib.api paketini dışa aktarıyor. com.mylib.internal paketi ve içindeki DatabaseHelper sınıfı, public olsa bile modül dışından erişilemez hale geliyor. Bu, gerçek kapsülleme sağlar. The module-info.java file only exports com.mylib.api. The com.mylib.internal package and its DatabaseHelper class become inaccessible from outside the module, even though they are public. This provides true encapsulation.
Pratik İpucu: Yeni bir kütüphane tasarlıyorsanız, modül sistemini en baştan kullanmayı düşünün. Bu, dahili uygulama detaylarınızı gerçek anlamda korur ve API yüzeyinizi küçük tutar. Mevcut projeler için geçiş zor olabilir, ancak yeni projeler için büyük avantaj sağlar. Practical Tip: If you're designing a new library, consider using the module system from the start. This truly protects your internal implementation details and keeps your API surface small. Migration can be difficult for existing projects, but it provides a significant advantage for new ones.
