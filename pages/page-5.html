Chapter 2: Creating and Destroying Objects Bölüm 2: Nesnelerin Oluşturulması ve Yok Edilmesi

Bu bölüm nesnelerin oluşturulması ve yok edilmesiyle ilgilenir: nesneleri ne zaman ve nasıl oluşturmalı, ne zaman ve nasıl oluşturmaktan kaçınmalı, zamanında yok edilmelerini nasıl sağlamalı ve yok edilmelerinden önce gerçekleşmesi gereken temizlik işlemlerini nasıl yönetmelisiniz.

This chapter concerns creating and destroying objects: when and how to create them, when and how to avoid creating them, how to ensure they are destroyed in a timely manner, and how to manage any cleanup actions that must precede their destruction.

Madde 1: Yapıcı Metot Yerine Statik Fabrika Metotlarını Düşünün Item 1: Consider Static Factory Methods Instead of Constructors

Item 1: Consider static factory methods instead of constructors Madde 1: Yapıcı Metot Yerine Statik Fabrika Metotlarını Düşünün

Bir sınıfın istemcilere (clients) bir örneğini (instance) sağlamasının geleneksel yolu, kamusal (public) bir yapıcı metot (constructor) sunmaktır. Her programcının araç kutusunda olması gereken bir teknik daha vardır. Bir sınıf, sınıfın bir örneğini döndüren kamusal bir statik fabrika metodu (static factory method) sağlayabilir. İşte Boolean sınıfından (boolean için sarmalayıcı ilkel sınıf / boxed primitive class) basit bir örnek. Bu metot, bir boolean ilkel (primitive) değerini bir Boolean nesne referansına dönüştürür:

The traditional way for a class to allow a client to obtain an instance is to provide a public constructor. There is another technique that should be a part of every programmer's toolkit. A class can provide a public static factory method, which is simply a static method that returns an instance of the class. Here's a simple example from Boolean (the boxed primitive class for boolean). This method translates a boolean primitive value into a Boolean object reference: 

public static Boolean valueOf(boolean b) {
    return b ? Boolean.TRUE : Boolean.FALSE;
}

Bir statik fabrika metodunun, Design Patterns kitabındaki [Gamma95] Factory Method tasarım kalıbıyla (design pattern) aynı şey olmadığına dikkat edin. Bu maddede açıklanan statik fabrika metodunun Design Patterns'da doğrudan bir karşılığı yoktur.

Note that a static factory method is not the same as the Factory Method pattern from Design Patterns [Gamma95]. The static factory method described in this item has no direct equivalent in Design Patterns.

Bir sınıf, istemcilerine kamusal yapıcı metotlar yerine veya bunlara ek olarak statik fabrika metotları sağlayabilir. Kamusal bir yapıcı metot yerine statik fabrika metodu sağlamanın hem avantajları hem de dezavantajları vardır.

A class can provide its clients with static factory methods instead of, or in addition to, public constructors. Providing a static factory method instead of a public constructor has both advantages and disadvantages.

Statik fabrika metotlarının yapıcı metotlara göre birinci avantajı, yapıcıların aksine isimlerinin olmasıdır. Bir yapıcı metodun parametreleri, kendi başlarına döndürülen nesneyi tanımlamıyorsa, iyi seçilmiş bir isme sahip bir statik fabrika, kullanımı daha kolay ve ortaya çıkan istemci kodunu daha okunabilir kılar. Örneğin, muhtemelen asal (prime) olan bir BigInteger döndüren BigInteger(int, int, Random) yapıcı metodu, BigInteger.probablePrime adlı bir statik fabrika metodu olarak ifade edilseydi çok daha iyi olurdu. (Bu metot Java 4'te eklendi.)

One advantage of static factory methods is that, unlike constructors, they have names. If the parameters to a constructor do not, in and of themselves, describe the object being returned, a static factory with a well-chosen name is easier to use and the resulting client code easier to read. For example, the constructor BigInteger(int, int, Random), which returns a BigInteger that is probably prime, would have been better expressed as a static factory method named BigInteger.probablePrime. (This method was added in Java 4.)

Bir sınıf, verilen bir imzaya (signature) sahip yalnızca tek bir yapıcı metoda sahip olabilir. Programcıların bu kısıtlamayı, parametre listeleri yalnızca parametre tiplerinin sırasında farklılık gösteren iki yapıcı metot sunarak aştıkları bilinmektedir. Bu gerçekten kötü bir fikirdir. Böyle bir API'nin kullanıcısı hangi yapıcının hangisi olduğunu asla hatırlayamayacak ve sonunda yanlış olanı çağıracaktır. Bu yapıcıları kullanan kodu okuyan kişiler, sınıf belgelerine (documentation) başvurmadan kodun ne yaptığını bilemeyeceklerdir.

A class can have only a single constructor with a given signature. Programmers have been known to get around this restriction by providing two constructors whose parameter lists differ only in the order of their parameter types. This is a really bad idea. The user of such an API will never be able to remember which constructor is which and will end up calling the wrong one by mistake. People reading code that uses these constructors will not know what the code does without referring to the class documentation.

İsimlere sahip oldukları için, statik fabrika metotları önceki paragrafta tartışılan kısıtlamayı paylaşmazlar. Bir sınıfın aynı imzaya sahip birden fazla yapıcı metoda ihtiyaç duyduğu durumlarda, yapıcıları farklılıklarını vurgulayan dikkatle seçilmiş isimlerle statik fabrika metotlarıyla değiştirin.

Because they have names, static factory methods don't share the restriction discussed in the previous paragraph. In cases where a class seems to require multiple constructors with the same signature, replace the constructors with static factory methods and carefully chosen names to highlight their differences.

Statik fabrika metotlarının yapıcı metotlara göre ikinci avantajı, her çağrıldıklarında yeni bir nesne oluşturmak zorunda olmamalarıdır. Bu, değişmez sınıfların (immutable classes) (Madde 17) önceden oluşturulmuş örnekleri (instances) kullanmasına veya örnekleri oluşturdukça önbelleğe almasına ve gereksiz kopya nesneler oluşturmaktan kaçınmak için bunları tekrar tekrar dağıtmasına olanak tanır. Boolean.valueOf(boolean) metodu bu tekniği gösterir: hiçbir zaman bir nesne oluşturmaz. Bu teknik, Flyweight kalıbına [Gamma95] benzerdir. Eşdeğer nesneler sıkça isteniyorsa, özellikle oluşturulmaları pahalıysa, performansı büyük ölçüde iyileştirebilir.

A second advantage of static factory methods is that, unlike constructors, they are not required to create a new object each time they're invoked. This allows immutable classes (Item 17) to use preconstructed instances, or to cache instances as they're constructed, and dispense them repeatedly to avoid creating unnecessary duplicate objects. The Boolean.valueOf(boolean) method illustrates this technique: it never creates an object. This technique is similar to the Flyweight pattern [Gamma95]. It can greatly improve performance if equivalent objects are requested often, especially if they are expensive to create.

Statik fabrika metotlarının tekrarlanan çağrılarda aynı nesneyi döndürebilmesi, sınıfların herhangi bir anda hangi örneklerin var olduğu üzerinde sıkı kontrol sağlamasına olanak tanır. Bunu yapan sınıflar örnek-kontrollü (instance-controlled) olarak adlandırılır. Örnek-kontrollü sınıflar yazmanın birkaç nedeni vardır. Örnek kontrolü, bir sınıfın tekil (singleton) (Madde 3) veya örneklenemez (noninstantiable) (Madde 4) olduğunu garanti etmeye olanak tanır. Ayrıca, değişmez bir değer sınıfının (immutable value class) (Madde 17) hiçbir iki eşit örneğin var olmadığını garanti etmesini sağlar: a.equals(b) ancak ve ancak a == b ise doğrudur. Bu, Flyweight kalıbının [Gamma95] temelidir. Enum tipleri (Madde 34) bu garantiyi sağlar.

The ability of static factory methods to return the same object from repeated invocations allows classes to maintain strict control over what instances exist at any time. Classes that do this are said to be instance-controlled. There are several reasons to write instance-controlled classes. Instance control allows a class to guarantee that it is a singleton (Item 3) or noninstantiable (Item 4). Also, it allows an immutable value class (Item 17) to make the guarantee that no two equal instances exist: a.equals(b) if and only if a == b. This is the basis of the Flyweight pattern [Gamma95]. Enum types (Item 34) provide this guarantee.

Statik fabrika metotlarının yapıcı metotlara göre üçüncü avantajı, dönüş tiplerinin herhangi bir alt tipinin (subtype) nesnesini döndürebilmeleridir. Bu, döndürülen nesnenin sınıfını seçmede büyük esneklik sağlar.

A third advantage of static factory methods is that, unlike constructors, they can return an object of any subtype of their return type. This gives you great flexibility in choosing the class of the returned object.

Bu esnekliğin bir uygulaması, bir API'nin sınıflarını kamusal yapmadan nesneler döndürebilmesidir. Uygulama sınıflarını bu şekilde gizlemek, çok kompakt bir API'ye yol açar. Bu teknik kendisini arayüz tabanlı çerçevelere (interface-based frameworks) (Madde 20) ödünç verir; burada arayüzler, statik fabrika metotları için doğal dönüş tipleri sağlar.

One application of this flexibility is that an API can return objects without making their classes public. Hiding implementation classes in this fashion leads to a very compact API. This technique lends itself to interface-based frameworks (Item 20), where interfaces provide natural return types for static factory methods.

Java 8'den önce, arayüzler static metotlara sahip olamıyordu. Geleneksel olarak, Type adlı bir arayüz için statik fabrika metotları, Types adlı örneklenemez bir eşlikçi sınıfa (companion class) (Madde 4) konulurdu. Örneğin, Java Koleksiyonlar Çerçevesi (Java Collections Framework), arayüzlerinin kırk beş yardımcı uygulamasını sunarak değiştirilemez koleksiyonlar (unmodifiable collections), senkronize koleksiyonlar (synchronized collections) ve benzeri işlevleri sağlar. Bu uygulamaların neredeyse tamamı, tek bir örneklenemez sınıf olan java.util.Collections içindeki statik fabrika metotları aracılığıyla dışa aktarılır. Döndürülen nesnelerin sınıfları tamamen kamusal olmayan (nonpublic) sınıflardır.

Prior to Java 8, interfaces couldn't have static methods. By convention, static factory methods for an interface named Type were put in a noninstantiable companion class (Item 4) named Types. For example, the Java Collections Framework has forty-five utility implementations of its interfaces, providing unmodifiable collections, synchronized collections, and the like. Nearly all of these implementations are exported via static factory methods in one noninstantiable class (java.util.Collections). The classes of the returned objects are all nonpublic.

Statik Fabrika Metodu Static Factory Method
Static Factory Method
Statik fabrika metodu (Static Factory Method), bir sınıfın yapıcı metodu yerine (veya ek olarak) sınıfın örneğini döndüren statik bir metottur. new anahtar kelimesi yerine anlamlı isimlerle nesne oluşturmayı sağlar. Yapıcıların aksine, her çağrıda yeni nesne oluşturmak zorunda değildir ve dönüş tipinin alt tiplerini döndürebilir. A Static Factory Method is a static method that returns an instance of a class instead of (or in addition to) a constructor. It enables object creation with meaningful names rather than the new keyword. Unlike constructors, it doesn't have to create a new object on each invocation and can return subtypes of the return type.
Kötü Örnek (Before) Bad Example (Before) 
// Yapıcı metotlar — hangisi ne döndürüyor?
public class Color {
    private final int r, g, b;

    public Color(int r, int g, int b) {
        this.r = r; this.g = g; this.b = b;
    }
}

// İstemci kodu — niyeti anlamak zor
Color c1 = new Color(255, 0, 0);
Color c2 = new Color(0, 128, 0);
Yapıcı metot çağrısından neyin oluşturulduğu belli değil. new Color(255, 0, 0) ifadesinin kırmızı renk olduğunu anlamak için sınıf belgesine bakmak gerekir. Aynı imzayla başka renk uzayları (HSB gibi) desteklenemez. It's unclear what is being created from the constructor call. Understanding that new Color(255, 0, 0) is red requires reading documentation. Other color spaces (like HSB) cannot be supported with the same signature.
İyi Örnek (After) Good Example (After) 
public class Color {
    private final int r, g, b;

    private Color(int r, int g, int b) {
        this.r = r; this.g = g; this.b = b;
    }

    public static Color fromRGB(int r, int g, int b) {
        return new Color(r, g, b);
    }

    public static Color fromHSB(float h, float s, float b) {
        // HSB → RGB dönüşümü
        return new Color(/* ... */);
    }

    public static Color red() {
        return new Color(255, 0, 0);
    }
}

// İstemci kodu — niyet açık
Color c1 = Color.red();
Color c2 = Color.fromHSB(0.33f, 1.0f, 0.5f);
fromRGB, fromHSB, red isimleri niyeti açıkça belirtir. Farklı parametre tipleriyle farklı oluşturma yolları sunulabilir. Sık kullanılan renkler için önbelleğe alma kolayca eklenebilir. Yapıcı private yapılarak kontrol sağlanmıştır. Names like fromRGB, fromHSB, red clearly express intent. Different creation paths with different parameter types are easily supported. Caching for frequently used colors can be easily added. The constructor is made private for control.
Pratik İpucu: Bir sınıfta birden fazla yapıcı metoda ihtiyaç duyduğunuzda, statik fabrika metotlarına geçmeyi düşünün. of, from, valueOf, getInstance, create gibi yaygın isimlendirme kalıplarını kullanın. Bu kalıplar, diğer programcıların kodunuzu hızlıca anlamasını sağlar. Practical Tip: When you need multiple constructors, consider switching to static factory methods. Use common naming conventions like of, from, valueOf, getInstance, create. These conventions help other programmers quickly understand your code.
Örnek-Kontrollü Sınıf Instance-Controlled Class
Instance-Controlled Class
Örnek-kontrollü sınıf (Instance-Controlled Class), hangi örneklerin (instances) var olduğunu kontrol altında tutan bir sınıftır. Statik fabrika metotları sayesinde sınıf, tekil (singleton), örneklenemez (noninstantiable) veya eşit örneklerin tekrarlanmadığı garanti sağlayabilir. Boolean, Integer (önbellek aralığında), Enum tipleri bu yaklaşımın örnekleridir. An Instance-Controlled Class maintains control over which instances exist. Through static factory methods, the class can guarantee singleton, noninstantiability, or that no two equal instances exist. Boolean, Integer (within cache range), and Enum types are examples of this approach.
Kötü Örnek (Before) Bad Example (Before) 
// Kontrol yok — her çağrıda yeni nesne
public class CurrencyUnit {
    private final String code;

    public CurrencyUnit(String code) {
        this.code = code;
    }
}

// Her çağrıda yeni nesne — bellek israfı
CurrencyUnit usd1 = new CurrencyUnit("USD");
CurrencyUnit usd2 = new CurrencyUnit("USD");
System.out.println(usd1 == usd2); // false!
Aynı para birimi için her seferinde yeni bir nesne oluşturuluyor. == karşılaştırması başarısız oluyor. Bellek israfı ve tutarsızlık riski var. Para birimi gibi sınırlı sayıda değeri olan kavramlar için gereksiz çoğaltma yapılıyor. A new object is created each time for the same currency. The == comparison fails. There's memory waste and inconsistency risk. For concepts with a limited number of values like currency, unnecessary duplication occurs.
İyi Örnek (After) Good Example (After) 
public class CurrencyUnit {
    private static final Map<String, CurrencyUnit> CACHE =
        new ConcurrentHashMap<>();

    private final String code;

    private CurrencyUnit(String code) {
        this.code = code;
    }

    public static CurrencyUnit of(String code) {
        return CACHE.computeIfAbsent(code, CurrencyUnit::new);
    }
}

CurrencyUnit usd1 = CurrencyUnit.of("USD");
CurrencyUnit usd2 = CurrencyUnit.of("USD");
System.out.println(usd1 == usd2); // true!
Yapıcı private yapılarak doğrudan nesne oluşturma engellendi. of fabrika metodu, aynı kod için her zaman aynı nesneyi döndürür. == ile güvenle karşılaştırılabilir. ConcurrentHashMap ile iş parçacığı güvenliği sağlandı. The constructor is private, preventing direct instantiation. The of factory method always returns the same object for the same code. Safe == comparison is possible. Thread safety is ensured with ConcurrentHashMap.
Pratik İpucu: Sınırlı sayıda değeri temsil eden sınıflar (para birimi, renk, durum kodları) için örnek kontrolü uygulayın. Eğer değer kümesi derleme zamanında (compile time) biliniyorsa, Enum kullanmayı tercih edin — Java'nın en güçlü örnek-kontrol mekanizmasıdır. Practical Tip: Apply instance control for classes representing a limited set of values (currency, color, status codes). If the value set is known at compile time, prefer using Enum — it's Java's most powerful instance-control mechanism.
Arayüz Tabanlı Çerçeve Interface-Based Framework
Interface-Based Framework
Arayüz tabanlı çerçeve (Interface-Based Framework), API'sini arayüzler (interfaces) üzerinden tanımlayan ve uygulama sınıflarını gizleyen bir yazılım çerçevesidir. Statik fabrika metotları, arayüz tipini döndürerek istemcilerin yalnızca arayüze bağımlı olmasını sağlar. Java Koleksiyonlar Çerçevesi (java.util.Collections) bunun en bilinen örneğidir. An Interface-Based Framework defines its API through interfaces and hides implementation classes. Static factory methods return the interface type, ensuring clients depend only on the interface. The Java Collections Framework (java.util.Collections) is the best-known example.
Kötü Örnek (Before) Bad Example (Before) 
// Uygulama sınıfı doğrudan açığa çıkıyor
public class JsonParser {
    public JsonObject parse(String json) { /* ... */ }
}
public class XmlParser {
    public XmlDocument parse(String xml) { /* ... */ }
}

// İstemci somut sınıflara bağımlı
JsonParser parser = new JsonParser();
İstemci kodu doğrudan JsonParser somut sınıfına bağımlıdır. Farklı bir parser kullanmak istediğinde tüm istemci kodu değişmelidir. Dönüş tipleri de farklıdır (JsonObject vs XmlDocument), polimorfizm kullanılamaz. Client code depends directly on the JsonParser concrete class. Switching to a different parser requires changing all client code. Return types differ (JsonObject vs XmlDocument), preventing polymorphism.
İyi Örnek (After) Good Example (After) 
// Arayüz tabanlı tasarım
public interface DocumentParser {
    Document parse(String input);
}

// Statik fabrika — uygulama sınıfları gizli
public class Parsers {
    private Parsers() {} // örneklenemez

    public static DocumentParser json() {
        return new JsonParserImpl();
    }

    public static DocumentParser xml() {
        return new XmlParserImpl();
    }
}

// İstemci yalnızca arayüze bağımlı
DocumentParser parser = Parsers.json();
Document doc = parser.parse(input);
İstemci yalnızca DocumentParser arayüzüne bağımlıdır. JsonParserImpl ve XmlParserImpl sınıfları paket-özel (package-private) olabilir. Uygulama değiştirildiğinde istemci kodu etkilenmez. Parsers eşlikçi sınıfı, örneklenemez yapılarak tek sorumluluk üstlenmiştir. The client depends only on the DocumentParser interface. JsonParserImpl and XmlParserImpl can be package-private. When the implementation changes, client code is unaffected. The Parsers companion class is made noninstantiable with a single responsibility.
Pratik İpucu: Java 8+ kullanıyorsanız, statik fabrika metotlarını doğrudan arayüzün içine koyabilirsiniz — ayrı bir eşlikçi sınıfa gerek kalmaz. Ancak uygulama kodu büyükse, yine de ayrı bir paket-özel sınıfa taşımak API'yi temiz tutar. Practical Tip: If you're using Java 8+, you can put static factory methods directly in the interface — no need for a separate companion class. However, if the implementation code is large, moving it to a separate package-private class still keeps the API clean.
