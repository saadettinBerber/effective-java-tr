Item 5: Prefer dependency injection to hardwiring resources

Pek çok sınıf, bir veya daha fazla temel kaynağa (underlying resource) bağımlıdır. Örneğin, bir yazım denetleyicisi (spell checker), bir sözlüğe bağımlıdır. Bu tür sınıfların statik yardımcı bir sınıf (static utility class) (Madde 4) şeklinde gerçekleşirildiğini görmek oldukça olağandır:

Many classes depend on one or more underlying resources. For example, a spell checker depends on a dictionary. It is not uncommon to see such classes implemented as static utility classes (Item 4):

// Yanlış: Statik yardımcı sınıfı kullanmak - Esnek değil (inflexible) ve test edilemez (untestable)! // Inappropriate use of static utility - inflexible & untestable! public class SpellChecker { private static final Lexicon dictionary = ...; private SpellChecker() {} // Örneklenemez (Noninstantiable) public static boolean isValid(String word) { ... } public static List<String> suggestions(String typo) { ... } }

Benzer şekilde, bunların Singleton (Madde 3) şeklinde gerçekleştirilmeleri de çok yaygındır:

Similarly, it’s not uncommon to see them implemented as singletons (Item 3):

// Yanlış: Singleton kalıbı kullanmak - Esnek değil ve test edilemez! // Inappropriate use of singleton - inflexible & untestable! public class SpellChecker { private final Lexicon dictionary = ...; private SpellChecker(...) {} public static INSTANCE = new SpellChecker(...); public boolean isValid(String word) { ... } public List<String> suggestions(String typo) { ... } }

Her iki yaklaşım da tatmin edici değildir, çünkü hepsi tek bir sözlük kullandığını veya tek bir sözlüğün yeteceğini varsayar. Uygulamada, her dilin kendi farklı sözlükleri vardır ve test evresi veya farklı özel amaçlı sözcük dağarcıkları için yine başka sözlükler gerekir. Tek bir sözlüğün sonsuza kadar işimizi çözeceğini ummak maalesef iyimserlikten öteye gidemez.

Siz de SpellChecker'ı birden çok sözlüğü desteklemesi için modifiye etmeyi düşünebilir, sözlük alanını (field) nonfinal yapıp sözlüğü metod ile değiştirebileceğinizi kurgulayabilirsiniz ancak bu hantal (awkward), hataya açık ve özellikle çok izlekli (concurrent) programlamada çalışması pek olası olmayan (unworkable) bir hal alır. Statik yardımcı sınıfları veya Singleton'lar, davranışları belirli kaynak (ya da kaynakların) girdisine (parameterized by resource) bağlılık gösteren durumlar için uygun tasarımlar değillerdir.

İhtiyacımız olan şey, aynı sınıftan (örneğin SpellChecker) her biri istenilen/ayrı kaynağı kullanan birbirinden bağımsız birden çok örneği (multiple instances) destekleme yeteneğidir.

Neither of these approaches is satisfactory, because they assume that there is only one dictionary worth using. In practice, each language has its own dictionary, and special dictionaries are used for special vocabularies. Also, it may be desirable to use a special dictionary for testing. It is wishful thinking to assume that a single dictionary will suffice for all time.

You could try to have SpellChecker support multiple dictionaries by making the dictionary field nonfinal and adding a method to change the dictionary in an existing spell checker, but this would be awkward, error-prone, and unworkable in a concurrent setting. Static utility classes and singletons are inappropriate for classes whose behavior is parameterized by an underlying resource.

Bağımlılık Enjeksiyonu / Dependency Injection (DI)

Bağımlılık enjeksiyonu (DI), bir sınıfın ihtiyaç duyduğu diğer nesneleri (bağımlılıkları) kendisinin new ile yaratması veya bir Singleton havuzundan çekip zorla alması yerine; kurucular (constructors), metotlar ya da DI frameworkleri aracılığıyla dışarıdan temin etme/aktarma fikridir. Bu sayede sınıflar test edilebilir, esnek ve başka yerlerde kullanılabilir hale gelirler.

Dependency Injection (DI) is the idea that rather than a class creating the objects it needs (via new or reaching into a Singleton), those dependencies are passed in from the outside (injected) typically via constructors. This makes the class testable, flexible, and reusable.

✗ KÖTÜ — Koda gömülü bağımlılık alanı (Hardwiring)
public class NotificationService { // Kendi loglarını yaratmayı seçmiş: private final Logger logger = new FileLogger("/var/log/app.log"); public void send(String msg) { logger.log("Sending " + msg); ... } }
✓ İYİ — Bağımlılık Enjeksiyonu (Constructor Injection)
public class NotificationService { private final Logger logger; // Hangi tip logger'ı seçeceğinize Dışarısı (istemci) karar verecek public NotificationService(Logger logger) { this.logger = logger; } } // İstemciniz istediği logger'ı enjekte edebilir: NotificationService emailSvc = new NotificationService(new ConsoleLogger()); NotificationService smsSvc = new NotificationService(new FileLogger());

Tight Coupling (Sıkı Bağımlılık)

Bir modül (veya sınıf), başka bir modüle yoğun derecede bağımlı olduğunda buna sıkı bağlılık (tight coupling) denir. Singleton sınıflar veya direkt new kullanarak oluşturulan somut bileşenler sıkı bağımlılığa neden olur, bu da bakım ve test zorluğu yaratır.

When a module or class relies heavily on another concrete class, it is said to be tightly coupled. Singletons and hardcoding instantiation with new create tight coupling, leading to maintenance and testing nightmares.

💡 Kural basit: "New considers true, Interface handles all." Ne kadar az new, o kadar gevşek bağımlılık (Loose Coupling)! (Veri taşıyan basit nesneler: List, String vb. için kural geçerli değildir.)
💡 The rule of thumb is: Limit new to value objects (data containers). For behavioral services, rely on interfaces and inject them. This promotes Loose Coupling.
