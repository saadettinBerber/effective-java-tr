NutritionFacts — Builder Kalıbı (tamamı)
NutritionFacts — Builder Pattern (complete)
// Builder Kalıbı (devam)
        public Builder fat(int val)
            { fat = val;          return this; }
        public Builder sodium(int val)
            { sodium = val;       return this; }
        public Builder carbohydrate(int val)
            { carbohydrate = val; return this; }

        public NutritionFacts build() {
            return new NutritionFacts(this);
        }
    }

    private NutritionFacts(Builder builder) {
        servingSize  = builder.servingSize;
        servings     = builder.servings;
        calories     = builder.calories;
        fat          = builder.fat;
        sodium       = builder.sodium;
        carbohydrate = builder.carbohydrate;
    }
}

NutritionFacts sınıfı değiştirilemez (immutable) olup tüm parametre varsayılan değerleri tek bir yerde toplanmıştır. Builder'ın setter metotları, çağrıların zincirlenebilmesi için Builder'ın kendisini döndürmektedir; bu da akıcı bir API (fluent API) oluşturur. İstemci kodu şu şekilde görünür:

The NutritionFacts class is immutable, and all parameter default values are in one place. The builder's setter methods return the builder itself so that invocations can be chained, resulting in a fluent API. Here's how the client code looks: 

NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
    .calories(100).sodium(35).carbohydrate(27).build();
✓ Sonuç: Bu istemci kodu yazmak kolaydır ve — daha önemlisi — okumak da kolaydır. Builder kalıbı, Python ve Scala'da bulunan adlandırılmış opsiyonel parametreleri (named optional parameters) simüle eder. ✓ Result: This client code is easy to write and, more importantly, easy to read. The Builder pattern simulates named optional parameters as found in Python and Scala.

Geçerlilik kontrolleri (validity checks), kısalık adına kod örneğinde çıkarılmıştır. Geçersiz parametreleri olabildiğince erken tespit etmek için, Builder'ın yapıcısında ve metotlarında parametre geçerliliğini denetleyin. build() metodu tarafından çağrılan yapıcıda ise birden fazla parametreyi birden ilgilendiren değişmezleri (invariants) denetleyin. Bu değişmezleri saldırılara karşı korumak için, kontrolleri Builder'dan parametreler kopyalandıktan sonra nesnenin kendi alanları üzerinde gerçekleştirin (Madde 50). Bir denetim başarısız olursa, hangi parametrelerin geçersiz olduğunu belirten bir ayrıntı mesajı içeren IllegalArgumentException (Madde 72) fırlatın (Madde 75).

Validity checks were omitted for brevity. To detect invalid parameters as soon as possible, check parameter validity in the builder's constructor and methods. Check invariants involving multiple parameters in the constructor invoked by the build method. To ensure these invariants against attack, do the checks on object fields after copying parameters from the builder (Item 50). If a check fails, throw an IllegalArgumentException (Item 72) whose detail message indicates which parameters are invalid (Item 75).

Builder kalıbı sınıf hiyerarşilerine (class hierarchies) son derece uygundur. Her sınıfa karşılık gelen, o sınıfın içine yuvalanmış (nested) paralel bir Builder hiyerarşisi kullanın. Soyut (abstract) sınıfların soyut Builder'ları; somut (concrete) sınıfların somut Builder'ları olur. Örneğin, çeşitli pizza türlerini temsil eden bir hiyerarşinin kökündeki soyut sınıfı düşünün:

Geçerlilik Kontrolü (Validity Check) Validity Check
Parametrelerin olabildiğince erken doğrulanması Validating parameters as early as possible
Builder kalıbında geçerlilik kontrolleri iki yerde yapılabilir: Builder'ın setter metotlarında (tek parametre kontrolleri) ve build() içindeki private yapıcıda (birden fazla parametreyi ilgilendiren değişmezler). Bu strateji "erken başarısız ol (fail-fast)" prensibini uygular. In the Builder pattern, validity checks can happen in two places: in the Builder's setter methods (single-parameter checks) and in the private constructor called by build() (multi-parameter invariants). This strategy implements the "fail-fast" principle.
✗ Kötü (kontrol yok, hata uzak noktada) 
// Kötü: Geçersiz değer nesneye girdi, hata çok sonra fırlatılıyor
public Builder timeout(int millis) {
    this.timeout = millis; // negatif değer kabul edildi!
    return this;
}
// ... çok sonra: timeout -1 ile ağ bağlantısı açılmaya çalışılıyor
Geçersiz değer sessizce depolanıyor; hata çok sonra, tamamen farklı bir kodda ortaya çıkıyor. Invalid value is silently stored; error surfaces much later in completely different code.
✓ İyi (setter'da erken kontrol) 
// İyi: Geçersiz değer hemen reddediliyor
public Builder timeout(int millis) {
    if (millis <= 0)
        throw new IllegalArgumentException(
            "timeout sıfırdan büyük olmalı, verildi: " + millis);
    this.timeout = millis;
    return this;
}
// Hata tam burada, açık bir mesajla fırlatılıyor
Hata, geçersiz değerin girildiği noktada, net bir mesajla fırlatılıyor. Hata ayıklama (debug) çok daha kolay. Error is thrown at the point of invalid input with a clear message. Debugging is much easier.
💡 İpucu: IllegalArgumentException hangi parametrenin geçersiz olduğunu ve neden geçersiz olduğunu açıkça belirtmelidir. Örnek: "timeout must be positive: " + timeout. 💡 Tip: The IllegalArgumentException should clearly state which parameter is invalid and why. Example: "timeout must be positive: " + timeout.
Değişmez (Invariant) Invariant
Nesne ömrü boyunca her zaman doğru olması gereken koşul A condition that must always be true throughout an object's lifetime
Değişmez (invariant), bir nesnenin tüm ömrü boyunca doğru kalması gereken koşuldur. Birden fazla parametreyi ilgilendiren değişmezler (örneğin "başlangıç tarihi bitiş tarihinden önce olmak zorunda") Builder'ın yapıcısında — parametreler kopyalandıktan sonra — denetlenmelidir. An invariant is a condition that must remain true throughout an object's lifetime. Multi-parameter invariants (e.g., "start date must be before end date") should be checked in the Builder's constructor — after parameters are copied from the builder.
✗ Kötü (değişmez denetlenmiyor) 
// Kötü: DateRange nesnesi geçersiz oluşturulabilir
public DateRange(Builder b) {
    this.start = b.start;
    this.end   = b.end;
    // Kontrol yok! start > end durumu sessizce geçebilir
}
start ve end arasındaki ilişki denetlenmiyor. Nesne geçersiz bir tarih aralığıyla oluşturulabiliyor. The relationship between start and end is not checked. Object can be created with an invalid date range.
✓ İyi (değişmez yapıcıda denetleniyor) 
// İyi: Değişmez build() tarafından çağrılan yapıcıda denetleniyor
private DateRange(Builder b) {
    this.start = b.start;
    this.end   = b.end;
    // Parametreler kopyalandıktan sonra kontrol et (Madde 50)
    if (this.start.isAfter(this.end))
        throw new IllegalArgumentException(
            "start (" + start + ") bitiş tarihinden sonra olamaz: " + end);
}
Alanlar kopyalandıktan sonra denetleniyor (kopyalama saldırısına karşı koruma). Her DateRange nesnesi geçerli garantilidir. Check is done after copying fields (protection against copy attacks). Every DateRange object is guaranteed valid.
💡 İpucu: Kontrolleri Builder parametrelerinde değil, nesnenin kendi alanlarında yapın. Bu, kötü niyetli bir başlıksız saldırıya (untrusted subclass attack) karşı koruma sağlar. 💡 Tip: Perform checks on the object's own fields, not on the builder's parameters. This protects against malicious subclass attacks.
Builder ile Sınıf Hiyerarşisi Builder with Class Hierarchy
Soyut sınıflara soyut Builder'lar, somut sınıflara somut Builder'lar Abstract builders for abstract classes, concrete builders for concrete classes
Builder kalıbı sınıf hiyerarşileriyle son derece iyi çalışır. Her sınıfta iç içe (nested) bir Builder alt sınıfı tanımlanır. Soyut sınıfın soyut Builder'ı, alt sınıflarda somutlaştırılır. Bu sayede her alt sınıf, atadan gelen tüm opsiyonları kullanabileceği gibi kendi opsiyonlarını da ekleyebilir. The Builder pattern works extremely well with class hierarchies. A nested Builder subclass is defined in each class. The abstract Builder from the parent is concretized in subclasses. Each subclass can use all options from the parent while adding its own.
✗ Kötü (hiyerarşide Builder yok) 
// Kötü: Her alt sınıf için farklı yapıcı imzaları
Vehicle car   = new Car("Toyota", 4, true, false, "red");
Vehicle truck = new Truck("Ford", 6, 5000, false, true);
// Her alt sınıf farklı bir API — tutarsız, okunaksız
Her alt sınıf farklı bir yapıcı imzasına sahip. Tutarsız API, hataya açık. Each subclass has a different constructor signature. Inconsistent API, error-prone.
✓ İyi (paralel Builder hiyerarşisi) 
// İyi: Paralel Builder hiyerarşisi, tutarlı API
Vehicle car = new Car.Builder("Toyota")
    .doors(4)
    .color("red")
    .sunroof(true)
    .build();

Vehicle truck = new Truck.Builder("Ford")
    .axles(6)
    .maxLoad(5000)
    .build();
// Her alt sınıf kendi özgün alanlarına sahip, ama API tutarlı
Her alt sınıf kendi Builder'ını kalıtım yoluyla genişletiyor. API tutarlı, okumak ve kullanmak kolay. Each subclass extends its own Builder via inheritance. Consistent API, easy to read and use.
💡 İpucu: Builder hiyerarşisinde simulated self-type (benzetilmiş kendi tipi) deyimini kullanın: abstract T self() metoduyla alt sınıfların Builder setter metotları casting gerektirmeden çalışabilir hale gelir. 💡 Tip: Use the simulated self-type idiom in Builder hierarchies: an abstract T self() method lets subclass Builder setters work without casting.
