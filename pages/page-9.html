Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün Item 2: Consider a Builder When Faced with Many Constructor Parameters

Item 2: Consider a builder when faced with many constructor parameters Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün

Statik fabrikalar ve yapıcı metotlar (constructors) ortak bir sınırlamayı paylaşır: çok sayıda opsiyonel (optional) parametreye iyi ölçeklenmezler. Paketlenmiş gıdaların üzerinde görülen Besin Bilgileri etiketini temsil eden bir sınıf düşünün. Bu etiketlerin birkaç zorunlu alanı vardır — porsiyon büyüklüğü (serving size), kaptaki porsiyon sayısı (servings per container) ve porsiyon başına kalori (calories per serving) — ve yirmiden fazla opsiyonel alanı vardır: toplam yağ, doymuş yağ, trans yağ, kolesterol, sodyum vb. Çoğu ürün bu opsiyonel alanların yalnızca birkaçında sıfırdan farklı değerlere sahiptir.

Static factories and constructors share a limitation: they do not scale well to large numbers of optional parameters. Consider the case of a class representing the Nutrition Facts label that appears on packaged foods. These labels have a few required fields—serving size, servings per container, and calories per serving—and more than twenty optional fields—total fat, saturated fat, trans fat, cholesterol, sodium, and so on. Most products have nonzero values for only a few of these optional fields.

Böyle bir sınıf için ne tür yapıcı metotlar veya statik fabrikalar yazmalısınız? Geleneksel olarak, programcılar teleskopik yapıcı (telescoping constructor) kalıbını kullanmışlardır; bu kalıpta yalnızca zorunlu parametrelere sahip bir yapıcı, tek bir opsiyonel parametreli başka bir yapıcı, iki opsiyonel parametreli başka bir yapıcı ve böyle devam ederek, tüm opsiyonel parametreleri içeren bir yapıcıyla sonlandırılır. İşte pratikte nasıl göründüğü. Kısa tutmak amacıyla yalnızca dört opsiyonel alan gösterilmektedir:

What sort of constructors or static factories should you write for such a class? Traditionally, programmers have used the telescoping constructor pattern, in which you provide a constructor with only the required parameters, another with a single optional parameter, a third with two optional parameters, and so on, culminating in a constructor with all the optional parameters. Here's how it looks in practice. For brevity's sake, only four optional fields are shown: 

// Teleskopik yapıcı kalıbı - iyi ölçeklenmez!
public class NutritionFacts {
    private final int servingSize;  // (mL)            zorunlu
    private final int servings;     // (per container)  zorunlu
    private final int calories;    // (per serving)    opsiyonel
    private final int fat;         // (g/serving)      opsiyonel
    private final int sodium;      // (mg/serving)     opsiyonel
    private final int carbs;       // (g/serving)      opsiyonel

    public NutritionFacts(int servingSize, int servings) {
        this(servingSize, servings, 0);
    }

    public NutritionFacts(int servingSize, int servings,
                           int calories) {
        this(servingSize, servings, calories, 0);
    }

    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat) {
        this(servingSize, servings, calories, fat, 0);
    }

    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat, int sodium) {
        this(servingSize, servings, calories, fat, sodium, 0);
    }

    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat, int sodium,
                           int carbs) {
        this.servingSize = servingSize;
        this.servings = servings;
        this.calories = calories;
        this.fat = fat;
        this.sodium = sodium;
        this.carbs = carbs;
    }
}

Örneğin, yalnızca servingSize (240), servings (8), calories (100) ve fat (35) öğelerini ayarlamak istediğinizde şu şekilde yapılır:

When you want to create an instance, you use the constructor with the shortest parameter list containing all the parameters you want to set: 

NutritionFacts cocaCola = new NutritionFacts(240, 8, 100, 35, 0, 0);

Genellikle bu yapıcı çağrısı, ayarlamak istemediniz ama ayarlamanız gereken birçok parametreyi gerektirir. Fakat burada, sodium (sodyum) için 0 değeri geçtik. Opsiyonel parametreler altı olur olmaz, bu çok kötü hale gelir. Kısa cümlede söyleyelim: teleskopik yapıcı kalıbı çalışır, ancak çok sayıda parametre olduğunda istemci kodu yazması ve okuması çok zordur. Okuyan kişi bu değerlerin ne anlama geldiğini anlamak için parametre sırası ezberleme zorunluluğunda kalır ve tipik olarak kod içinde birbirine yakın yazılmış sayı dizilerini görür:

Typically this constructor invocation will require many parameters that you don't want to set, but you're forced to pass a value for them anyway. In this case, we passed a value of 0 for fat. With only six parameters this may not seem so bad, but it quickly gets out of hand as the number of parameters increases. In short, the telescoping constructor pattern works, but it is hard to write client code when there are many parameters, and harder still to read it. The reader is left wondering what all those values mean and must carefully count parameters to find out:

Diğer bir seçenek de JavaBeans kalıbı (JavaBeans pattern) kullanmaktır; burada boş bir yapıcıyla nesne oluşturulur ve ardından setter metotlar (setter methods) ile istenen alanlar ayarlanır:

A second alternative is the JavaBeans pattern, in which you call a parameterless constructor to create the object and then call setter methods to set each required and optional parameter: 

// JavaBeans kalıbı
NutritionFacts cocaCola = new NutritionFacts();
cocaCola.setServingSize(240);
cocaCola.setServings(8);
cocaCola.setCalories(100);
cocaCola.setFat(35);

Maalesef, JavaBeans kalıbının kendine ait ciddi dezavantajları vardır. Nesne, oluşturma işlemi tamamlanmadan (setterler çağrılmadan) tutarsız bir durumda (inconsistent state) olabilir. JavaBeans kalıbı da yapıcı ve statik fabrika metotlarından (static factory methods) — yani değişmezliği (immutability) sağlamak imkansız kılmaktadır. Bu, thread güvenliğini (thread safety) sağlamak için ekstra çaba gerektirir.

Unfortunately, the JavaBeans pattern has serious disadvantages of its own. Because construction is split across multiple calls, a JavaBeans object may be in an inconsistent state partway through its construction. The class does not have the option of enforcing consistency merely by checking constructor parameters. It is also impossible to make a JavaBeans class immutable (Item 17), and it requires added effort on the part of the programmer to ensure thread safety.

Neyse ki üçüncü bir seçenek vardır: Builder kalıbı (Builder pattern). İstemci, gerekli parametreleri ile bir Builder nesnesi oluşturur ve daha sonra setter benzeri metotlarla (setter-like methods) opsiyonel parametreleri ayarlar. Son olarak istemci, değişmez (immutable) nesneyi döndüren build() metotunu çağırır. Builder, genellikle oluşturduğu sınıfın bir statik üye sınıfıdır (static member class):

There is a third alternative that combines the safety of the telescoping constructor pattern with the readability of the JavaBeans pattern. It is a form of the Builder pattern [Gamma95]. Instead of making the desired object directly, the client calls a constructor (or static factory) with all of the required parameters and gets a builder object. Then the client calls setter-like methods on the builder object to set each optional parameter of interest. Finally, the client calls a parameterless build method to generate the object, which is typically immutable. The builder is typically a static member class (Item 24) of the class it builds. Here's how it looks in practice: 

// Builder kalıbı
public class NutritionFacts {
    private final int servingSize;
    private final int servings;
    private final int calories;
    private final int fat;
    private final int sodium;
    private final int carbs;

    public static class Builder {
        // Gerekli parametreler
        private final int servingSize;
        private final int servings;

        // Opsiyonel parametreler - varsayılan değerler
        private int calories    = 0;
        private int fat         = 0;
        private int sodium      = 0;
        private int carbs       = 0;

        public Builder(int servingSize, int servings) {
            this.servingSize = servingSize;
            this.servings = servings;
        }

        public Builder calories(int val)
            { calories = val; return this; }
        public Builder fat(int val)
            { fat = val; return this; }
        public Builder sodium(int val)
            { sodium = val; return this; }
        public Builder carbs(int val)
            { carbs = val; return this; }

        public NutritionFacts build() {
            return new NutritionFacts(this);
        }
    }

    private NutritionFacts(Builder builder) {
        servingSize = builder.servingSize;
        servings = builder.servings;
        calories = builder.calories;
        fat = builder.fat;
        sodium = builder.sodium;
        carbs = builder.carbs;
    }
}

İstemci kodu okunması kolay olması için yazılır:

Client code is much easier to write when the builder is in use: 

NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
    .calories(100)
    .fat(35)
    .sodium(35)
    .carbs(27)
    .build();

Bu istemci kodu yazması ve okuması son derece kolaydır. Builder kalıbı, Python ve Scala gibi adlandırılmış opsiyonel parametreleri (named optional parameters) olan dillerdeki yapının çok iyi bir simülasyonudur. Teklifin (proposal) gözlemleri (insight) söyledir: Builder kalıbı, Bölüm 4'te (Item 18) ele alınan bileşim (composition) tarafından istenen doğru desenin bir varyasyonudur ve çok sayıda opsiyonel parametreye sahip sınıfları tanımlamak için mükemmel bir seçimdir.

This client code is much easier to write and, far more importantly, much easier to read. The Builder pattern simulates the optional parameters found in Python and Scala. Critically, the Builders can have default values for their parameters. The builder is smart enough to fill in parameters. The NutritionFacts class is immutable, and all parameter defaulting is done in the builder. The build method could check invariants (Item 49). It is very simple to make the builder thread-safe if multiple threads are to share a builder.

Teleskopik Yapıcı Kalıbı Telescoping Constructor Pattern
Telescoping Constructor Pattern
Teleskopik yapıcı kalıbı, çok sayıda opsiyonel parametreye sahip sınıflar için giderek artan sayıda parametre içeren yapıcı metotlar zinciri oluşturmaktır. Her yapıcı bir öncekini çağırır ve yeni bir parametre ekler. Parametre sayısı arttıkça kod okunması ve yazılması çok zorlaşır — hangi parametrenin ne anlama geldiğini takip etmek neredeyse imkansız hale gelir. The Telescoping Constructor Pattern creates a chain of constructors with increasing numbers of parameters for classes with many optional parameters. Each constructor calls the previous one and adds a new parameter. As the parameter count grows, the code becomes very hard to read and write — tracking which parameter means what becomes nearly impossible.
Kötü Örnek (Before) Bad Example (Before) 
// Teleskopik yapıcı — çok sayıda yapıcı gerekli
public class DatabaseConfig {
    private final String host;     // zorunlu
    private final int port;              // zorunlu
    private final String username;  // opsiyonel
    private final String password;  // opsiyonel
    private final int timeout;          // opsiyonel

    public DatabaseConfig(String host, int port) {
        this(host, port, "", "", 5000);
    }

    public DatabaseConfig(String host, int port,
                             String username) {
        this(host, port, username, "", 5000);
    }

    public DatabaseConfig(String host, int port,
                             String username, String password) {
        this(host, port, username, password, 5000);
    }

    public DatabaseConfig(String host, int port,
                             String username, String password,
                             int timeout) {
        this.host = host;
        this.port = port;
        this.username = username;
        this.password = password;
        this.timeout = timeout;
    }
}
Beş parametre için dört yapıcı gerekli. İki parametre daha eklersek bu sayı katlanır. Çağrı tarafında new DatabaseConfig("localhost", 5432, "admin", "pass", 10000) hangi parametrenin ne olduğu açık değildir. Five parameters require four constructors. Add two more parameters and the number doubles. At the call site, new DatabaseConfig("localhost", 5432, "admin", "pass", 10000) doesn't make it clear which parameter is which.
İyi Örnek (After) Good Example (After) 
// Builder kalıbı — okunabilir ve ölçeklenebilir
public class DatabaseConfig {
    private final String host;
    private final int port;
    private final String username;
    private final String password;
    private final int timeout;

    public static class Builder {
        private final String host;
        private final int port;
        private String username = "";
        private String password = "";
        private int timeout = 5000;

        public Builder(String host, int port) {
            this.host = host;
            this.port = port;
        }
        public Builder username(String u) { username = u; return this; }
        public Builder password(String p) { password = p; return this; }
        public Builder timeout(int t) { timeout = t; return this; }

        public DatabaseConfig build() {
            return new DatabaseConfig(this);
        }
    }
    private DatabaseConfig(Builder b) {
        this.host = b.host;
        this.port = b.port;
        this.username = b.username;
        this.password = b.password;
        this.timeout = b.timeout;
    }
}

// Kullanım — her parametre açıkça görülür
DatabaseConfig config = new DatabaseConfig.Builder("localhost", 5432)
    .username("admin")
    .password("secret")
    .timeout(10000)
    .build();
Builder ile her parametre adla belirtilir. .username("admin") yazmak, beşinci pozisyon argümanı geçmekten çok daha okunabilir. Yeni bir parametre eklersek sadece Builder'a bir metot eklemek yeterlidir. With Builder, each parameter is specified by name. Writing .username("admin") is far more readable than passing a fifth positional argument. If we add a new parameter, we just add a method to the Builder.
Pratik İpucu: Üç veya daha fazla opsiyonel parametreniz varsa, teleskopik yapıcı yerine Builder kalıbını düşünün. Özellikle parametreler aynı tipteyse (birden fazla String veya int gibi), Builder yazılı hataları (yazım ve tür hatalarını) önler ve kodu okunaklı tutar. Practical Tip: If you have three or more optional parameters, prefer the Builder pattern over telescoping constructors. Especially when parameters share the same type (multiple Strings or ints), Builder prevents errors and keeps code readable.
JavaBeans Kalıbı JavaBeans Pattern
JavaBeans Pattern
JavaBeans kalıbı, boş bir yapıcı metotla nesne oluşturmak ve ardından set metotlarıyla alanları ayarlamaktır. Okunabilirlik açısından teleskopik yapıcıdan iyidir, ancak ciddi sorunları vardır: nesne oluşturma sırasında tutarsız durumda olabilir ve değişmez nesne oluşturması imkansızdır. The JavaBeans pattern creates an object with a no-argument constructor and then sets fields via setter methods. It's more readable than telescoping constructors, but has serious problems: the object can be in an inconsistent state during construction, and immutability is impossible.
Kötü Örnek (Before) Bad Example (Before) 
// JavaBeans kalıbı — tutarsız durum riski
public class Point {
    private int x;
    private int y;

    public Point() { }
    public void setX(int x) { this.x = x; }
    public void setY(int y) { this.y = y; }
}

// Nesne tutarsız durumda kalabilir
Point p = new Point();
p.setX(10);
// Bu noktada y henüz ayarlanmadı — tutarsız!
p.setY(20);
setX ve setY arasında Point nesnesi eksik bir durumda (tutarsız). Eğer başka bir thread bu noktada nesneyi erişirse, yanlış veriler alabilir. Between setX and setY, the Point object is in an incomplete state (inconsistent). If another thread accesses it at this point, it may get incorrect data.
İyi Örnek (After) Good Example (After) 
// Builder kalıbı — güvenli ve değişmez
public class Point {
    private final int x;
    private final int y;

    public static class Builder {
        private int x = 0;
        private int y = 0;

        public Builder x(int val) { x = val; return this; }
        public Builder y(int val) { y = val; return this; }

        public Point build() {
            return new Point(x, y);
        }
    }
    private Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}

// Kullanım — her zaman tutarlı
Point p = new Point.Builder()
    .x(10)
    .y(20)
    .build();
// p tamamen oluşturulmuş, tutarlı ve değişmez
Builder kalıbı ile build() çağrılana kadar nesne oluşturulmaz. Bu süreçte nesne tutarsız durumda olmaz. Sonuçta elde edilen Point nesnesi değişmezdir (final alanlar). With the Builder pattern, the object isn't created until build() is called. The object is never in an inconsistent state. The resulting Point object is immutable (final fields).
Pratik İpucu: JavaBeans kalıbı sade göründüğü halde, thread güvenliği sorunları ve tutarsız durum riskleri nedeniyle multi-threaded uygulamalarda zararlıdır. Builder kalıbı özellikle değişmez nesneler gereken durumlarda (veritabanı modelleri, konfigürasyon sınıfları) tercih edilmelidir. Practical Tip: The JavaBeans pattern seems simple but poses thread-safety and consistency risks in multi-threaded applications. The Builder pattern is especially preferred when immutable objects are needed (database models, configuration classes).
Builder Kalıbı Builder Pattern
Builder Pattern (GoF Design Pattern)
Builder kalıbı, karmaşık nesnelerin adım adım oluşturulmasını sağlayan bir tasarım kalıbıdır. İstemci önce bir Builder nesnesi oluşturur (zorunlu parametreleri geçerek), ardından setter benzeri metotlarla istenen parametreleri belirler ve son olarak build() çağrısıyla değişmez (immutable) nesneyi elde eder. Bu kalıp hem okunabilirlik hem de güvenlik sağlar: nesne tamamlanmadan kullanılamaz ve alan değerleri sonradan değiştirilemez. The Builder Pattern is a design pattern for step-by-step construction of complex objects. The client first creates a Builder object (passing required parameters), sets desired parameters through setter-like methods, and finally obtains the immutable object via a build() call. This pattern provides both readability and safety: the object cannot be used before completion, and field values cannot be changed afterward.
Kötü Örnek (Before) Bad Example (Before) 
// Teleskopik yapıcı — karmaşık ve kötü okunabilir
public class HttpClient {
    private final String host;
    private final int port;
    private final String protocol;
    private final String userAgent;
    private final int timeout;
    private final boolean followRedirects;

    public HttpClient(String h, int p) {
        this(h, p, "HTTP", "Java", 5000, true);
    }
    public HttpClient(String h, int p, String proto) {
        this(h, p, proto, "Java", 5000, true);
    }
    // ... 4 daha yapıcı
    public HttpClient(String h, int p, String proto,
                         String ua, int t, boolean fr) {
        host = h; port = p; protocol = proto;
        userAgent = ua; timeout = t; followRedirects = fr;
    }
}

new HttpClient("api.example.com", 443, "HTTPS",
              "Mozilla/5.0", 10000, false);
Altı parametreli bir sınıf için çok sayıda yapıcı gerekir. Çağrı noktasında parametrelerin anlamı belirsizdir. With six parameters, many constructors are needed. The meaning of parameters at the call site is unclear.
İyi Örnek (After) Good Example (After) 
// Builder kalıbı — açık, ölçeklenebilir ve güvenli
public class HttpClient {
    private final String host;
    private final int port;
    private final String protocol;
    private final String userAgent;
    private final int timeout;
    private final boolean followRedirects;

    public static class Builder {
        private final String host;
        private final int port;
        private String protocol = "HTTP";
        private String userAgent = "Java";
        private int timeout = 5000;
        private boolean followRedirects = true;

        public Builder(String host, int port) {
            this.host = host;
            this.port = port;
        }
        public Builder protocol(String p) { protocol = p; return this; }
        public Builder userAgent(String u) { userAgent = u; return this; }
        public Builder timeout(int t) { timeout = t; return this; }
        public Builder followRedirects(boolean f) {
            followRedirects = f; return this;
        }
        public HttpClient build() {
            return new HttpClient(this);
        }
    }
    private HttpClient(Builder b) {
        host = b.host; port = b.port; protocol = b.protocol;
        userAgent = b.userAgent; timeout = b.timeout;
        followRedirects = b.followRedirects;
    }
}

// Kullanım — akıcı, güvenli ve okunabilir
HttpClient client = new HttpClient.Builder("api.example.com", 443)
    .protocol("HTTPS")
    .userAgent("Mozilla/5.0")
    .timeout(10000)
    .followRedirects(false)
    .build();
Her parametre adla belirtilir ve türü statik olarak kontrol edilir. Metot zincirleme (chaining) ile okunması kolay. Yeni parametreler eklemek mevcut kodu bozmaz. Each parameter is specified by name and type-checked statically. Method chaining makes it easy to read. Adding new parameters doesn't break existing code.
Pratik İpucu: Builder kalıbı ilk başta daha fazla kod gibi görünse de (boilerplate), opsiyonel parametre sayısı arttıkça karşılığını verir. Lombok'un @Builder ek açıklaması veya IDE refactoring araçlarıyla (IntelliJ: "Replace Constructor with Builder") standart kalıp kodu otomatik üretilebilir. Genel kural: 4+ parametre veya aynı tipte 2+ opsiyonel parametre varsa Builder düşünün. Practical Tip: The Builder pattern may seem like more code initially (boilerplate), but it pays off as optional parameters grow. Lombok's @Builder annotation or IDE refactoring tools (IntelliJ: "Replace Constructor with Builder") can auto-generate the boilerplate. Rule: consider Builder for 4+ parameters or 2+ optional parameters of the same type.
