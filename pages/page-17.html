Builder kalıbı (Builder pattern) oldukça esnektir. Tek bir builder, birden fazla nesne oluşturmak için tekrar tekrar kullanılabilir. Üretilen nesneleri çeşitlendirmek için build metodunun farklı çağrıları arasında builder'ın parametrelerinde oynamalar yapılabilir. Bir builder, her nesne oluşturuluşunda artan bir seri numarası gibi bazı alanları örnek (instance) oluşturulurken otomatik olarak doldurabilir.

Builder kalıbının (Builder pattern) dezavantajları da vardır. Bir nesne oluşturmak için önce o nesnenin builder'ını oluşturmanız gerekir. Bu builder'ı oluşturmanın maliyeti pratikte fark edilecek seviyede olmasa da, performans açısından kritik durumlarda sorun yaratabilir. Ayrıca, Builder kalıbı teleskopik yapıcı (telescoping constructor) kalıbından daha uzun kod (verbose) gerektirir, bu yüzden sadece buna değecek kadar parametre olduğunda, örneğin dört veya daha fazla parametre varsa kullanılmalıdır. Ancak gelecekte daha fazla parametre eklemek isteyebileceğinizi aklınızdan çıkarmayın. Eğer işe yapıcı metotlarla (constructors) veya statik fabrika metotlarıyla (static factory methods) başlayıp, sınıf evrildikçe ve parametre sayısı kontrolden çıktığında builder'a geçiş yaparsanız, eski yapıcı metotlar veya statik fabrikalar göze batacaktır. Bu yüzden, çoğu zaman en başından itibaren bir builder ile başlamak daha iyidir.

Özetle, özellikle parametrelerin çoğu opsiyonel (optional) veya aynı türdeyse, yapıcıları veya statik fabrika metotları çok sayıda parametreye sahip olacak olan sınıfları tasarlarken Builder kalıbı iyi bir seçimdir. İstemci kodunu builder'lar ile okumak ve yazmak, teleskopik yapıcılarla okuyup yazmaktan çok daha kolaydır ve builder'lar JavaBeans kalıbından çok daha güvenlidir.

The Builder pattern is quite flexible. A single builder can be used repeatedly to build multiple objects. The parameters of the builder can be tweaked between invocations of the build method to vary the objects that are created. A builder can fill in some fields automatically upon object creation, such as a serial number that increases each time an object is created.

The Builder pattern has disadvantages as well. In order to create an object, you must first create its builder. While the cost of creating this builder is unlikely to be noticeable in practice, it could be a problem in performance-critical situations. Also, the Builder pattern is more verbose than the telescoping constructor pattern, so it should be used only if there are enough parameters to make it worthwhile, say four or more. But keep in mind that you may want to add more parameters in the future. But if you start out with constructors or static factories and switch to a builder when the class evolves to the point where the number of parameters gets out of hand, the obsolete constructors or static factories will stick out like a sore thumb. Therefore, it’s often better to start with a builder in the first place.

In summary, the Builder pattern is a good choice when designing classes whose constructors or static factories would have more than a handful of parameters, especially if many of the parameters are optional or of identical type. Client code is much easier to read and write with builders than with telescoping constructors, and builders are much safer than JavaBeans.

Item 3: Enforce the singleton property with a private constructor or an enum type

Singleton (Tekil), tam olarak yalnızca bir kez örneklenen (instantiated) bir sınıftır [Gamma95]. Singleton'lar genellikle bir fonksiyon (Madde 24) gibi durumsuz (stateless) bir nesneyi ya da doğası gereği tekil olan bir sistem bileşenini temsil eder. Bir sınıfı singleton yapmak, istemcilerini (clients) test etmeyi zorlaştırabilir çünkü o sınıf tipini temsil eden bir arayüzü (interface) uygulamadığı sürece bir singleton yerine sahte (mock) bir uygulama koymak imkansızdır.

Singleton'ları uygulamanın iki yaygın yolu vardır. Her ikisi de yapıcı metodu (constructor) private tutmaya ve tek örneğe (sole instance) erişim sağlamak için public statik bir üye (member) dışa aktarmaya dayanır. İlk yaklaşımda bu üye public final bir alandır (field):

A singleton is simply a class that is instantiated exactly once [Gamma95]. Singletons typically represent either a stateless object such as a function (Item 24) or a system component that is intrinsically unique. Making a class a singleton can make it difficult to test its clients because it’s impossible to substitute a mock implementation for a singleton unless it implements an interface that serves as its type.

Singleton (Tekil) Kalıbı / Singleton Pattern

Singleton kalıbı, bir sınıfın dünya üzerinde (daha doğrusu JVM üzerinde) yalnızca bir örneğinin (instance) olmasını garanti eden tasarım kalıbıdır. Veritabanı bağlantı havuzları, yapılandırma (configuration) yöneticileri veya loglama sistemleri gibi merkezi yönetilmesi gereken bileşenlerde tercih edilir.

The Singleton pattern guarantees that a class has exactly one instance across the entire application (JVM). It is typically used for centralized components like database connection pools, configuration managers, or logging systems.

✗ KÖTÜ — Çoklu örnek kontrol altına alınmamış
public class ConfigManager { // Yapıcı public bırakılmış, herkes new ile instance yaratabilir. public ConfigManager() { loadConfig(); } }
✓ İYİ — Basit bir Singleton Tasarımı (Enum yaklaşımı daha iyidir)
public class VideoPlayerConfig { // Kendi instance'ını yaratıp gizliyor public static final VideoPlayerConfig INSTANCE = new VideoPlayerConfig(); // Yapıcı private, dışarıdan kimse new ile yaratamaz private VideoPlayerConfig() { loadConfig(); } }
💡 Singleton yapmak, global bir değişken oluşturmaya çok benzer. Bu yüzden mümkünse sınıfların bağımlılıkları dışarıdan enjekte edilmeli (Dependency Injection), Singleton yalnızca gerçekten ihtiyaç duyulan donanım arayüzü veya paylaşımlı havuzlar için kullanılmalıdır.
💡 Creating a Singleton is akin to having a global variable. Aim to pass dependencies explicitly (Dependency Injection), reserving Singletons for shared resources like hardware interfaces or pools.

Mocking (Sahte Nesneler) / Mocking

Bir programı test ederken, sınıfı veritabanından, ağ veya diğer harici bileşenlerden izole etmek için "sahte" (mock) nesnelere ihtiyaç duyarız. Ancak bir Singleton nesneyi mock nesne ile değiştirmek çok zordur, çünkü koda sıkıca (tightly coupled) gömülüdür. Arayüz kullanmak (Interface) bu sorunu çözer.

To isolate a class during testing, we often replace external dependencies (database, network) with "mock" objects. Replacing a Singleton with a mock is extremely difficult because it is tightly coupled to the code. Extracting an interface solves this testability issue.

✗ KÖTÜ — Test edilemeyen Singleton kullanımı
public class UserService { public void registerUser(User u) { // Singleton doğrudan çağrılıyor. Test esnasında gerçek DB'ye gider! DatabaseConnection.getInstance().save(u); } }
✓ İYİ — Arayüzü olan Singleton (Mock edilebilir)
public interface DatabaseDataStore { void save(User u); } public class UserService { private final DatabaseDataStore db; // Bağımlılık dışarıdan alınıyor (Dependency Injection) public UserService(DatabaseDataStore db) { this.db = db; } public void registerUser(User u) { db.save(u); } } // Test sırasında artık gerçek bir Singleton yerine sahte bir MockDataStore gönderebiliriz!
💡 Test edilebilirlik (Testability), iyi bir yazılım mimarisinin önceliklerinden olmalıdır. Eğer Singleton nesneler testlerinizi zorlaştırıyorsa, muhtemelen tasarımı esnetmeniz gerekiyordur.
💡 Testability is a hallmark of good architecture. If Singletons are preventing your code from being unit-tested, it's a sign that your design is too rigid.
