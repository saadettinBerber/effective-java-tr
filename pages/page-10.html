Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün Item 2: Consider a Builder When Faced with Many Constructor Parameters

Item 2: Consider a builder when faced with many constructor parameters Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün

İstemci kodu okunması kolay ve yazılması kolaysa, Builder kalıbı Python ve Scala gibi adlandırılmış opsiyonel parametreleri (named optional parameters) olan dillerdeki yapının çok iyi bir simülasyonudur. Builder'ın akıllıca tasarlanması, parametrelerine varsayılan değerleri (default values) sağlayabilir. Builder, değişmezlik (invariant) kontrol yapabilir — tamamlanmış (final) nesneyi sunmadan önce Builder'ın alanlarında hata yoksa kontrol edebilir. Builder'ın çok önemli avantajı, birden fazla thread'in (iş parçacığı) bir Builder nesnesini güvenle paylaşabilmesidir.

This client code is much easier to write and, far more importantly, much easier to read. The Builder pattern simulates the optional parameters found in Python and Scala. Critically, the Builders can have default values for their parameters. The builder is smart enough to fill in parameters. The NutritionFacts class is immutable, and all parameter defaulting is done in the builder. The build method could check invariants (Item 49). It is very simple to make the builder thread-safe if multiple threads are to share a builder.

Bir zamanlar Builder kalıbı Bloch'a NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8).calories(100).fat(35).sodium(35).carbs(27).build(); gibi bir çağrı yazmasını (yazma sürecinde) mümkün kılmıştır. Her Builder metodu, Builder nesnesinin bir başka Builder nesnesine geri dönüşü sağlar. Bunu metot zincirleme (method chaining) veya akıcı arayüz (fluent interface) denir.

A nice feature of the Builder pattern is that it reads nicely. The method invocation on lines 2–5 are easier to understand than the telescoping constructor. This is related to the fact that the Builder pattern allows you to use method chaining—also known as fluent interface. Here's how the client code reads: 

// Builder ile metot zincirleme — okunması çok kolay
NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
    .calories(100)
    .fat(35)
    .sodium(35)
    .carbs(27)
    .build();

Builder kalıbının tek sınırlaması, nesne oluşturmak için Builder nesnesini önce oluşturmanız gerekliliğidir. Çok sayıda parametreli yapıcı metotların daha sık olarak kullanıldığı ortamlarda bu ekstra maliyet önemli olabilir. Ayrıca, Builder kalıbı teleskopik yapıcı kalıbından daha ayrıntılı (verbose) ve karmaşıktır. Bu nedenle, bunu sadece çok sayıda parametreniz (dört veya daha fazla, ideal olarak) olduğunda kullanmalısınız. Fakat dikkat edin — API'nin gerçek büyümesinden muasır gelişim süreci kapsamında başlayabilirsiniz (veya başlamış olabilirsiniz).

The Builder pattern is flexible. A single builder can be used to build multiple objects. The parameters of the builder can be tweaked between object constructions to vary the created objects. The builder can automatically fill in some fields, such as a serial number that increments each time an object is created, or the timestamp.

Pratikte, Builder kalıbı çok sayıda başarılı uygulama görmüştür. Java'daki bazı standart kütüphaneler Builder kalıbını kullanır: StringBuilder (karakter dizileri oluşturmak için), TreeMap (ağaç haritaları için), ve HTTP istek kütüphaneleri. Çoğu popüler Java web çerçevesi (framework) de Builder'ı tercih eder. Lombok gibi araçlar da @Builder ek açıklaması ile Builder kodunu otomatik olarak oluşturabilir.

In short, the Builder pattern is a good choice when designing classes whose constructors or static factories would have more than a handful of parameters. It is much easier to read and write client code with builders than with telescoping constructors, and builders are much safer than JavaBeans.

Özet: Çok sayıda parametreye sahip sınıfları tasarlarken, Builder kalıbı, teleskopik yapıcı kalıbından çok daha iyi ve okunabilir bir seçimdir. Builder kalıbı, özelliklede dört veya daha fazla parametre olduğunda tercih edilmelidir. Builder metotları this nesnesini döndürerek metot zincirleme (method chaining) sağlar, bu da istemci kodunu okunması kolay hale getirir.

Summary: The Builder pattern is a good choice when designing classes whose constructors or static factories would have more than a handful of parameters. It is much easier to read and write client code with builders than with telescoping constructors, and builders are much safer than JavaBeans.

Metot Zincirleme Method Chaining
Method Chaining / Fluent Interface
Metot zincirleme (method chaining), bir nesne üzerinde art arda metotlar çağrılmasını ve her metot çağrısından sonra aynı nesneyi (genellikle this) döndürmesini sağlayan bir tekniktir. Bu, istemci kodunu okunması kolay ve akıcı (fluent) bir biçimde yazılmasını mümkün kılar. Özellikle Builder kalıbında ve akıcı arayüzlerde (fluent interfaces) kullanılır. Method chaining is a technique where methods called on an object return the same object (usually this, allowing consecutive method calls. This makes client code readable and "fluent" in style. It's particularly useful in the Builder pattern and fluent interfaces.
Kötü Örnek (Before) Bad Example (Before) 
// Metot zincirleme olmadan — çok ayrıntılı (verbose)
QueryBuilder qb = new QueryBuilder("SELECT * FROM users");
qb.where("age > ?");
qb.addParameter(18);
qb.orderBy("name");
qb.limit(10);
String sql = qb.build();
Her metot çağrısı ayrı bir satırda. Kod uzun ve okunması yorucu. İnşa sürecinin her adımı benzer bir yapıda tekrarlanır. Each method call is on a separate line. The code is verbose and tedious to read. Each step of the construction repeats similar patterns.
İyi Örnek (After) Good Example (After) 
// Metot zincirleme ile — akıcı ve okunabilir
String sql = new QueryBuilder("SELECT * FROM users")
    .where("age > ?")
    .addParameter(18)
    .orderBy("name")
    .limit(10)
    .build();
Her metot kendisini döndürdüğü için, çağrılar zincirleme yapılabilir. Kod daha kısa, açık ve okuması kolaydır. Niyet (intent) hemen belli olur. Since each method returns itself, calls can be chained. The code is concise, clear, and easy to read. The intent is immediately obvious.
Pratik İpucu: Method chaining'i uygulamak için, Builder veya konfigürasyon sınıflarındaki her "setter" benzeri metot this veya return this; ile sonlandırılmalıdır. StringBuilder ve Stream API'si gibi Java standart kütüphaneleri bu tekniği yoğun olarak kullanır. Practical Tip: To implement method chaining, every "setter"-like method in a Builder or configuration class should end with this or return this;. Java standard libraries like StringBuilder and Stream API use this technique extensively.
Akıcı Arayüz Fluent Interface
Fluent Interface Design Pattern
Akıcı arayüz (fluent interface), metot zincirleme yoluyla kodu insan diline yakın, okuması doğal bir şekilde yazılmasını sağlayan bir tasarım kalıbıdır. API'ler akıcı arayüz kullanarak, karmaşık işlemleri basit ve okunabilir bir biçimde ifade edilebilir hale getirebilir. Amacı, kod okunabilirliğini artırmak ve API'nin sezgisel olması sağlamaktır. A fluent interface is a design pattern that uses method chaining to make code read naturally, close to human language. APIs using fluent interfaces can express complex operations in a simple and readable way. The goal is to improve code readability and make the API intuitive.
Kötü Örnek (Before) Bad Example (Before) 
// Akıcı olmayan arayüz — çok adımlı ve komplike
HttpRequest req = new HttpRequest("https://api.example.com");
req.setMethod("POST");
req.setHeader("Content-Type", "application/json");
req.setBody("{\"user\": \"alice\"}");
req.setRetries(3);
req.setTimeoutMs(5000);
HttpResponse res = req.execute();
Setter metotları void döndürüyor, bu yüzden zincirleme yapılamıyor. Ayrıca setTimeoutMs gibi adlandırmalar da natural değildir. Setter methods return void, so chaining isn't possible. Also, naming like setTimeoutMs is less natural. It doesn't read like a sentence.
İyi Örnek (After) Good Example (After) 
// Akıcı arayüz — doğal ve okunabilir
HttpResponse res = new HttpRequest("https://api.example.com")
    .post()
    .withHeader("Content-Type", "application/json")
    .withBody("{\"user\": \"alice\"}")
    .retries(3)
    .timeout(5000, TimeUnit.MILLISECONDS)
    .execute();
Her metot this döndürüyor. .post(), .withHeader() gibi isimlendirmeler daha doğal görünüyor. Bütün yapısı bir cümle gibi okuluyor ve niyeti hemen belli oluyor. Each method returns this for chaining. Method names like .post(), .withHeader() read more naturally. The whole structure reads like a sentence and intent is immediately clear.
Pratik İpucu: Fluent interface tasarlarken, metot adları emir kipi veya "with" ön eki kullanan isimlendirme ("post", "withHeader") tercih edilmelidir. Her metot Builder nesnesini döndürmelidir. Java'daki Stream API (stream().filter().map().collect()) fluent interface'in mükemmel bir örneğidir. Practical Tip: When designing fluent interfaces, method names should use imperative or "with" prefixes ("post", "withHeader"). Each method should return the Builder object. Java's Stream API (stream().filter().map().collect()) is a perfect example of fluent interface.
Değişmezlik Kontrolü Invariant Checking
Invariant Checking & Validation
Değişmezlik kontrolü (invariant checking), nesne oluşturulduktan sonra ve hatta kullanılmadan önce, nesnenin durumunun tutarlı ve geçerli olup olmadığını kontrol etme işlemidir. Değişmez (invariant), nesneler sırasında her zaman doğru olması gereken bir koşuldur. Builder kalıbında, build() metodu çağrılmadan önce tüm parametrelerin doğruluğu kontrol edilebilir. Bu sayede hatalı nesneler oluşması engellenir. Invariant checking is the process of validating that an object's state is consistent and valid after (or before) it's created. An invariant is a condition that must always be true about an object. In the Builder pattern, before build() is called, all parameters can be validated. This prevents invalid objects from being created.
Kötü Örnek (Before) Bad Example (Before) 
// Doğrulama olmadan — hatalı nesneler oluşabilir
public class DateRange {
    private final LocalDate start;
    private final LocalDate end;

    public DateRange(LocalDate start, LocalDate end) {
        this.start = start;    // Doğrulama yok!
        this.end = end;      // end < start olabilir!
    }
}

// Hata: start > end — geçersiz bir DateRange
DateRange broken = new DateRange(
    LocalDate.of(2025, 1, 31),  // start
    LocalDate.of(2025, 1, 1)   // end (yanlış!)
);
Parametreler doğrulanmıyor. end tarihi start tarihinden daha eski olabilir. Nesne oluşturulduktan sonra bu hata fark edilirse, hata ayıklamak çok zor olabilir. Parameters aren't validated. The end date could be before start. If this error is discovered after object creation, debugging becomes difficult.
İyi Örnek (After) Good Example (After) 
// Builder ile doğrulama — hataları erken yakalar
public class DateRange {
    private final LocalDate start;
    private final LocalDate end;

    public static class Builder {
        private LocalDate start;
        private LocalDate end;

        public Builder start(LocalDate s) { start = s; return this; }
        public Builder end(LocalDate e) { end = e; return this; }

        public DateRange build() {
            // Doğrulama — start <= end olmalı
            if (start != null && end != null && start.isAfter(end)) {
                throw new IllegalArgumentException(
                    "start (" + start + ") end'den (" + end + ") sonra olamaz"
                );
            }
            return new DateRange(this);
        }
    }
    private DateRange(Builder b) {
        this.start = b.start;
        this.end = b.end;
    }
}

// Doğrulama başarısız — hata hemen çıkar
DateRange range = new DateRange.Builder()
    .start(LocalDate.of(2025, 1, 31))
    .end(LocalDate.of(2025, 1, 1))
    .build();  // IllegalArgumentException fırlatılır!
build() metodu parametreleri kontrol eder. Eğer start > end ise, hemen IllegalArgumentException fırlatılır. Hata oluşturma noktasında hemen belli olur, hata ayıklama kolaydır. The build() method validates parameters. If start > end, it immediately throws IllegalArgumentException. The error is obvious at the point of construction, making debugging easy.
Pratik İpucu: Builder'ın build() metotunda her zaman önemli değişmezlik kontrollerini yapın. Null kontrolleri, aralık doğrulamaları, tutarsızlık kontrolleri burada yapılmalıdır. Bu sayede hatalı nesneler sistem içinde yayılmaz. Hata mesajları açık ve anlaşılır olmalıdır.

Practical Tip: Always perform critical invariant checks in the Builder's build() method. Null checks, range validations, and consistency checks should be done here. This prevents invalid objects from spreading through the system. Error messages should be clear and descriptive.
