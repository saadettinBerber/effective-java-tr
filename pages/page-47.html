Chapter 3 — Item 11: hashCode — HashMap Sorunu
↩ Önceki sayfadan devam — Madde 11: hashCode sözleşmesinin ihlali ve HashMap'teki etkisi

hashCode'u ezmediğinizde ihlal edilen anahtar kural ikincisidir: eşit nesnelerin eşit hash kodlarına sahip olması gerekir. İki ayrı örnek, bir sınıfın equals metoduna göre mantıksal olarak eşit olabilir; ancak Object'in hashCode metodu açısından, bunlar ortak bir yanı olmayan iki nesnedir. Bu nedenle, Object'in hashCode metodu, sözleşmenin gerektirdiği iki eşit sayı yerine görünüşte rastgele iki sayı döndürür.

Örneğin, Madde 10'daki PhoneNumber sınıfının örneklerini bir HashMap'te anahtar olarak kullanmaya çalıştığınızı varsayalım:

The key provision violated when you fail to override hashCode is the second one: equal objects must have equal hash codes. Two distinct instances may be logically equal, but Object's hashCode returns two random numbers instead of two equal ones as required.

For example, suppose you use PhoneNumber instances as keys in a HashMap:

Map<PhoneNumber, String> m = new HashMap<>(); m.put(new PhoneNumber(707, 867, 5309), "Jenny"); // Beklenti: "Jenny" döndürür // Gerçek: null döndürür! m.get(new PhoneNumber(707, 867, 5309));

m.get(new PhoneNumber(707, 867, 5309))'un "Jenny" döndürmesini beklersiniz; ancak bunun yerine null döndürür. İki PhoneNumber örneği söz konusudur: biri HashMap'e ekleme için, diğeri (eşit olan) geri alma denemesi için kullanılır. PhoneNumber sınıfının hashCode'u ezmemiş olması, iki eşit örneğin eşit olmayan hash kodlarına sahip olmasına neden olur. Bu nedenle, get metodu telefon numarasını, put metodunun onu sakladığı kovadan (bucket) farklı bir kovada arar. İki örnek aynı kovaya denk gelse bile, get metodu neredeyse kesinlikle null döndürecektir; çünkü HashMap, her giriş ile ilişkilendirilen hash kodunu önbelleğe alan bir optimizasyona sahiptir ve hash kodları eşleşmiyorsa nesne eşitliğini kontrol etme zahmetine girmez.

Bu sorunu düzeltmek, PhoneNumber için düzgün bir hashCode metodu yazmak kadar basittir. Peki bir hashCode metodu nasıl görünmeli? İşte en kötü ama "yasal" uygulama — asla kullanmayın:

You'd expect "Jenny", but get null. Two PhoneNumber instances are involved: one for insertion, one (equal) for retrieval. Without hashCode override, they get different hash codes, so get looks in the wrong bucket. Even if they hash to the same bucket, HashMap caches hash codes and won't check equality if codes don't match.

Fixing this is simple — write a proper hashCode. Here's the worst legal one — never use:

// Mümkün olan en kötü yasal hashCode — asla kullanmayın! @Override public int hashCode() { return 42; }

Bu "yasal"dır çünkü eşit nesnelerin aynı hash koduna sahip olmasını garanti eder. Korkunçtur çünkü her nesnenin aynı hash koduna sahip olmasını garanti eder. Bu nedenle, her nesne aynı kovaya (bucket) düşer ve hash tabloları bağlantılı listelere (linked lists) dönüşür. Doğrusal (linear) zamanda çalışması gereken programlar, bunun yerine ikinci dereceden (quadratic) zamanda çalışır.

İyi bir hash fonksiyonu, eşit olmayan örnekler için eşit olmayan hash kodları üretme eğilimindedir. İşte basit bir tarif:

1. result adında bir int değişkeni tanımlayın ve bunu nesnenizde ilk anlamlı alan için hesaplanan hash kodu c ile başlatın.

2. Kalan her anlamlı alan f için bir int hash kodu c hesaplayın: İlkel tür ise Type.hashCode(f), nesne referansı ise f.hashCode() özyinelemeli olarak, dizi ise Arrays.hashCode(), null ise 0 kullanın. Sonra birleştirin: result = 31 * result + c;

3. result'ı döndürün.

It's legal but atrocious — every object hashes to the same bucket, degenerating hash tables to linked lists. Programs that should run in linear time run in quadratic time.

A good hash function produces unequal codes for unequal instances. Recipe:

1. Initialize result to hash code of first significant field.

2. For each remaining field: compute hash code c and combine: result = 31 * result + c;

3. Return result.

HashMap Başarısızlık Senaryosu

HashMap her anahtar nesne için hash kodunu hesaplar ve bunu bir "kova" (bucket) dizinine dönüştürür. put ve get çağrıları arasında eşit olan iki nesnenin hash kodları farklıysa, farklı kovalara düşerler.

Ek olarak, HashMap bir optimizasyon olarak her girişteki hash kodunu önbelleğe alır ve hash kodları eşleşmezse equals'ı bile çağırmaz — doğrudan null döndürür.

HashMap computes a hash code for each key and maps it to a bucket index. If two equal objects have different codes, they land in different buckets. Additionally, HashMap caches hash codes and skips equals entirely if codes don't match.

hashCode Tarifi (31 Çarpanı)

Hash hesaplamasında çarpan olarak 31 kullanılır çünkü:

• Tek sayı (odd): Çift sayı olsaydı ve çarpma taşsaydı bilgi kaybedilirdi (çünkü 2 ile çarpma kaydırma demektir).

• Asal sayı (prime): Geleneksel olarak tercih edilir, daha iyi dağılım sağlar.

• Optimizasyon: 31 * i == (i << 5) - i — modern JVM'ler bu dönüşümü otomatik yapar.

• Sıra bağımlılığı: Çarpma, sonucun alan sırasına bağlı olmasını sağlar — anagramlar farklı hash kodları alır.

31 is used because it's an odd prime. 31 * i == (i << 5) - i. The multiplication makes the result order-dependent, so anagrams get different codes.
