Chapter 3 — Item 10: equals — Liskov & Composition
↩ Önceki sayfadan devam — Madde 10: getClass yaklaşımının sorunu ve Liskov İkame Prensibi

getClass yaklaşımı, nesneleri yalnızca aynı uygulama sınıfına (implementation class) sahip olduklarında eşit sayma etkisine sahiptir. Bu o kadar da kötü görünmeyebilir, ancak sonuçları kabul edilemezdir: Point'in bir alt sınıfının bir örneği hâlâ bir Point'tir ve bir Point olarak işlev görmesi gerekir; ama bu yaklaşımı kullanırsanız bunu yapamaz!

Bir noktanın birim çember (unit circle) üzerinde olup olmadığını söyleyen bir metot yazmak istediğimizi varsayalım:

The getClass approach has the effect of equating objects only if they have the same implementation class. This may not seem so bad, but the consequences are unacceptable: An instance of a subclass of Point is still a Point, and it still needs to function as one, but it fails to do so if you take this approach!

Let's suppose we want to write a method to tell whether a point is on the unit circle:

// unitCircle — birim çember üzerindeki tüm noktalar private static final Set<Point> unitCircle = Set.of( new Point( 1, 0), new Point( 0, 1), new Point(-1, 0), new Point( 0, -1)); public static boolean onUnitCircle(Point p) { return unitCircle.contains(p); }

Bir değer bileşeni eklemeyen, yapıcısında (constructor) kaç örnek oluşturulduğunu izleyen basit bir Point alt sınıfı düşünün:

Suppose you extend Point in some trivial way that doesn't add a value component, by having its constructor keep track of how many instances have been created:

public class CounterPoint extends Point { private static final AtomicInteger counter = new AtomicInteger(); public CounterPoint(int x, int y) { super(x, y); counter.incrementAndGet(); } public static int numberCreated() { return counter.get(); } }

Liskov İkame Prensibi (Liskov substitution principle), bir türün herhangi bir önemli özelliğinin tüm alt türlerinde de geçerli olması gerektiğini söyler; böylece tür için yazılmış herhangi bir metot, alt türlerinde de eşit derecede iyi çalışmalıdır [Liskov87]. Ancak Point sınıfı getClass tabanlı bir equals metodu kullanırsa, onUnitCircle metodu CounterPoint örneğinin x ve y koordinatlarına bakılmaksızın false döndürecektir. Çünkü HashSet dahil olmak üzere çoğu koleksiyon, kapsama testi (containment test) için equals metodunu kullanır ve hiçbir CounterPoint örneği herhangi bir Point'e eşit olmaz. Ancak Point üzerinde düzgün bir instanceof tabanlı equals metodu kullanırsanız, aynı onUnitCircle metodu CounterPoint örneğiyle sunulduğunda sorunsuz çalışır.

Örneklendirilebilen bir sınıfı genişletip değer bileşeni eklemenin tatmin edici bir yolu olmasa da, güzel bir geçici çözüm (workaround) vardır: Madde 18'in tavsiyesine uyun — "Kalıtım yerine bileşimi tercih edin" (Favor composition over inheritance). ColorPoint'in Point'i genişletmesi yerine, ColorPoint'e özel (private) bir Point alanı ve bu renkli noktayla aynı konumdaki noktayı döndüren genel (public) bir görünüm metodu (view method) verin:

The Liskov substitution principle says that any important property of a type should also hold for all its subtypes. But if Point uses a getClass-based equals, the onUnitCircle method will return false regardless of the CounterPoint's coordinates. Because most collections use equals for containment, no CounterPoint will ever equal any Point. If you use a proper instanceof-based equals on Point, the same onUnitCircle works fine with a CounterPoint.

While there is no satisfactory way to extend an instantiable class and add a value component, there is a fine workaround: Follow Item 18's advice — "Favor composition over inheritance." Instead of having ColorPoint extend Point, give ColorPoint a private Point field and a public view method:

// equals sözleşmesini ihlal etmeden değer bileşeni ekler // Adds a value component without violating the equals contract public class ColorPoint { private final Point point; private final Color color; public ColorPoint(int x, int y, Color color) { point = new Point(x, y); this.color = Objects.requireNonNull(color); } // Bu ColorPoint'in Point görünümünü döndürür public Point asPoint() { return point; } @Override public boolean equals(Object o) { if (!(o instanceof ColorPoint)) return false; ColorPoint cp = (ColorPoint) o; return cp.point.equals(point) && cp.color.equals(color); } ... // Kalan kısım çıkarıldı }

🔍 Kavramlar: 🔍 Concepts:

Liskov İkame Prensibi (LSP)

Barbara Liskov tarafından formüle edilen bu prensip: "Bir üst türün (supertype) herhangi bir önemli özelliği, tüm alt türlerinde (subtypes) de geçerli olmalıdır." [Liskov87]

Pratik sonuç: Bir Point alt sınıfı (CounterPoint) hâlâ bir Point'tir ve bir Point'in çalıştığı her yerde çalışmalıdır. getClass tabanlı equals bu prensibi ihlal eder çünkü alt sınıf örneklerini "eşit olmayan" ilan eder.

Formulated by Barbara Liskov: "Any important property of a supertype should also hold for all its subtypes." [Liskov87]

Practical: A Point subclass (CounterPoint) is still a Point and must work everywhere a Point does. getClass-based equals violates this by declaring subclass instances "not equal".

💡 instanceof kullanın, getClass değil. instanceof, alt sınıfların üst sınıf olarak düzgünce çalışmasını (polimorfizm) garanti eder.

Bileşim Çözümü (Composition over Inheritance)

Kalıtım yerine bileşim kullanarak equals sözleşmesini korumak mümkündür:

• ColorPoint extends Point yerine → ColorPoint içinde özel bir Point alanı tutun.

• asPoint() görünüm metodu ile Point bağlamında kullanım imkanı sağlayın.

• equals yalnızca ColorPoint örneklerini karşılaştırır — simetri, geçişlilik, tutarlılık korunur.

Using composition instead of inheritance preserves the equals contract:

• Instead of ColorPoint extends Point → keep a private Point field inside ColorPoint.

• Provide an asPoint() view method for use in Point contexts.

• equals only compares ColorPoint instances — symmetry, transitivity, consistency preserved.
