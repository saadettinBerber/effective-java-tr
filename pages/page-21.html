Bu gereksinimi karşılayan basit bir tasarım kalıbı (pattern), yeni bir örnek (instance) oluşturulurken kaynağı (resource) doğrudan sınıfın yapıcı metoduna (constructor) aktarmaktır (pass in). ...client (in our example, the dictionary). A simple pattern that satisfies this requirement is to pass the resource into the constructor when creating a new instance. This is one form of dependency injection: the dictionary is a dependency of the spell checker and is injected into the spell checker when it is created.

// Bağımlılık enjeksiyonu esneklik ve test edilebilirlik sağlar // Dependency injection provides flexibility and testability public class SpellChecker { private final Lexicon dictionary; public SpellChecker(Lexicon dictionary) { this.dictionary = Objects.requireNonNull(dictionary); } public boolean isValid(String word) { ... } public List<String> suggestions(String typo) { ... } }

Bağımlılık enjeksiyonu tasarım kalıbı o kadar basittir ki, birçok programcı adının bu olduğunu dahi bilmeden onu yıllarca kullanır. Bizim yazım denetleyici (spell checker) örneğimiz yalnızca tek bir kaynağa (sözlüğe) sahip olsa da, bağımlılık enjeksiyonu keyfi sayıda kaynakla ve dilediğiniz bağımlılık ağaçlarıyla (dependency graphs) birlikte de çalışır. Verilerin değişmezliğini (immutability) (Madde 17) korur, böylece birden çok istemci (client) (istemcilerin temel alınan aynı kaynağı arzu ettiği varsayılarak) bağımlı nesneleri ortaklaşa paylaşabilir. Bağımlılık enjeksiyonu sadece yapıcı metotlara (constructors) değil, statik fabrikalara (static factories) (Madde 1) ve builder'lara (Madde 2) da eşit ölçüde uygulanabilir.

Bu kalıbın yararlı bir varyantı da yapıcı metoda bir kaynak fabrikası (resource factory) aktarmaktır. Bir fabrika, belirli türde yeni örnekler oluşturabilmek için defalarca çağrılabilen bir nesnedir. Bu tür fabrikalar aslen Factory Method (Fabrika Metodu) tasarım kalıbını (Design Pattern) [Gamma95] cisme büründürürler. Java 8 ile birlikte dile eklenen Supplier<T> arayüzü fabrika metodları temsil etmek amacıyla kusursuz bir biçimde tasarlanmıştır. Parametre girdisi olarak dışarıdan Supplier<T> bekleyen metotlar genellikle fabrikanın oluşturacağı tip parametresini "sınırlı bir joker tipiyle (bounded wildcard type)" (Madde 31) daraltmalıdır (constrain). Böylece istemciye, belirlenen asıl tipte (veya onun bir alt tipinde) örnekler oluşturan herhangi bir fabrikayı aktarma ihtimali tanınmış olur. Misal, aşağıda her bir döşeme taşını (tile) oluşturmak için istemci tarafından sağlanan bir fabrika kullanarak bir mozaik üreten bir metoda örnek yer almaktadır:

The dependency injection pattern is so simple that many programmers use it for years without knowing it has a name. While our spell checker example had only a single resource (the dictionary), dependency injection works with an arbitrary number of resources and arbitrary dependency graphs. It preserves immutability (Item 17), so multiple clients can share dependent objects (assuming the clients desire the same underlying resources). Dependency injection is equally applicable to constructors, static factories (Item 1), and builders (Item 2).

A useful variant of the pattern is to pass a resource factory to the constructor. A factory is an object that can be called repeatedly to create instances of a type. Such factories embody the Factory Method pattern [Gamma95]. The Supplier<T> interface, introduced in Java 8, is perfect for representing factories. Methods that take a Supplier<T> on input should typically constrain the factory’s type parameter using a bounded wildcard type (Item 31) to allow the client to pass in a factory that creates any subtype of a specified type. For example, here is a method that makes a mosaic using a client-provided factory to produce each tile:

Mosaic create(Supplier<? extends Tile> tileFactory) { ... }

Bağımlılık enjeksiyonu, test edilebilirliği ve esnekliği büyük ölçüde artırsa da, genelde binlerce bağımlılık barındıran devasa projelerde kodu darmadağın edebilme (clutter up) potansiyeline sahiptir. Neyse ki, bu dağınıklık bir bağımlılık enjeksiyonu altyapısı (DI framework) kullanılarak... (Devamı sonraki sayfada)

Factory Method (Fabrika Metodu) & Supplier

Bazen bir nesnenin constructor'ına bir bağımlılık listesi veya nesne değil de yeni bağımlılıkları oluşturmayı bilen bir üretici mekanizma / fabrika göndermek isteriz. Java 8 ile Supplier<T> arayüzü bu işlemi çok kolaylaştırmıştır, her istendiğinde yeni bir referans elde etmeyi olanaklı kılar.

Sometimes you don't just want to inject a static dependency, but rather a producer mechanism / factory that knows how to create new dependencies on the fly. Java 8's Supplier<T> interface makes this incredibly simple, acting as a lightweight Factory Method pattern.

✗ KÖTÜ — Koda gömülü fabrika bağımlılığı
public class GameEngine { public Enemy spawnEnemy() { // Daima aynı tip, esnemeye kapalı return new OrcEnemy(); } }
✓ İYİ — Supplier kullanarak dinamik Üretici Yöntemi (Factory Method)
public class GameEngine { private final Supplier<Enemy> enemyFactory; public GameEngine(Supplier<Enemy> enemyFactory) { this.enemyFactory = enemyFactory; } public Enemy spawnEnemy() { // Hangi üretici verilmişse ondan çağırılır return enemyFactory.get(); } } // İstemci her senaryoda farklı bir fabrika fırlatabilir: GameEngine devEngine = new GameEngine(OrcEnemy::new); GameEngine elfEngine = new GameEngine(ElfEnemy::new);

Bounded Wildcard (Sınırlı Joker)

Jenerik parametrelerde ? extends T kullanmak, bir tipin tamı tamına aynısı olmasını beklemediğimizi, aksine o türü (T) genişleten/miras alan (veya tam o tip olan) nesnelere tolerans göstereceğimizi belirtir (Üst sınır — Upper Bound).

Using ? extends T in generic parameters tells the compiler we are flexible: we can accept not just exactly T, but any type that extends or implements T (Upper Bound wildcard).

✗ KÖTÜ — Esnemez Tip Parametresi
// Yalnızca mutlak şekilde Tile dönen fabrika kabul edilir. Mosaic create(Supplier<Tile> tileFactory) { ... } // RedTile açıkça bir Tile arabirimi olsa da kabul edilmez Supplier<RedTile> redFactory = RedTile::new; create(redFactory); // Derleme Hata (Compile Error)!
✓ İYİ — Bounded Wildcard ile Tam Esneklik
// Herhangi bir Tile'ı veya alt türünü barındıran her türlü factory uygun Mosaic create(Supplier<? extends Tile> tileFactory) { ... } Supplier<RedTile> redFactory = RedTile::new; create(redFactory); // Başarılı (Valid code)
💡 Ürettiğiniz API'lerde listeler veya supplier'lar dışarıdan çekilecekse, tüketen parametreler için hemen hemen daima wildcard kullanmayı pratik haline getirin. API'nizin kullanımı ciddi oranda esnek kalır.
💡 When designing APIs that consume generics (Lists, Suppliers, etc.), getting into the habit of using wildcards makes your API dramatically more flexible for its clients.
