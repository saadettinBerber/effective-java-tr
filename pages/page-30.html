Sonlandırıcıların ciddi bir güvenlik sorunu vardır: sınıfınızı sonlandırıcı saldırılarına (finalizer attacks) karşı açık hale getirirler. Bir sonlandırıcı saldırısının ardındaki fikir basittir: Eğer bir yapıcı metottan (constructor) veya onun serileştirme karşılıklarından (readObject ve readResolve metotları — Bölüm 12) bir istisna fırlatılırsa, kötü niyetli bir alt sınıfın (malicious subclass) sonlandırıcısı, aslında "dal üzerinde ölmesi" (died on the vine) gereken yarım kalmış (partially constructed) nesne üzerinde çalışabilir. Bu sonlandırıcı, nesneye bir statik alana (static field) referans kaydedebilir ve böylece Çöp Toplayıcı tarafından toplanmasını engelleyebilir. Biçimsiz (malformed) nesne bir kez kaydedildiğinde, başlangıçta var olmasına asla izin verilmemesi gereken bu nesne üzerinde keyfi metotları çağırmak son derece basit bir iş haline gelir. Bir yapıcı metottan istisna fırlatmak, bir nesnenin var olmasını önlemek için yeterli olmalıdır; ancak sonlandırıcıların varlığında bu yeterli değildir. Bu tür saldırılar korkunç sonuçlara yol açabilir. final sınıfları sonlandırıcı saldırılarına karşı bağışıktır; çünkü hiç kimse final bir sınıfın kötü niyetli bir alt sınıfını yazamaz. final olmayan sınıfları sonlandırıcı saldırılarından korumak için, hiçbir şey yapmayan bir final finalize metodu yazın.

Peki, dosyalar veya iş parçacıkları gibi sonlandırma gerektiren kaynakları kapsayan nesnelerin sınıfı için bir sonlandırıcı veya temizleyici yazmak yerine ne yapmalısınız? Sınıfınızın AutoCloseable arayüzünü uygulamasını sağlayın ve istemcilerinin (clients) her örnek artık gerekli olmadığında close metodunu çağırmasını zorunlu kılın; tipik olarak istisna durumlarında bile sonlandırmayı garanti etmek için try-with-resources kullanarak (Madde 9). Bahsetmeye değer bir detay şudur: Örnek, kapanıp kapanmadığını takip etmelidir (keep track); close metodu bir alanda (field) nesnenin artık geçerli olmadığını kaydetmeli ve diğer metotlar bu alanı kontrol ederek nesne kapandıktan sonra çağrılırlarsa bir IllegalStateException fırlatmalıdır.

Peki, temizleyicilerin ve sonlandırıcıların, eğer varsa, ne işe yaradığı? Belki iki meşru (legitimate) kullanım alanları vardır. Birincisi, bir kaynağın sahibinin (owner) close metodunu çağırmayı ihmal etmesi durumunda bir güvenlik ağı (safety net) olarak hizmet etmektir. Temizleyicinin veya sonlandırıcının zamanında çalışacağına (hatta çalışacağına bile) dair hiçbir garanti olmasa da, istemci bunu yapmazsa kaynağı geç serbest bırakmak hiçbir zaman serbest bırakmamaktan iyidir. Böyle bir güvenlik ağı sonlandırıcısı yazmayı düşünüyorsanız, korumanın maliyete değip değmeyeceğini uzun uzun düşünün. FileInputStream, FileOutputStream, ThreadPoolExecutor ve java.sql.Connection gibi bazı Java kütüphane sınıfları, güvenlik ağı işlevi gören sonlandırıcılara sahiptir.

Under these circumstances, creating, cleaning, and destroying an object takes about 66 ns on my machine, which means you pay a factor of five (not fifty) for the insurance of a safety net if you don't use it.

Finalizers have a serious security problem: they open your class up to finalizer attacks. The idea behind a finalizer attack is simple: If an exception is thrown from a constructor or its serialization equivalents—the readObject and readResolve methods (Chapter 12)—the finalizer of a malicious subclass can run on the partially constructed object that should have "died on the vine." This finalizer can record a reference to the object in a static field, preventing it from being garbage collected. Once the malformed object has been recorded, it is a simple matter to invoke arbitrary methods on this object that should never have been allowed to exist in the first place. Throwing an exception from a constructor should be sufficient to prevent an object from coming into existence; in the presence of finalizers, it is not. Such attacks can have dire consequences. Final classes are immune to finalizer attacks because no one can write a malicious subclass of a final class. To protect nonfinal classes from finalizer attacks, write a final finalize method that does nothing.

So what should you do instead of writing a finalizer or cleaner for a class whose objects encapsulate resources that require termination, such as files or threads? Just have your class implement AutoCloseable, and require its clients to invoke the close method on each instance when it is no longer needed, typically using try-with-resources to ensure termination even in the face of exceptions (Item 9). One detail worth mentioning is that the instance must keep track of whether it has been closed: the close method must record in a field that the object is no longer valid, and other methods must check this field and throw an IllegalStateException if they are called after the object has been closed.

So what, if anything, are cleaners and finalizers good for? They have perhaps two legitimate uses. One is to act as a safety net in case the owner of a resource neglects to call its close method. While there's no guarantee that the cleaner or finalizer will run promptly (or at all), it is better to free the resource late than never if the client fails to do so. If you're considering writing such a safety-net finalizer, think long and hard about whether the protection is worth the cost. Some Java library classes, such as FileInputStream, FileOutputStream, ThreadPoolExecutor, and java.sql.Connection, have finalizers that serve as safety nets.

Finalizer Attack (Sonlandırıcı Saldırısı)

Saldırgan, hedef sınıfı genişleten (extends) kötü niyetli bir alt sınıf yazar ve finalize() içinde yarısı yapılmış nesneyi bir statik alana kaydeder. Yapıcı metot istisna fırlatsa bile nesne bellekte canlı kalır ve saldırgan istediği metodu çağırabilir.

An attacker creates a malicious subclass, overrides finalize() to save the half-constructed object in a static field. Even though the constructor threw, the object stays alive and the attacker can call any method on it.

❌ KÖTÜ ÖRNEK — Saldırıya açık sınıf

public class SecureService { public SecureService(String token) { if (!isValid(token)) throw new SecurityException("Geçersiz token!"); } public void deleteAllData() { /* tehlikeli işlem */ } } // Saldırgan alt sınıfı: public class EvilSubclass extends SecureService { static SecureService stolen; public EvilSubclass() { super("INVALID"); } @Override protected void finalize() { stolen = this; } } // stolen.deleteAllData() → KABUTİ VEYA!!! 💀

✅ İYİ ÖRNEK — Korunmuş sınıf

public class SecureService { // Boş final finalize → alt sınıf override edemez @Override protected final void finalize() { } // ... veya sınıfı 'final' yapın }
💡 En basit savunma: sınıfınızı final yapın. Eğer alt sınıflama gerekiyorsa, protected final void finalize() {} yazın.

AutoCloseable Arayüzü

java.lang.AutoCloseable, try-with-resources bloğu ile otomatik kaynak yönetimi için Java 7'de eklenen temel arayüzdür. Tek bir close() metodu tanımlar. Dosyalar, veritabanı bağlantıları, soketler gibi herhangi bir dış kaynağı kapsayan sınıflar bu arayüzü uygulamalıdır.

java.lang.AutoCloseable is the fundamental interface added in Java 7 for automatic resource management via try-with-resources. It defines a single close() method. Any class wrapping an external resource (files, connections, sockets) should implement this.

✅ İYİ ÖRNEK

public class ResourceWrapper implements AutoCloseable { private boolean closed = false; private final Resource res; public void doWork() { if (closed) throw new IllegalStateException("Zaten kapatıldı!"); // ... iş mantığı } @Override public void close() { if (!closed) { res.release(); closed = true; } } }
💡 close() metodu idempotent olmalıdır: birden fazla kez çağrılsa bile güvenli bir şekilde çalışmalıdır. Bu nedenle closed bayrağı kullanmak iyi bir pratiktir.

Safety Net (Güvenlik Ağı) Kalıbı

Güvenlik ağı, istemcinin close() çağırmayı unutması durumunda kaynağın yine de – geç bile olsa – serbest bırakılmasını sağlayan son çare mekanizmasıdır. Asıl kaynak yönetimi try-with-resources ile yapılır; temizleyici veya sonlandırıcı yalnızca "tembel istemci sigortası" olarak kullanılır.

JDK'daki FileInputStream, FileOutputStream ve java.sql.Connection bu kalıbı kullanır.

A safety net ensures that if a client forgets to call close(), the resource will still be freed — albeit late. Primary resource management is done via try-with-resources; cleaners/finalizers serve only as "lazy client insurance."

JDK's FileInputStream, FileOutputStream, and java.sql.Connection use this pattern.

💡 Güvenlik ağı modunda temizleyici kullanımı, tam temizleyici kullanımına göre çok daha hızlıdır: 66 ns vs 500 ns. Bunun nedeni, güvenlik ağı yalnızca istemci close() çağırmayı başaramadığında devreye girmesidir.
