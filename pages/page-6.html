Madde 1: Yapıcı Metot Yerine Statik Fabrika Metotlarını Düşünün (devam) Item 1: Consider Static Factory Methods Instead of Constructors (cont.)

Item 1: Consider static factory methods instead of constructors Madde 1: Yapıcı Metot Yerine Statik Fabrika Metotlarını Düşünün

Koleksiyonlar Çerçevesi (Collections Framework) API'si, kırk beş ayrı kamusal sınıf dışa aktarmış olsaydı çok daha büyük olurdu — her kolaylık uygulaması için bir tane. Azaltılan sadece API'nin hacmi değil, aynı zamanda kavramsal ağırlığıdır (conceptual weight): programcıların API'yi kullanabilmek için öğrenmeleri gereken kavramların sayısı ve zorluğu. Programcı, döndürülen nesnenin arayüzü tarafından belirlenen API'ye tam olarak sahip olduğunu bilir, bu yüzden uygulama sınıfı için ek belge okumaya gerek yoktur. Ayrıca, böyle bir statik fabrika metodu kullanmak istemcinin döndürülen nesneye uygulama sınıfı yerine arayüz üzerinden başvurmasını gerektirir ki bu genellikle iyi bir pratiktir (Madde 64).

The Collections Framework API is much smaller than it would have been had it exported forty-five separate public classes, one for each convenience implementation. It is not just the bulk of the API that is reduced but the conceptual weight: the number and difficulty of the concepts that programmers must master in order to use the API. The programmer knows that the returned object has precisely the API specified by its interface, so there is no need to read additional class documentation for the implementation class. Furthermore, using such a static factory method requires the client to refer to the returned object by interface rather than implementation class, which is generally good practice (Item 64).

Java 8 itibarıyla, arayüzlerin statik metotlar içeremeyeceği kısıtlaması kaldırıldı, dolayısıyla bir arayüz için örneklenemez bir eşlikçi sınıf (companion class) sağlamak için genellikle çok az neden kaldı. Böyle bir sınıfta yer alacak birçok kamusal statik üye, bunun yerine arayüzün kendisine konulmalıdır. Ancak yine de uygulama kodunun büyük kısmını ayrı bir paket-özel (package-private) sınıfa koymak gerekebileceğini unutmayın. Bunun nedeni, Java 8'in bir arayüzün tüm statik üyelerinin kamusal olmasını gerektirmesidir. Java 9 özel statik metotlara izin verir, ancak statik alanlar ve statik üye sınıfları hâlâ kamusal olmak zorundadır.

As of Java 8, the restriction that interfaces cannot contain static methods was eliminated, so there is typically little reason to provide a noninstantiable companion class for an interface. Many public static members that would have been at home in such a class should instead be put in the interface itself. Note, however, that it may still be necessary to put the bulk of the implementation code behind these static methods in a separate package-private class. This is because Java 8 requires all static members of an interface to be public. Java 9 allows private static methods, but static fields and static member classes are still required to be public.

Statik fabrikaların dördüncü avantajı, döndürülen nesnenin sınıfının çağrıdan çağrıya giriş parametrelerinin bir fonksiyonu olarak değişebilmesidir. Bildirilen dönüş tipinin herhangi bir alt tipi (subtype) geçerlidir. Döndürülen nesnenin sınıfı sürümden sürüme de değişebilir.

A fourth advantage of static factories is that the class of the returned object can vary from call to call as a function of the input parameters. Any subtype of the declared return type is permissible. The class of the returned object can also vary from release to release.

EnumSet sınıfının (Madde 36) kamusal yapıcı metotları yoktur, yalnızca statik fabrikaları vardır. OpenJDK uygulamasında, alttaki enum tipinin boyutuna bağlı olarak iki alt sınıftan birinin örneğini döndürürler: altmış dört veya daha az elemana sahipse (çoğu enum tipi böyledir), statik fabrikalar tek bir long ile desteklenen bir RegularEnumSet örneği döndürür; altmış beş veya daha fazla elemana sahipse, fabrikalar bir long dizisi ile desteklenen bir JumboEnumSet örneği döndürür.

The EnumSet class (Item 36) has no public constructors, only static factories. In the OpenJDK implementation, they return an instance of one of two subclasses, depending on the size of the underlying enum type: if it has sixty-four or fewer elements, as most enum types do, the static factories return a RegularEnumSet instance, which is backed by a single long; if the enum type has sixty-five or more elements, the factories return a JumboEnumSet instance, backed by a long array.

Bu iki uygulama sınıfının varlığı istemciler için görünmezdir. Eğer RegularEnumSet küçük enum tipleri için performans avantajı sağlamayı bırakırsa, hiçbir olumsuz etki yaratmadan gelecek bir sürümde kaldırılabilir. Benzer şekilde, gelecek bir sürüm performans için yararlı olacaksa EnumSet'in üçüncü veya dördüncü bir uygulamasını ekleyebilir. İstemciler fabrikadan geri aldıkları nesnenin sınıfını ne bilirler ne de önemserler; tek önemsedikleri, nesnenin EnumSet'in bir alt sınıfı olmasıdır.

The existence of these two implementation classes is invisible to clients. If RegularEnumSet ceased to offer performance advantages for small enum types, it could be eliminated from a future release with no ill effects. Similarly, a future release could add a third or fourth implementation of EnumSet if it proved beneficial for performance. Clients neither know nor care about the class of the object they get back from the factory; they care only that it is some subclass of EnumSet.

Statik fabrikaların beşinci avantajı, döndürülen nesnenin sınıfının, metodu içeren sınıf yazıldığı sırada var olmasına gerek olmamasıdır. Bu tür esnek statik fabrika metotları, Java Veritabanı Bağlantısı API'si (JDBC) gibi hizmet sağlayıcı çerçevelerinin (service provider frameworks) temelini oluşturur. Hizmet sağlayıcı çerçevesi, sağlayıcıların bir hizmeti uyguladığı ve sistemin uygulamaları istemcilere sunarak istemcileri uygulamalardan ayırdığı bir sistemdir.

A fifth advantage of static factories is that the class of the returned object need not exist when the class containing the method is written. Such flexible static factory methods form the basis of service provider frameworks, like the Java Database Connectivity API (JDBC). A service provider framework is a system in which providers implement a service, and the system makes the implementations available to clients, decoupling the clients from the implementations.

Bir hizmet sağlayıcı çerçevesinin üç temel bileşeni vardır: bir uygulamayı temsil eden hizmet arayüzü (service interface); sağlayıcıların uygulamaları kaydetmek için kullandığı sağlayıcı kayıt API'si (provider registration API); ve istemcilerin hizmetin örneklerini elde etmek için kullandığı hizmet erişim API'si (service access API). Hizmet erişim API'si, istemcilerin bir uygulama seçmek için kriter belirtmesine izin verebilir. Böyle bir kriter yoksa, API varsayılan bir uygulamanın örneğini döndürür veya istemcinin mevcut tüm uygulamalar arasında gezinmesine olanak tanır. Hizmet erişim API'si, hizmet sağlayıcı çerçevesinin temelini oluşturan esnek statik fabrikadır.

There are three essential components in a service provider framework: a service interface, which represents an implementation; a provider registration API, which providers use to register implementations; and a service access API, which clients use to obtain instances of the service. The service access API may allow clients to specify criteria for choosing an implementation. In the absence of such criteria, the API returns an instance of a default implementation, or allows the client to cycle through all available implementations. The service access API is the flexible static factory that forms the basis of the service provider framework.

Bir hizmet sağlayıcı çerçevesinin opsiyonel dördüncü bileşeni, hizmet arayüzünün örneklerini üreten bir fabrika nesnesini tanımlayan hizmet sağlayıcı arayüzüdür (service provider interface). Hizmet sağlayıcı arayüzü yoksa, uygulamalar yansıtma (reflection) yoluyla (Madde 65) örneklenmelidir. JDBC durumunda, Connection hizmet arayüzünün rolünü oynar, DriverManager.registerDriver sağlayıcı kayıt API'sidir, DriverManager.getConnection hizmet erişim API'sidir ve Driver hizmet sağlayıcı arayüzüdür.

An optional fourth component of a service provider framework is a service provider interface, which describes a factory object that produce instances of the service interface. In the absence of a service provider interface, implementations must be instantiated reflectively (Item 65). In the case of JDBC, Connection plays the part of the service interface, DriverManager.registerDriver is the provider registration API, DriverManager.getConnection is the service access API, and Driver is the service provider interface.

Hizmet sağlayıcı çerçevesi kalıbının birçok varyantı vardır. Örneğin, hizmet erişim API'si sağlayıcının sunduğundan daha zengin bir hizmet arayüzü döndürebilir. Bu, Bridge kalıbıdır [Gamma95]. Bağımlılık enjeksiyonu çerçeveleri (dependency injection frameworks) (Madde 5) güçlü hizmet sağlayıcılar olarak görülebilir. Java 6'dan beri, platform genel amaçlı bir hizmet sağlayıcı çerçevesi olan java.util.ServiceLoader'ı içerir, dolayısıyla genellikle kendinizinkini yazmanıza gerek yoktur (Madde 59). JDBC, ServiceLoader kullanmaz çünkü JDBC ondan önce gelir.

There are many variants of the service provider framework pattern. For example, the service access API can return a richer service interface to clients than the one furnished by providers. This is the Bridge pattern [Gamma95]. Dependency injection frameworks (Item 5) can be viewed as powerful service providers. Since Java 6, the platform includes a general-purpose service provider framework, java.util.ServiceLoader, so you needn't, and generally shouldn't, write your own (Item 59). JDBC doesn't use ServiceLoader, as the former predates the latter.

Kavramsal Ağırlık Conceptual Weight
Conceptual Weight
Kavramsal ağırlık (Conceptual Weight), bir API'yi kullanabilmek için programcıların öğrenmesi gereken kavramların sayısını ve zorluğunu ifade eder. İyi tasarlanmış bir API, mümkün olan en az kavramsal ağırlıkla maksimum işlevsellik sunar. Uygulama detaylarını gizleyerek ve arayüzlere programlayarak kavramsal ağırlık azaltılabilir. Conceptual Weight refers to the number and difficulty of concepts that programmers must master to use an API. A well-designed API provides maximum functionality with minimal conceptual weight. Hiding implementation details and programming to interfaces helps reduce conceptual weight.
Kötü Örnek (Before) Bad Example (Before) 
// Yüksek kavramsal ağırlık — 6 farklı sınıf öğrenmeli
SyncArrayList<String> list1 = new SyncArrayList<>();
UnmodArrayList<String> list2 = new UnmodArrayList<>(list1);
CheckedArrayList<String> list3 =
    new CheckedArrayList<>(list1, String.class);
SyncLinkedList<String> list4 = new SyncLinkedList<>();
UnmodLinkedList<String> list5 = new UnmodLinkedList<>(list4);
EmptyList<String> list6 = new EmptyList<>();
Her varyasyon için ayrı bir kamusal sınıf var. Programcı altı farklı sınıf adını, her birinin yapıcısını ve hangisinin ne işe yaradığını öğrenmek zorunda. API yüzeyi gereksiz yere büyük. There's a separate public class for each variation. A programmer must learn six different class names, their constructors, and what each does. The API surface is unnecessarily large.
İyi Örnek (After) Good Example (After) 
// Düşük kavramsal ağırlık — tek sınıf, statik fabrikalar
List<String> list1 = Collections.synchronizedList(
    new ArrayList<>());
List<String> list2 = Collections.unmodifiableList(list1);
List<String> list3 = Collections.checkedList(
    list1, String.class);
List<String> list4 = Collections.emptyList();
Tüm varyasyonlar Collections sınıfındaki statik fabrika metotları aracılığıyla sunuluyor. İstemci yalnızca List arayüzünü biliyor. Uygulama sınıfları tamamen gizli. Öğrenilmesi gereken tek kavram: Collections yardımcı sınıfı. All variations are provided through static factory methods in the Collections class. The client only knows the List interface. Implementation classes are completely hidden. The only concept to learn: the Collections utility class.
Pratik İpucu: API tasarımında "bir kavramla kaç şey yapılabilir?" sorusunu sorun. Eğer her işlem için yeni bir sınıf veya arayüz öğrenmek gerekiyorsa, API çok ağır demektir. Mümkünse az sayıda arayüz ve çok sayıda statik fabrika ile aynı işlevselliği sunun. Practical Tip: In API design, ask "how much can be done with one concept?" If each operation requires learning a new class or interface, the API is too heavy. When possible, provide the same functionality through a few interfaces and many static factories.
Hizmet Sağlayıcı Çerçevesi Service Provider Framework
Service Provider Framework (SPF)
Hizmet sağlayıcı çerçevesi (Service Provider Framework), sağlayıcıların bir hizmeti uyguladığı ve sistemin bu uygulamaları istemcilere sunarak istemcileri uygulamalardan ayırdığı bir mimari kalıptır. Üç temel bileşenden oluşur: hizmet arayüzü (service interface), sağlayıcı kayıt API'si (provider registration API) ve hizmet erişim API'si (service access API). JDBC bu kalıbın en bilinen örneğidir. A Service Provider Framework (SPF) is an architectural pattern where providers implement a service, and the system makes implementations available to clients while decoupling them from implementations. It has three essential components: service interface, provider registration API, and service access API. JDBC is the best-known example of this pattern.
Kötü Örnek (Before) Bad Example (Before) 
// İstemci doğrudan uygulamaya bağımlı
public class NotificationService {
    public void send(String message) {
        // Doğrudan e-posta gönderimi — değiştirmek zor
        SmtpClient smtp = new SmtpClient("smtp.gmail.com");
        smtp.send(message);
    }
}

// SMS'e geçmek istediğinizde tüm kodu değiştirmelisiniz
Bildirim hizmeti doğrudan SmtpClient somut sınıfına bağlıdır. SMS, push notification veya başka bir kanal eklemek istediğinizde tüm kodu değiştirmeniz gerekir. Sağlayıcı ve istemci sıkı bağımlıdır. The notification service depends directly on the SmtpClient concrete class. Adding SMS, push notifications, or other channels requires changing all the code. Provider and client are tightly coupled.
İyi Örnek (After) Good Example (After) 
// 1. Hizmet arayüzü (Service Interface)
public interface NotificationSender {
    void send(String to, String message);
}

// 2. Sağlayıcı kayıt + hizmet erişim API'si
public class Notifications {
    private static final Map<String, NotificationSender>
        providers = new ConcurrentHashMap<>();

    private Notifications() {}

    // Sağlayıcı kayıt API'si
    public static void register(String name,
                                    NotificationSender sender) {
        providers.put(name, sender);
    }

    // Hizmet erişim API'si
    public static NotificationSender of(String name) {
        return providers.get(name);
    }
}

// Kullanım — istemci uygulamadan bağımsız
Notifications.register("email", new EmailSender());
Notifications.register("sms", new SmsSender());

NotificationSender sender = Notifications.of("sms");
sender.send("+905551234567", "Merhaba!");
NotificationSender hizmet arayüzüdür. Notifications.register sağlayıcı kayıt API'sidir. Notifications.of hizmet erişim API'sidir. İstemci yalnızca arayüze bağımlıdır — yeni sağlayıcılar eklemek mevcut kodu etkilemez. NotificationSender is the service interface. Notifications.register is the provider registration API. Notifications.of is the service access API. The client depends only on the interface — adding new providers doesn't affect existing code.
Pratik İpucu: Java 6+'da java.util.ServiceLoader kullanarak kendi hizmet sağlayıcı çerçevenizi sıfırdan yazmaktan kaçının. ServiceLoader, META-INF/services dosyaları aracılığıyla sağlayıcıları otomatik keşfeder. Daha karmaşık ihtiyaçlar için Dagger veya Spring gibi bağımlılık enjeksiyonu çerçeveleri kullanın. Practical Tip: In Java 6+, use java.util.ServiceLoader to avoid writing your own service provider framework from scratch. ServiceLoader automatically discovers providers through META-INF/services files. For more complex needs, use dependency injection frameworks like Dagger or Spring.
