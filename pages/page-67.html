Chapter 4 — Item 22-23: Sabitler & Etiketler

Madde 22: Arayüzleri Yalnızca Tür Tanımlamak İçin Kullanın

Item 22: Use interfaces only to define types

Bir sınıf bir arayüzü uyguladığında, arayüz sınıfın örnekleriyle neler yapılabileceğini söyleyen bir tür (type) olarak hizmet eder. Bir arayüzü başka herhangi bir amaçla kullanmak uygunsuz olur.

Bu testte başarısız olan bir arayüz türü, sabit arayüzüdür (constant interface) — yalnızca sabitler içeren, metot bulunmayan bir arayüz:

Interfaces serve as types. Using them for anything else is inappropriate. The constant interface antipattern fails this test:

// Sabit arayüzü anti-pattern — KULLANMAYIN! public interface PhysicalConstants { static final double AVOGADROS_NUMBER = 6.022_140_857e23; static final double BOLTZMANN_CONST = 1.380_648_52e-23; ... }

Bu kötü bir kalıptır — sabitleri dışa aktarmak istiyorsanız, bunları bir yardımcı sınıfa (utility class) veya ilgili sınıfa/arayüze static final alan olarak ekleyin.

Use utility classes or add constants to relevant classes instead.

Madde 23: Etiketli Sınıflar Yerine Sınıf Hiyerarşilerini Tercih Edin

Item 23: Prefer class hierarchies to tagged classes

Bazen örneklerinin iki veya daha fazla çeşidi olan bir sınıfla karşılaşabilirsiniz — bir etiket alanı (tag field) ile çeşidi belirtir:

Sometimes you see a class with a tag field indicating its flavor:

// Etiketli sınıf — sınıf hiyerarşisinden çok daha kötü! class Figure { enum Shape { RECTANGLE, CIRCLE }; final Shape shape; // Etiket alanı // Yalnızca RECTANGLE için double length, width; // Yalnızca CIRCLE için double radius; double area() { switch (shape) { case RECTANGLE: return length * width; case CIRCLE: return Math.PI * radius * radius; default: throw new AssertionError(shape); } } }

Etiketli sınıflar, karmaşık, hata eğilimli ve verimsizdir — enum, etiket alanı, switch ifadesi, karışık alanlar, gereksiz bellek kullanımı, derleme zamanı güvenliği yok. Bunlar aslında sınıf hiyerarşisinin yetersiz bir taklididir:

Tagged classes are verbose, error-prone, and inefficient. They're a poor imitation of class hierarchies:

// Sınıf hiyerarşisi — etiketli sınıfın yerine abstract class Figure { abstract double area(); } class Circle extends Figure { final double radius; Circle(double radius) { this.radius = radius; } @Override double area() { return Math.PI * radius * radius; } } class Rectangle extends Figure { final double length, width; Rectangle(double l, double w) { length = l; width = w; } @Override double area() { return length * width; } }

Sınıf hiyerarşisi versiyonu alanı gereksiz bellek israfını ortadan kaldırır, derleme zamanı tür güvenliği sağlar ve yeni şekiller eklemek basittir — sadece yeni bir alt sınıf ekleyin.

Class hierarchy eliminates waste, provides type safety, and makes adding new shapes simple — just add a subclass.

🔍 Kavramlar: 🔍 Concepts:

Etiketli Sınıf Anti-Pattern

Etiketli sınıflar şu sorunları taşır:

• Karmaşıklık: enum, switch, birden çok çeşide ait alanlar karışır
• Bellek israfı: Her çeşidin kullanmadığı alanlar yer kaplar
• Tür güvenliği yok: Yanlış alan erişimi derleme zamanında yakalanmaz
• Genişletilemez: Yeni çeşit eklemek tüm switch'leri güncellemeyi gerektirir

Çözüm: Soyut sınıf + alt sınıflar hiyerarşisi — temiz, güvenli, genişletilebilir.

Tagged classes are verbose, waste memory, lack type safety, and are hard to extend. Replace with abstract class + subclass hierarchy.
