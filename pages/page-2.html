Bu kitap yeni başlayanlar için değildir: Java ile zaten rahat olduğunuzu varsayar. Eğer değilseniz, Peter Sestoft'un Java Precisely [Sestoft16] gibi birçok kaliteli giriş metninden birini değerlendirin. Effective Java, dil hakkında çalışma düzeyinde bilgiye sahip herkes için erişilebilir olacak şekilde tasarlanmış olsa da, ileri düzey programcılar için bile düşünce malzemesi sağlamalıdır.

This book is not for beginners: it assumes that you are already comfortable with Java. If you are not, consider one of the many fine introductory texts, such as Peter Sestoft's Java Precisely [Sestoft16]. While Effective Java is designed to be accessible to anyone with a working knowledge of the language, it should provide food for thought even for advanced programmers.

Bu kitaptaki kuralların çoğu birkaç temel ilkeden türemektedir. Açıklık (clarity) ve basitlik (simplicity) her şeyin üstündedir. Bir bileşenin (component) kullanıcısı, onun davranışı karşısında asla şaşırmamalıdır. Bileşenler olabildiğince küçük olmalıdır, ancak daha küçük de olmamalıdır. (Bu kitapta kullanıldığı şekliyle bileşen terimi, bireysel bir metottan, birden fazla paketten oluşan karmaşık bir çerçeveye (framework) kadar herhangi bir yeniden kullanılabilir yazılım elemanını ifade eder.) Kod kopyalanmak yerine yeniden kullanılmalıdır (reuse). Bileşenler arasındaki bağımlılıklar (dependencies) minimumda tutulmalıdır. Hatalar (errors), oluştuktan sonra mümkün olan en kısa sürede — ideal olarak derleme zamanında (compile time) — tespit edilmelidir.

Most of the rules in this book derive from a few fundamental principles. Clarity and simplicity are of paramount importance. The user of a component should never be surprised by its behavior. Components should be as small as possible but no smaller. (As used in this book, the term component refers to any reusable software element, from an individual method to a complex framework consisting of multiple packages.) Code should be reused rather than copied. The dependencies between components should be kept to a minimum. Errors should be detected as soon as possible after they are made, ideally at compile time.

Bu kitaptaki kurallar zamanın yüzde 100'ünde geçerli olmasa da, vakaların büyük çoğunluğunda en iyi programlama pratiklerini yansıtmaktadır. Bu kuralları körü körüne takip etmemeli, ancak yalnızca ara sıra ve iyi bir gerekçeyle ihlal etmelisiniz. Programlamayı öğrenmek, tıpkı diğer birçok disiplin gibi, önce kuralları öğrenmek, sonra ne zaman kırılacağını öğrenmekten ibarettir.

While the rules in this book do not apply 100 percent of the time, they do characterize best programming practices in the great majority of cases. You should not slavishly follow these rules, but violate them only occasionally and with good reason. Learning the art of programming, like most other disciplines, consists of first learning the rules and then learning when to break them.

Bu kitap çoğunlukla performansla ilgili değildir. Açık, doğru, kullanılabilir, sağlam, esnek ve bakımı kolay programlar yazmakla ilgilidir. Bunu başarabilirseniz, ihtiyacınız olan performansı elde etmek genellikle nispeten basit bir meseledir (Madde 67). Bazı maddeler performans kaygılarını ele almaktadır ve bu maddelerin birkaçı performans rakamları sunmaktadır. "Benim makinemde" ifadesiyle sunulan bu rakamlar, en iyi ihtimalle yaklaşık değerler olarak kabul edilmelidir.

For the most part, this book is not about performance. It is about writing programs that are clear, correct, usable, robust, flexible, and maintainable. If you can do that, it's usually a relatively simple matter to get the performance you need (Item 67). Some items do discuss performance concerns, and a few of these items provide performance numbers. These numbers, which are introduced with the phrase "On my machine," should be regarded as approximate at best.

For what it's worth, my machine is an aging homebuilt 3.5GHz quad-core Intel Core i7-4770K with 16 gigabytes of DDR3-1866 CL9 RAM, running Azul's Zulu 9.0.0.15 release of OpenJDK, atop Microsoft Windows 7 Professional SP1 (64-bit).

Anti-Kalıp Antipattern
Antipattern
Anti-kalıplar (Antipatterns), ilk bakışta makul görünen ancak pratikte ciddi sorunlara yol açan yaygın programlama hatalarıdır. Effective Java boyunca // Never do this! yorumuyla işaretlenen örnekler, bu tür anti-kalıpların somut gösterimleridir. Bunları tanımak, iyi kod yazmak kadar önemlidir. Antipatterns are common programming mistakes that seem reasonable at first glance but lead to serious problems in practice. Throughout Effective Java, examples marked with // Never do this! are concrete demonstrations of such antipatterns. Recognizing them is as important as writing good code.
Kötü Örnek (Before) Bad Example (Before) 
// Never do this! - God Object antipattern
public class ApplicationManager {
    private Connection dbConnection;
    private Properties config;
    private Logger logger;

    public void saveUser(String name) { /* ... */ }
    public void sendEmail(String to) { /* ... */ }
    public void generateReport() { /* ... */ }
    public void processPayment(double amount) { /* ... */ }
    public void validateInput(String input) { /* ... */ }
    // ... 50+ daha fazla metot
}
Tek bir sınıf, veritabanı erişimi, e-posta gönderimi, rapor oluşturma ve ödeme işleme gibi birbirinden bağımsız sorumlulukları üstleniyor. Bu "Tanrı Nesnesi" (God Object) anti-kalıbı, bakımı, testi ve genişletmeyi son derece zorlaştırır. A single class handles database access, email sending, report generation, and payment processing. This "God Object" antipattern makes maintenance, testing, and extension extremely difficult.
İyi Örnek (After) Good Example (After) 
// Sorumluluklar ayrı sınıflara dağıtılmış
public class UserRepository {
    public void save(User user) { /* ... */ }
}

public class EmailService {
    public void send(String to, String body) { /* ... */ }
}

public class ReportGenerator {
    public Report generate(ReportCriteria criteria) { /* ... */ }
}

public class PaymentProcessor {
    public PaymentResult process(Payment payment) { /* ... */ }
}
Her sınıf tek bir sorumluluğa sahiptir (Tek Sorumluluk İlkesi / SRP). Bu yapı sayesinde her sınıf bağımsız olarak test edilebilir, değiştirilebilir ve genişletilebilir. Each class has a single responsibility (Single Responsibility Principle / SRP). This structure allows each class to be independently tested, modified, and extended.
Pratik İpucu: Bir sınıfın ne yaptığını tek bir cümleyle açıklayamıyorsanız, muhtemelen çok fazla sorumluluk üstlenmiştir. "Ve" kelimesi kullanmak zorunda kalıyorsanız, sınıfı bölmeyi düşünün. Practical Tip: If you can't describe what a class does in a single sentence, it probably has too many responsibilities. If you find yourself using the word "and," consider splitting the class.
Bileşen Component
Component
Effective Java'da bileşen (component) terimi, bireysel bir metottan birden fazla paketten oluşan karmaşık bir çerçeveye (framework) kadar herhangi bir yeniden kullanılabilir yazılım elemanını ifade eder. İyi tasarlanmış bileşenler küçük, odaklı ve birbirinden bağımsızdır. Bileşenler arasındaki bağımlılıklar minimumda tutulmalıdır. In Effective Java, the term component refers to any reusable software element, from an individual method to a complex framework consisting of multiple packages. Well-designed components are small, focused, and independent. Dependencies between components should be kept to a minimum.
Kötü Örnek (Before) Bad Example (Before) 
// Sıkı bağımlılık - bileşenler birbirine dolanmış
public class OrderService {

    public void placeOrder(Order order) {
        // Doğrudan somut sınıflara bağımlı
        MySqlDatabase db = new MySqlDatabase();
        db.save(order);

        SmtpEmailClient email = new SmtpEmailClient();
        email.send(order.getCustomerEmail(),
                   "Order confirmed");

        StripePayment payment = new StripePayment();
        payment.charge(order.getTotal());
    }
}
OrderService, MySqlDatabase, SmtpEmailClient ve StripePayment gibi somut sınıflara doğrudan bağımlıdır. Veritabanını değiştirmek istediğinizde tüm servisi yeniden yazmak gerekir. OrderService is directly coupled to concrete classes like MySqlDatabase, SmtpEmailClient, and StripePayment. Changing the database requires rewriting the entire service.
İyi Örnek (After) Good Example (After) 
// Gevşek bağımlılık - arayüzler üzerinden iletişim
public class OrderService {
    private final OrderRepository repository;
    private final NotificationSender notifier;
    private final PaymentGateway gateway;

    public OrderService(OrderRepository repository,
                        NotificationSender notifier,
                        PaymentGateway gateway) {
        this.repository = repository;
        this.notifier = notifier;
        this.gateway = gateway;
    }

    public void placeOrder(Order order) {
        repository.save(order);
        notifier.send(order.getCustomerEmail(),
                       "Order confirmed");
        gateway.charge(order.getTotal());
    }
}
Bağımlılıklar arayüzler (interfaces) üzerinden enjekte ediliyor. OrderService artık somut sınıfları bilmiyor; istediğimiz veritabanı, bildirim veya ödeme sistemi kolayca değiştirilebilir. Dependencies are injected through interfaces. OrderService no longer knows about concrete classes; the database, notification, or payment system can be easily swapped.
Pratik İpucu: Bir bileşenin kalitesini test edilebilirliğiyle ölçebilirsiniz. Eğer birim testi yazarken çok fazla mock oluşturmak zorunda kalıyorsanız, bileşeniniz muhtemelen çok fazla bağımlılığa sahiptir. Practical Tip: You can measure a component's quality by its testability. If you need to create too many mocks when writing unit tests, your component probably has too many dependencies.
Derleme Zamanı Hata Tespiti Compile-Time Error Detection
Compile-Time Error Detection
Hataların mümkün olan en erken aşamada — ideal olarak derleme zamanında (compile time) — yakalanması, Effective Java'nın en temel ilkelerinden biridir. Derleme zamanında yakalanan bir hata, çalışma zamanında (runtime) keşfedilen bir hataya kıyasla çok daha ucuz ve güvenlidir. Java'nın tip sistemi (type system) bu amaçla güçlü bir araçtır. Catching errors as early as possible — ideally at compile time — is one of the most fundamental principles of Effective Java. An error caught at compile time is much cheaper and safer than one discovered at runtime. Java's type system is a powerful tool for this purpose.
Kötü Örnek (Before) Bad Example (Before) 
// Hatalar çalışma zamanına kadar gizlenir
public class ConfigLoader {

    public Object getSetting(String key) {
        Map<String, Object> settings = loadSettings();
        return settings.get(key);
    }
}

// Kullanan kod - ClassCastException riski
String timeout = (String) loader.getSetting("timeout");
int port = (Integer) loader.getSetting("port");
Object dönüş tipi, derleyicinin tip güvenliğini sağlamasını engeller. Yanlış bir tip dönüşümü (cast) ancak çalışma zamanında ClassCastException ile ortaya çıkar. The Object return type prevents the compiler from ensuring type safety. An incorrect cast only manifests as a ClassCastException at runtime.
İyi Örnek (After) Good Example (After) 
// Tip güvenliği derleme zamanında sağlanır
public class TypedConfig {
    private final Map<ConfigKey<?>, Object> settings;

    public <T> T get(ConfigKey<T> key) {
        return key.type().cast(settings.get(key));
    }
}

// Tip-güvenli anahtar tanımları
public static final ConfigKey<Integer> PORT =
    ConfigKey.of("port", Integer.class);
public static final ConfigKey<String> TIMEOUT =
    ConfigKey.of("timeout", String.class);

// Kullanan kod - derleme zamanında güvenli
int port = config.get(PORT);        // tip güvenli
String timeout = config.get(TIMEOUT); // tip güvenli
Jenerik ConfigKey<T> kullanarak, derleyici her get çağrısında doğru tipi garanti eder. Yanlış tip kullanımı derleme zamanında yaklanır; çalışma zamanı sürprizleri ortadan kalkar. By using generic ConfigKey<T>, the compiler guarantees the correct type at every get call. Type misuse is caught at compile time; runtime surprises are eliminated.
Pratik İpucu: Kodunuzda (Type) şeklinde tip dönüşümleri (cast) görüyorsanız, bunların jeneriklerle (generics) ortadan kaldırılıp kaldırılamayacağını sorgulayın. Her tip dönüşümü, derleme zamanı güvenliğinden vazgeçtiğiniz bir noktadır. Practical Tip: If you see (Type) casts in your code, question whether they can be eliminated with generics. Every cast is a point where you give up compile-time safety.
Kod Yeniden Kullanımı Code Reuse
Code Reuse vs. Code Duplication
"Kod kopyalanmak yerine yeniden kullanılmalıdır" — bu ilke, yazılım mühendisliğinin temel taşlarından biridir. Aynı mantığı birden fazla yere kopyalamak, bir hata bulunduğunda veya davranış değiştirildiğinde tüm kopyaları bulmayı ve güncellemeyi gerektirir. DRY (Don't Repeat Yourself) ilkesi olarak da bilinir. "Code should be reused rather than copied" — this principle is a cornerstone of software engineering. Copying the same logic to multiple places requires finding and updating all copies when a bug is found or behavior changes. This is also known as the DRY (Don't Repeat Yourself) principle.
Kötü Örnek (Before) Bad Example (Before) 
// Aynı doğrulama mantığı her yerde tekrarlanıyor
public class UserController {
    public void createUser(String email) {
        if (email == null || !email.contains("@")
                || email.length() > 254) {
            throw new IllegalArgumentException();
        }
        // ...
    }
}

public class OrderController {
    public void placeOrder(String email) {
        if (email == null || !email.contains("@")
                || email.length() > 254) {
            throw new IllegalArgumentException();
        }
        // ...
    }
}
E-posta doğrulama mantığı iki farklı sınıfta birebir tekrarlanıyor. Doğrulama kuralı değiştiğinde (örneğin regex eklenmesi gerektiğinde) tüm kopyaları bulmak ve güncellemek gerekir. Email validation logic is duplicated verbatim in two different classes. When validation rules change (e.g., adding regex), all copies must be found and updated.
İyi Örnek (After) Good Example (After) 
// Ortak mantık tek bir yerde, yeniden kullanılabilir
public final class EmailValidator {

    private static final int MAX_LENGTH = 254;

    private EmailValidator() { }

    public static void validate(String email) {
        if (email == null || !email.contains("@")
                || email.length() > MAX_LENGTH) {
            throw new IllegalArgumentException(
                "Invalid email: " + email);
        }
    }
}

// Her yerde aynı doğrulamayı kullan
EmailValidator.validate(email);
Doğrulama mantığı tek bir yardımcı sınıfta (utility class) merkezi hale getirildi. Artık kural değişikliği tek bir yerde yapılır ve tüm kullanım noktaları otomatik güncellenir. Sihirli sayı da (magic number) isimlendirilmiş bir sabite dönüştürüldü. Validation logic is centralized in a single utility class. Rule changes are made in one place and automatically apply to all usage points. The magic number was also converted to a named constant.
Pratik İpucu: "Üç Kural"ını uygulayın: Aynı kodu üçüncü kez kopyaladığınızı fark ettiğinizde, onu mutlaka yeniden kullanılabilir bir bileşene çıkarın. İki tekrar kabul edilebilir, üç tekrar bir uyarı işaretidir. Practical Tip: Apply the "Rule of Three": When you notice yourself copying the same code for the third time, extract it into a reusable component. Two repetitions may be acceptable; three is a warning sign.
