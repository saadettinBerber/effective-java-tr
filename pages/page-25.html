Chapter 2 — Item 7: Artık zamanını doldurmuş eski(ölü) nesne referanslarını tamamen silkeleyip temizleyin / Eliminate obsolete object references

...veya C++ gibi bellek yönetimini sizin bizzat manuel yönettiğiniz dillerden Java gibi "çöp toplayıcılı (garbage-collected)" bir dile geçiş yaptıysanız, eski objelerle işiniz bittiğinde bunların otomatik olarak bellekten geri iddia edilmesi (reclaimed) programcı sıfatıyla işinizi olağanüstü kolaylaştırmıştır. Otomatik çöp temizliği nimetini ilk kez tecrübe ettiğinizde kulağa neredeyse sihirmiş (magic) gibi gelir. Ne var ki, bu rahatlık "artık bellek yönetimiyle ilgili kesinlikle düşünmeme gerek yok!" şeklinde bir yanılgıya kolaylıkla sebebiyet verebilir, lakin bu hiç de büsbütün doğru bir intiba değildir.

Aşağıdaki çok bilindik ve meşhur Stack (Yığın) sınıfı uyarlamasını göz önünde bulundurun:

...or C++, to a garbage-collected language such as Java, your job as a programmer was made much easier by the fact that your objects are automatically reclaimed when you’re through with them. It seems almost like magic when you first experience it. It can easily lead to the impression that you don’t have to think about memory management, but this isn’t quite true.

Consider the following simple stack implementation:

// Siz buradaki "hafıza kaçağını (memory leak)" saptayabildiniz mi? // Can you spot the "memory leak"? public class Stack { private Object[] elements; private int size = 0; private static final int DEFAULT_INITIAL_CAPACITY = 16; public Stack() { elements = new Object[DEFAULT_INITIAL_CAPACITY]; } public void push(Object e) { ensureCapacity(); elements[size++] = e; } public Object pop() { if (size == 0) throw new EmptyStackException(); return elements[--size]; } /** * En az bir element daha alabilecek kadar kapasite olduğundan emin olur, * dizi limiti her dolduğunda (taşma ihtimalinde) havuz kapasitesini kabaca ikiye katlar. */ private void ensureCapacity() { if (elements.length == size) elements = Arrays.copyOf(elements, 2 * size + 1); } }

İlk bakışta bu programın gözle görülür korkunç, aşikâr bir problemi bulunmuyor gibi görünebilir (ancak yine de siz buradaki yapının ideal "jenerik—generic" tarzda daha güncel bir uyarlaması için detaylı bir okuma olan Madde 29'a bakın). Siz bu programı dibine kadar yorucu bin bir teste (exhaustively) de tabi tutsanız, bu stack tüm o yorucu testleri yıldızlı pekiyilerle göz kamaştırıcı şekilde hatasız geçecektir—ama yine de derinde çok ciddi pusuda bekleyen korkunç bir problem vardır (lurking). Geniş manada ele alındığında (Loosely speaking), bu programın şüphesiz biçimde bir "hafıza kaçağı (memory leak)" tehlikesi yatmaktadır; bu gizli kaçak sessiz bir cinayet gibi varlığını, Çöp Toplayıcı'ya (Garbage Collector) durduk yere fazladan mesai yüklenmesi veya uygulamanın ayakizinin sinsice tırmanması sonucuna istinaden yalnızca azalan performans eğrilerinde belli edebiilir. Durumlar aşırı vahim hallere yaklaştığında (In extreme cases), bu tür sinsi bellek sızıntıları disk paging'e (disk belleği kullanımı) kapı aralar; hatta daha fenası da belleğin iflas etmesine neden olarak bilindik vahşi OutOfMemoryError çökmesiyle programı sonlandırabilir ki ancak bunun ne mutlu ki nadir yaşanacağını belirteyim.

O halde bu ölümcül bellek kaçağı tam olarak nerededir? Diyelim ki bir yığın (stack) olağanca nesneyle tepeleme doldu ve (büyüdü - grew) sonrasında da pop() metoduyla tekrardan eksilmeye ve küçülmeye (shrinks) başladı. Bu silinen objeler gerçekte . . . (Devamı sonraki sayfada)

There’s nothing obviously wrong with this program (but see Item 29 for a generic version). You could test it exhaustively, and it would pass every test with flying colors, but there’s a problem lurking. Loosely speaking, the program has a “memory leak,” which can silently manifest itself as reduced performance due to increased garbage collector activity or increased memory footprint. In extreme cases, such memory leaks can cause disk paging and even program failure with an OutOfMemoryError, but such failures are relatively rare.

🔍 Kavramlar: 🔍 Concepts:

Garbage Collector (Çöp Toplayıcı) / GC

C ve C++ dillerinde bilgisayardan manuel istenen belleği (RAM) programcının gerisin geri tekrar bellekten silerek iade etmesi (örn. free() veya delete) şarttır. Java gibi yüksek seviyeli dillerde ise bellekteki bir nesne artık uygulamanın hiçbir ucundan (root node) ulaşılamaz / referans barındırmaz ise, sinsi bir Java arka plan servisi olan JVM "Garbage Collector" devreye girip o sahipsiz nesneyi uzay boşluğuna fırlatıp hafızadaki o yeri sizin için ferahlatır ve açar.

In languages like C/C++, you must manually allocate and free() memory. In Java, an invisible background process called the JVM Garbage Collector sweeps through your heap memory occasionally and auto-deletes any objects that don't have active references pointing to them anymore.

💡 Java'nın mucize gibi otomatik çöp sildiği gerçeği maalesef bizi "artık hafıza yönetiminde tembel olabilirim" yalanına teşvik edebilir. Yanlış tasarımla canlı bir listeye nesne tıkıştırıp unutursanız, o listeye giden referans hiç kesilmeyeceği için GC nesneyi silemez. O objeye "Ölü/Tarihi Geçmiş Referans" deriz.

Memory Leak (Hafıza / Bellek Sızıntısı Kaçağı)

Memory Leak kısaca programın ayırdığı ve ancak ve ancak bir daha aslında hiç kullanmayacağı o devasa belleği işletim sistemine inatla geri salamaması, teslim edememesi kilitlenme noktasıdır.

Bilhassa koleksiyonlar, listeler ve nesne saklayan diziler bu kaçağın efendisidir. Stack örneğindeki array boyutu 16 eleman ve boyu (size) 5 olduğunda... Geriye kalan kullanılmayan 11 elemanlık boş kısımlardaki eski objelerin referansı silinmediği sürece (yani oradaki slot "null" yapılmadığı müddetçe) Çöp toplayıcı GC bunu hâlâ kullanıldığı farz ederek asla silemez. Saatler sonra koca uygulama şişer, yavaşlar ve OOM Error fırlatır.

A Memory Leak is a situation where unused, discarded objects are stubbornly retained in memory because your code inadvertently holds an active reference to them. The GC cannot delete them as long as this reference exists. Over time, your RAM usage swells until the system crashes with OutOfMemoryError.

Disk Paging & Swapping

Bilgisayardaki veya sunucunuzdaki Fiziksel RAM tamamen dolduğunda (örn bellek kaçakları yüzünden), işletim sistemi aniden uygulamayı çökertmek yerine hayatta tutabilmek için aşırı uyduruk son bir hileye başvurur: Normalde inanılmaz derecede, kat ve kat daha yavaş olan HDD, SSD gibi kalıcı fiziksel disklerinizi yapay olarak "RAM" gibi kullanmaya kalkışıp (page table vs swap space üzerinden) uygulamayı bir süre daha yavaştan ittirerek ayağa tutmaya çalışır.

When system RAM gets exhausted entirely (e.g., due to extreme memory leaks), the operating system starts using empty portions of the physical Hard Drive or SSD as a fake emergency RAM (a technique called Swapping/Paging). Since SSDs/HDDs are vastly slower than physical RAM chips, the performance of the program crumbles drastically.

💡 Düşen uygulama performansının en büyük faillerinden biri de RAM tükenip makinenin diski sömürdüğü bu acı verici "paging" kâbusudur.
