Chapter 1: Introduction Bölüm 1: Giriş

Bu kitap, Java programlama dilini ve onun temel kütüphanelerini — java.lang, java.util ve java.io ile java.util.concurrent ve java.util.function gibi alt paketlerini — etkili bir şekilde kullanmanıza yardımcı olmak için tasarlanmıştır. Diğer kütüphaneler de zaman zaman ele alınmaktadır.

This book is designed to help you make effective use of the Java programming language and its fundamental libraries: java.lang, java.util, and java.io, and subpackages such as java.util.concurrent and java.util.function. Other libraries are discussed from time to time.

Bu kitap, her biri bir kural ileten doksan maddeden (item) oluşmaktadır. Bu kurallar, en iyi ve en deneyimli programcılar tarafından genel olarak faydalı kabul edilen pratikleri yansıtmaktadır. Maddeler, her biri yazılım tasarımının geniş bir yönünü kapsayan on bir bölüm (chapter) halinde gevşek bir şekilde gruplandırılmıştır. Kitabın baştan sona okunması amaçlanmamıştır: her madde aşağı yukarı kendi başına bağımsızdır. Maddeler yoğun bir şekilde çapraz referanslandırılmıştır, böylece kitapta kolayca kendi rotanızı çizebilirsiniz.

This book consists of ninety items, each of which conveys one rule. The rules capture practices generally held to be beneficial by the best and most experienced programmers. The items are loosely grouped into eleven chapters, each covering one broad aspect of software design. The book is not intended to be read from cover to cover: each item stands on its own, more or less. The items are heavily cross-referenced so you can easily plot your own course through the book.

Tasarım Kalıpları Design Patterns
Design Patterns — Gang of Four [Gamma95]
Tasarım kalıpları (Design Patterns), yazılım geliştirmede tekrar eden sorunlara yönelik denenmiş ve doğrulanmış çözüm şablonlarıdır. "Gang of Four" (GoF) olarak bilinen dört yazar — Gamma, Helm, Johnson ve Vlissides — tarafından sistematize edilmiştir. Effective Java boyunca bu kalıplara sık sık referans verilmektedir. Design Patterns are proven, reusable solutions to commonly recurring problems in software development. They were systematized by the four authors known as the "Gang of Four" (GoF) — Gamma, Helm, Johnson, and Vlissides. Effective Java frequently references these patterns throughout the book.
Kötü Örnek (Before) Bad Example (Before) 
// Doğrudan nesne oluşturma - esnekliği kısıtlar
public class NotificationService {

    public void send(String message, String type) {
        if (type.equals("email")) {
            EmailSender sender = new EmailSender();
            sender.send(message);
        } else if (type.equals("sms")) {
            SmsSender sender = new SmsSender();
            sender.send(message);
        } else if (type.equals("push")) {
            PushSender sender = new PushSender();
            sender.send(message);
        }
    }
}
Her yeni bildirim tipi eklendiğinde mevcut kodu değiştirmek gerekmektedir. Bu, Açık/Kapalı İlkesini (Open/Closed Principle) ihlal eder ve bakım maliyetini artırır. Every time a new notification type is added, existing code must be modified. This violates the Open/Closed Principle and increases maintenance cost.
İyi Örnek (After) Good Example (After) 
// Strategy Pattern kullanarak esneklik sağlama
public interface NotificationSender {
    void send(String message);
}

public class EmailSender implements NotificationSender {
    @Override
    public void send(String message) {
        // E-posta gönderim mantığı
    }
}

public class NotificationService {
    private final NotificationSender sender;

    public NotificationService(NotificationSender sender) {
        this.sender = sender;
    }

    public void send(String message) {
        sender.send(message);
    }
}
Strategy kalıbını (Strategy Pattern) kullanarak, yeni bildirim tipi eklemek için mevcut koda dokunmadan yeni bir sınıf oluşturmak yeterlidir. Bağımlılıkları tersine çevirerek (Dependency Inversion) sistemi genişletilebilir hale getirdik. Using the Strategy Pattern, adding a new notification type only requires creating a new class without touching existing code. By inverting dependencies (Dependency Inversion), we made the system extensible.
Pratik İpucu: Kodunuzda if/else veya switch zincirleri gördüğünüzde, bunların bir tasarım kalıbıyla değiştirilip değiştirilemeyeceğini düşünün. Strategy, Factory Method ve Observer kalıpları en sık kullanılan alternatiflerdir. Practical Tip: When you see if/else or switch chains in your code, consider whether they could be replaced by a design pattern. Strategy, Factory Method, and Observer are the most commonly used alternatives.
API (Application Programming Interface)
Uygulama Programlama Arayüzü Application Programming Interface
API (Application Programming Interface), bir yazılım bileşeniyle dışarıdan nasıl etkileşim kurulacağını tanımlayan sözleşme (contract) niteliğindeki arayüzdür. Java'da API denildiğinde genellikle bir sınıfın, arayüzün veya paketin kamusal metotları (public methods) ve tipleri kastedilir. İyi tasarlanmış bir API, kullanıcı için anlaşılır, yanlışa yer bırakmayan ve genişletilebilir olmalıdır. An API (Application Programming Interface) is a contract-like interface that defines how external code interacts with a software component. In Java, API typically refers to the public methods and types of a class, interface, or package. A well-designed API should be understandable, hard to misuse, and extensible.
Kötü Örnek (Before) Bad Example (Before) 
// Kötü API tasarımı - belirsiz parametre anlamları
public class UserManager {

    public List<Object> get(String s, boolean b,
                                  int n) {
        // s nedir? b ne işe yarar? n neyi sınırlar?
        return null;
    }
}
Metot adı belirsiz (get), parametreler kendini açıklamıyor (s, b, n), dönüş tipi genel (List<Object>) ve null döndürüyor. Bu API'yi kullanan geliştirici, kaynak kodunu okumadan metodu anlayamaz. The method name is vague (get), parameters are unclear (s, b, n), the return type is generic (List<Object>), and it returns null. A developer using this API cannot understand the method without reading the source code.
İyi Örnek (After) Good Example (After) 
// İyi API tasarımı - kendini açıklayan, tip-güvenli
public class UserRepository {

    public List<User> findActiveUsersByRole(
            Role role, int maxResults) {
        // Açık metot adı, anlamlı parametreler,
        // tip-güvenli dönüş değeri
        return Collections.emptyList();
    }
}
Metot adı ne yaptığını açıkça belirtiyor, parametreler anlamlı tiplerle tanımlanmış, dönüş tipi belirli (List<User>) ve boş liste döndürerek null'dan kaçınılmış. Bu API kendini belgelemektedir (self-documenting). The method name clearly states what it does, parameters are defined with meaningful types, the return type is specific (List<User>), and it returns an empty list instead of null. This API is self-documenting.
Pratik İpucu: Bir sınıfın kamusal metotlarını yazarken, kendinizi o sınıfın kullanıcısı olarak hayal edin. Metot imzasına bakarak ne yaptığını anlayabiliyor musunuz? Eğer JavaDoc okumadan anlayamıyorsanız, API'niz yeterince açık değildir. Practical Tip: When writing public methods for a class, imagine yourself as a user of that class. Can you understand what the method does just by looking at its signature? If you cannot understand it without reading JavaDoc, your API is not clear enough.
