Item 2: Consider a builder when faced with many constructor parameters Madde 2: Çok Sayıda Parametreyle Karşılaşınca Builder'ı Düşünün
↩ Önceki sayfadan devam: Teleskopik yapıcı (telescoping constructor) kalıbı inceleniyordu. ↩ Continued from previous page: The telescoping constructor pattern was being discussed.

…hangi parametrenin ne anlama geldiğini anlamak için tek tek saymanız gerekir. Aynı tipte art arda gelen uzun parametre dizileri ince hatalara (subtle bugs) yol açabilir. İstemci (client) iki parametreyi yanlışlıkla yer değiştirirse, derleyici (compiler) şikâyet etmez; ancak program çalışma zamanında (runtime) yanlış davranır (Madde 51).

…parameters to find out. Long sequences of identically typed parameters can cause subtle bugs. If the client accidentally reverses two such parameters, the compiler won't complain, but the program will misbehave at runtime (Item 51).

Çok sayıda opsiyonel (optional) parametreyle karşılaştığınızda başvurabileceğiniz ikinci alternatif, JavaBeans kalıbıdır (JavaBeans pattern). Bu yaklaşımda nesneyi oluşturmak için parametresiz bir yapıcı metot (parameterless constructor) çağrılır; ardından her zorunlu ve istenen her opsiyonel alan için ayrı ayrı setter metotları çağrılır:

A second alternative when you're faced with many optional parameters in a constructor is the JavaBeans pattern, in which you call a parameterless constructor to create the object and then call setter methods to set each required parameter and each optional parameter of interest:

NutritionFacts — JavaBeans Kalıbı
NutritionFacts — JavaBeans Pattern
// JavaBeans Kalıbı — tutarsızlığa izin verir, değiştirilebilirliği zorunlu kılar
public class NutritionFacts {
    // Parametreler varsayılan değerlerine ilklendiriliyor
    private int servingSize  = -1; // Zorunlu; varsayılan değer yok
    private int servings     = -1; // Zorunlu; varsayılan değer yok
    private int calories     = 0;
    private int fat          = 0;
    private int sodium       = 0;
    private int carbohydrate = 0;

    public NutritionFacts() { }

    // Setter metotları
    public void setServingSize(int val)  { servingSize = val;  }
    public void setServings(int val)     { servings = val;     }
    public void setCalories(int val)    { calories = val;    }
    public void setFat(int val)         { fat = val;         }
    public void setSodium(int val)      { sodium = val;      }
    public void setCarbohydrate(int val){ carbohydrate = val; }
}

Bu kalıbın teleskopik yapıcı kalıbının hiçbir dezavantajı yoktur. Nesne oluşturmak kolaydır, biraz uzun olsa da; ve ortaya çıkan kodu okumak son derece rahat:

This pattern has none of the disadvantages of the telescoping constructor pattern. It is easy, if a bit wordy, to create instances, and easy to read the resulting code: 

NutritionFacts cocaCola = new NutritionFacts();
cocaCola.setServingSize(240);
cocaCola.setServings(8);
cocaCola.setCalories(100);
cocaCola.setSodium(35);
cocaCola.setCarbohydrate(27);

Ne var ki JavaBeans kalıbının kendine özgü ciddi dezavantajları vardır. Nesnenin oluşturulması birden fazla çağrıya yayıldığından, bir JavaBean'in oluşturma sürecinin ortasında tutarsız bir durumda (inconsistent state) bulunması mümkündür. Sınıf, tutarlılığı yalnızca yapıcı metot parametrelerinin geçerliliğini denetleyerek sağlama seçeneğine sahip değildir. Tutarsız durumdaki bir nesneyi kullanmaya çalışmak, hatayı içeren koddan çok uzak noktalarda sorunlara yol açabilir ve bu durum hata ayıklamayı (debug) son derece güçleştirir. Birbiriyle ilişkili bir başka dezavantaj ise JavaBeans kalıbının…

Unfortunately, the JavaBeans pattern has serious disadvantages of its own. Because construction is split across multiple calls, a JavaBean may be in an inconsistent state partway through its construction. The class does not have the option of enforcing consistency merely by checking the validity of the constructor parameters. Attempting to use an object when it's in an inconsistent state may cause failures that are far removed from the code containing the bug and hence difficult to debug. JavaBeans Kalıbı (JavaBeans Pattern) JavaBeans Pattern
Parametresiz yapıcı + setter metotlarla nesne oluşturma Object construction via parameterless constructor + setters
JavaBeans kalıbında nesne önce parametresiz yapıcı ile oluşturulur, ardından alanlar tek tek setter metotları aracılığıyla atanır. Okunabilirliği yüksek ancak oluşturma sürecinin ortasında nesne geçersiz bir durumda kalabilir. In the JavaBeans pattern, an object is first created with a no-arg constructor, then fields are set individually via setter methods. Readable but the object can be in an invalid state mid-construction.
✗ Kötü (JavaBeans riski) 
// Kötü: Alanlar tek tek set ediliyor; nesne eksik kalabilir
ServerConfig config = new ServerConfig();
config.setHost("localhost");
// Unutuldu: config.setPort(8080)
// config artık geçersiz durumda!
server.start(config); // NullPointerException veya yanlış davranış
Port ayarlanmadan nesne kullanıma geçiyor. Derleyici bunu yakalayamaz; hata ancak çalışma zamanında ortaya çıkar. The object is used before port is set. The compiler can't catch this; the error only surfaces at runtime.
✓ İyi (Builder kalıbı) 
// İyi: Tüm zorunlu alanlar builder constructor'ında zorunlu kılınıyor
ServerConfig config = new ServerConfig.Builder("localhost", 8080)
    .timeout(30)
    .maxConnections(100)
    .build();
Zorunlu parametreler Builder'ın yapıcısına taşındı. Nesne ya tam ve geçerli olarak oluşturulur, ya da hiç oluşturulamaz. Required parameters are moved to Builder's constructor. The object is either fully valid or not created at all.
💡 İpucu: JavaBeans kalıbı mevcut kütüphanelerle uyumluluk için zorunlu kalabilir (örneğin Spring MVC form nesneleri). Ancak kendi tasarımlarınızda tercih etmekten kaçının. 💡 Tip: The JavaBeans pattern may be unavoidable for compatibility with existing frameworks (e.g., Spring MVC form objects). But avoid it in your own designs.
Tutarsız Durum (Inconsistent State) Inconsistent State
Nesnenin oluşturma sürecinde eksik veya geçersiz alanlarla bulunması Object being in an incomplete or invalid state during construction
JavaBeans kalıbında nesne oluşturma birden fazla adıma yayıldığı için, herhangi bir adımda nesne eksik alanlara sahip olabilir. Bu durumda nesneyi kullanan kod, asıl hatanın kaynağından çok uzak bir noktada başarısız olabilir. In the JavaBeans pattern, construction spans multiple steps, so at any step the object may have missing fields. Code using such an object may fail far from the actual source of the bug.
✗ Kötü (tutarsız durum) 
// Kötü: EmailMessage tutarsız durumda başlatılıyor
EmailMessage msg = new EmailMessage();
msg.setSubject("Merhaba");
// msg.setTo() unutuldu — recipient eksik
emailService.send(msg); // Uzak bir sınıfta NullPointerException
Alıcı alanı boş. Hata emailService.send() içinde fırlatılıyor ama asıl sorun yukarıda, setTo()'nun unutulmasında. Recipient field is null. Exception is thrown inside emailService.send() but the real problem is above — setTo() was forgotten.
✓ İyi (doğrulama builder'da) 
// İyi: Zorunlu alanlar builder içinde doğrulanıyor
public EmailMessage(Builder builder) {
    if (builder.to == null)
        throw new IllegalArgumentException("'to' alanı zorunlu");
    this.to = builder.to;
    // diğer alanlar...
}

// Kullanım: Eksik olursa build() sırasında hata fırlatılır
EmailMessage msg = new EmailMessage.Builder()
    .to("kullanici@ornek.com")
    .subject("Merhaba")
    .build(); // Hata varsa burada, erken ve açıkça
Hata nesnenin kullanım noktasında değil, oluşturulma noktasında fırlatılıyor. "Fail-fast" prensibi. Error is thrown at construction point, not at usage point. This is the fail-fast principle.
💡 İpucu: Nesnenin hiçbir zaman tutarsız durumda bulunmaması gerekiyorsa, tüm zorunlu alanları yapıcı metotta alın ve doğrulayın — ister doğrudan yapıcı ister Builder üzerinden. 💡 Tip: If an object should never be in an inconsistent state, take all required fields in the constructor and validate them — whether through a direct constructor or a Builder.
Aynı Tipli Parametre Tehlikesi Identically-Typed Parameter Risk
Benzer tipli parametrelerin yanlış sıralaması derleme hatası vermez Swapping same-typed parameters causes no compile error but wrong behavior
Teleskopik yapıcı kalıbının önemli bir zafiyeti: arka arkaya aynı tipten parametreler geldiğinde, yanlış sırayla aktarılan argümanlar derleme zamanında yakalanamaz. Derleyici sadece tiplere bakar, anlama bakmaz. A key weakness of the telescoping constructor: when consecutive parameters have the same type, arguments passed in the wrong order produce no compile error. The compiler checks types, not meaning.
✗ Kötü (yanlış sıra fark edilmez) 
// Kötü: Yapıcıda 4 adet int parametre — enlem/boylam sırası kolayca karışır
public BoundingBox(int north, int south, int east, int west) { ... }

// Kullanımda east ile west yanlış sırada — derleyici sessiz kalır!
BoundingBox box = new BoundingBox(41, 36, 29, 26); // hangisi ne?
Dört int parametrenin anlamı belirsiz. Konum yanlış hesaplanır, hata çalışma zamanında ve muhtemelen çok uzak bir noktada fark edilir. Four int parameters with unclear meaning. Location computed incorrectly; error noticed at runtime, possibly far from the source.
✓ İyi (Builder ile adlandırılmış parametreler) 
// İyi: Builder ile her parametre adıyla atanıyor
BoundingBox box = new BoundingBox.Builder()
    .north(41)
    .south(36)
    .east(29)
    .west(26)
    .build();
Her değer açıkça adlandırıldı. Sıralama hatası yapılamaz çünkü her değer kendi metoduyla geçiyor. Every value is explicitly named. Order mistakes are impossible because each value is passed through its own method.
💡 İpucu: Bir metodun ya da yapıcının aynı tipte 3'ten fazla parametresi varsa, Builder veya özel bir parametre nesnesi (parameter object) oluşturmayı ciddi olarak değerlendirin. 💡 Tip: If a method or constructor has more than 3 parameters of the same type, seriously consider a Builder or a dedicated parameter object.
