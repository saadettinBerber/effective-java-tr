Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün Item 2: Consider a Builder When Faced with Many Constructor Parameters

Item 2: Consider a builder when faced with many constructor parameters Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün

Statik fabrikalar ve yapıcı metotlar (constructors) ortak bir sınırlamayı paylaşır: çok sayıda opsiyonel parametreye iyi ölçeklenmezler. Paketlenmiş gıdaların üzerinde görülen Besin Bilgileri etiketini temsil eden bir sınıf düşünün. Bu etiketlerin birkaç zorunlu alanı vardır — porsiyon büyüklüğü, kaptaki porsiyon sayısı ve porsiyon başına kalori — ve yirmiden fazla opsiyonel alanı vardır: toplam yağ, doymuş yağ, trans yağ, kolesterol, sodyum vb. Çoğu ürün bu opsiyonel alanların yalnızca birkaçında sıfırdan farklı değerlere sahiptir.

Static factories and constructors share a limitation: they do not scale well to large numbers of optional parameters. Consider the case of a class representing the Nutrition Facts label that appears on packaged foods. These labels have a few required fields—serving size, servings per container, and calories per serving—and more than twenty optional fields—total fat, saturated fat, trans fat, cholesterol, sodium, and so on. Most products have nonzero values for only a few of these optional fields.

Böyle bir sınıf için ne tür yapıcı metotlar veya statik fabrikalar yazmalısınız? Geleneksel olarak, programcılar teleskopik yapıcı (telescoping constructor) kalıbını kullanmışlardır; bu kalıpta yalnızca zorunlu parametrelere sahip bir yapıcı, tek bir opsiyonel parametreli başka bir yapıcı, iki opsiyonel parametreli başka bir yapıcı ve böyle devam ederek, tüm opsiyonel parametreleri içeren bir yapıcıyla sonlandırılır. İşte pratikte nasıl göründüğü. Kısa tutmak amacıyla yalnızca dört opsiyonel alan gösterilmektedir:

What sort of constructors or static factories should you write for such a class? Traditionally, programmers have used the telescoping constructor pattern, in which you provide a constructor with only the required parameters, another with a single optional parameter, a third with two optional parameters, and so on, culminating in a constructor with all the optional parameters. Here's how it looks in practice. For brevity's sake, only four optional fields are shown:

Teleskopik Yapıcı Kalıbı Telescoping Constructor Pattern
Telescoping Constructor Pattern
Teleskopik yapıcı kalıbı (Telescoping Constructor Pattern), çok sayıda opsiyonel parametreye sahip sınıflar için giderek daha fazla parametre içeren yapıcı metotlar zinciri oluşturmaktır. Her yapıcı bir öncekini çağırır ve yeni bir parametre ekler. Parametre sayısı arttıkça kod okunması ve yazılması çok zorlaşır — hangi parametrenin ne anlama geldiğini takip etmek neredeyse imkansız hale gelir. The Telescoping Constructor Pattern creates a chain of constructors with increasing numbers of parameters for classes with many optional parameters. Each constructor calls the previous one and adds a new parameter. As the parameter count grows, the code becomes very hard to read and write — tracking which parameter means what becomes nearly impossible.
Kötü Örnek (Before) Bad Example (Before) 
// Teleskopik yapıcı — parametre sayısı arttıkça kabus
public class Pizza {
    private final String crust;     // zorunlu
    private final String sauce;     // zorunlu
    private final boolean cheese;
    private final boolean pepperoni;
    private final boolean mushrooms;
    private final boolean olives;

    public Pizza(String crust, String sauce) {
        this(crust, sauce, false, false,
             false, false);
    }
    public Pizza(String crust, String sauce,
                 boolean cheese) {
        this(crust, sauce, cheese, false,
             false, false);
    }
    // ... 4 yapıcı daha
}

// Çağrı — hangi boolean ne anlama geliyor?
Pizza p = new Pizza("thin", "tomato",
    true, false, true, false);
Altı yapıcı gerekiyor ve her yeni malzeme için bir tane daha eklenecek. Çağrı noktasında true, false, true, false dizisi hangi malzemenin ne olduğunu söylemiyor — parametre sırasını ezberlemeniz gerekiyor. Six constructors are needed, and each new topping requires another. At the call site, the true, false, true, false sequence doesn't tell you which topping is which — you need to memorize the parameter order.
İyi Örnek (After) Good Example (After) 
// Builder kalıbı — okunabilir ve esnek
public class Pizza {
    private final String crust;
    private final String sauce;
    private final boolean cheese;
    private final boolean pepperoni;
    private final boolean mushrooms;
    private final boolean olives;

    public static class Builder {
        private final String crust;
        private final String sauce;
        private boolean cheese    = false;
        private boolean pepperoni = false;
        private boolean mushrooms = false;
        private boolean olives    = false;

        public Builder(String crust, String sauce) {
            this.crust = crust;
            this.sauce = sauce;
        }
        public Builder cheese()    { cheese = true; return this; }
        public Builder pepperoni() { pepperoni = true; return this; }
        public Builder mushrooms() { mushrooms = true; return this; }
        public Builder olives()    { olives = true; return this; }

        public Pizza build() {
            return new Pizza(this);
        }
    }
    private Pizza(Builder b) { /* alanları kopyala */ }
}

// Çağrı — her parametre açıkça okunabilir
Pizza p = new Pizza.Builder("thin", "tomato")
    .cheese()
    .mushrooms()
    .build();
Builder kalıbı ile her opsiyonel parametre adıyla belirtilir. Çağrı noktasında .cheese().mushrooms() yazmak, true, false, true, false'dan çok daha okunabilir. Yeni malzeme eklemek mevcut kodu bozmaz. With the Builder pattern, each optional parameter is specified by name. Writing .cheese().mushrooms() at the call site is far more readable than true, false, true, false. Adding new toppings doesn't break existing code.
Pratik İpucu: Üç veya daha fazla opsiyonel parametreniz varsa, teleskopik yapıcı yerine Builder kalıbını tercih edin. Özellikle parametreler aynı tipteyse (birden fazla boolean veya int gibi), Builder hataları önler. IDE'ler Builder oluşturmayı otomatikleştirebilir (IntelliJ: "Replace Constructor with Builder" refactoring). Practical Tip: If you have three or more optional parameters, prefer the Builder pattern over telescoping constructors. Especially when parameters share the same type (multiple booleans or ints), Builder prevents errors. IDEs can automate Builder creation (IntelliJ: "Replace Constructor with Builder" refactoring).
Builder Kalıbı Builder Pattern
Builder Pattern (GoF)
Builder kalıbı (Builder Pattern), karmaşık nesnelerin adım adım oluşturulmasını sağlayan bir tasarım kalıbıdır. İstemci önce bir Builder nesnesi oluşturur, ardından setter benzeri metotlarla istenen parametreleri belirler ve son olarak build() çağrısıyla değişmez (immutable) nesneyi elde eder. Bu kalıp hem okunabilirlik hem de güvenlik sağlar: nesne tamamlanmadan kullanılamaz ve alan değerleri sonradan değiştirilemez. The Builder Pattern is a design pattern for step-by-step construction of complex objects. The client first creates a Builder object, sets desired parameters through setter-like methods, and finally obtains the immutable object via a build() call. This pattern provides both readability and safety: the object cannot be used before completion, and field values cannot be changed afterward.
Kötü Örnek (Before) Bad Example (Before) 
// JavaBeans kalıbı — tutarsız durum riski
public class HttpRequest {
    private String url;
    private String method;
    private Map<String, String> headers;
    private String body;
    private int timeout;

    public HttpRequest() {}
    public void setUrl(String url) { this.url = url; }
    public void setMethod(String m) { this.method = m; }
    public void setHeaders(Map<String,String> h) { this.headers = h; }
    public void setBody(String b) { this.body = b; }
    public void setTimeout(int t) { this.timeout = t; }
}

// Nesne tutarsız durumda olabilir
HttpRequest req = new HttpRequest();
req.setUrl("https://api.example.com");
// method ayarlanmadan kullanılabilir → BUG!
req.setTimeout(5000);
JavaBeans kalıbında nesne boş yapıcı ile oluşturulup setter'larla doldurulur. Sorun: nesne birden fazla çağrıyla oluşturulduğu için oluşturma sürecinde tutarsız durumda (inconsistent state) kalabilir. Ayrıca setter'lar nesneyi değişebilir (mutable) kılar, bu da thread güvenliğini zorlaştırır. In the JavaBeans pattern, the object is created with an empty constructor and filled via setters. Problem: since the object is constructed over multiple calls, it may be in an inconsistent state during construction. Also, setters make the object mutable, complicating thread safety.
İyi Örnek (After) Good Example (After) 
// Builder kalıbı — güvenli ve okunabilir
public class HttpRequest {
    private final String url;
    private final String method;
    private final Map<String, String> headers;
    private final String body;
    private final int timeout;

    public static class Builder {
        private final String url;    // zorunlu
        private String method = "GET";
        private Map<String,String> headers = Map.of();
        private String body = "";
        private int timeout = 30_000;

        public Builder(String url) {
            this.url = Objects.requireNonNull(url);
        }
        public Builder method(String m) { method = m; return this; }
        public Builder header(String k, String v) {
            headers = new HashMap<>(headers);
            headers.put(k, v); return this;
        }
        public Builder body(String b) { body = b; return this; }
        public Builder timeout(int ms) { timeout = ms; return this; }
        public HttpRequest build() {
            return new HttpRequest(this);
        }
    }

    private HttpRequest(Builder b) {
        this.url = b.url;
        this.method = b.method;
        this.headers = Map.copyOf(b.headers);
        this.body = b.body;
        this.timeout = b.timeout;
    }
}

// Kullanım — akıcı ve güvenli
HttpRequest req = new HttpRequest.Builder("https://api.example.com")
    .method("POST")
    .header("Content-Type", "application/json")
    .body("{\"key\": \"value\"}")
    .timeout(5000)
    .build();
Builder kalıbı ile zorunlu parametreler (url) Builder yapıcısında alınır, opsiyonel parametreler metot zincirleme (method chaining) ile ayarlanır. build() çağrılana kadar nesne oluşturulmaz — tutarsız durum imkansızdır. Sonuçta elde edilen HttpRequest değişmezdir (immutable). With the Builder pattern, required parameters (url) are taken in the Builder constructor, optional parameters are set via method chaining. The object isn't created until build() is called — inconsistent state is impossible. The resulting HttpRequest is immutable.
Pratik İpucu: Builder kalıbı ilk başta daha fazla kod gibi görünse de, opsiyonel parametre sayısı arttıkça karşılığını verir. Lombok'un @Builder ek açıklaması veya IDE refactoring araçlarıyla standart kalıp kodu (boilerplate) otomatik üretilebilir. Kural: 4+ parametre veya aynı tipte 2+ opsiyonel parametre varsa Builder düşünün. Practical Tip: The Builder pattern may seem like more code initially, but it pays off as optional parameters grow. Lombok's @Builder annotation or IDE refactoring tools can auto-generate the boilerplate. Rule of thumb: consider Builder for 4+ parameters or 2+ optional parameters of the same type.
