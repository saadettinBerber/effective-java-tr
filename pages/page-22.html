Bağımlılık enjeksiyonu (dependency injection) olarak bilinen bu pratik, sınıfın esnekliğini (flexibility), tekrar kullanılabilirliğini (reusability) ve test edilebilirliğini (testability) büyük ölçüde artıracaktır.

...framework, such as Dagger [Dagger], Guice [Guice], or Spring [Spring]. The use of these frameworks is beyond the scope of this book, but note that APIs designed for manual dependency injection are trivially adapted for use by these frameworks.

In summary, do not use a singleton or static utility class to implement a class that depends on one or more underlying resources whose behavior affects that of the class, and do not have the class create these resources directly. Instead, pass the resources, or factories to create them, into the constructor (or static factory or builder). This practice, known as dependency injection, will greatly enhance the flexibility, reusability, and testability of a class.

Item 6: Avoid creating unnecessary objects

Çoğu zaman, bir nesneye her ihtiyaç duyulduğunda işlevsel olarak tamamen eşdeğer (functionally equivalent) yeni bir nesne oluşturmak yerine tek bir nesneyi tekrar kullanmak (reuse) daha uygundur. Tekrar kullanım hem daha performanslı (faster) hem de daha şıktır (stylish). Eğer bir nesne değişmezse (immutable) (Madde 17), hiçbir koşulda sorunsuzca tekrar kullanılabilir.

Nelerin asla yapılmaması gerektiğine dair ekstrem bir örnek olarak şu koda bakınız:

It is often appropriate to reuse a single object instead of creating a new functionally equivalent object each time it is needed. Reuse can be both faster and more stylish. An object can always be reused if it is immutable (Item 17).

As an extreme example of what not to do, consider this statement:

String s = new String("bikini"); // BUNU YAPMAYIN! (DON'T DO THIS!)

Bu deyim, her çalıştırıldığında kendine has yepeni bir String örneği (instance) oluşturur ve üstelik buradaki nesne oluşturmaların tamamı tamamen gereksizdir. String yapıcısına parametre olarak gönderilen ("bikini") aslında zaten bir String örneğidir ve yapıcı tarafından oluşturulup belleğe işlenecek bu yeni nesneyle işlevsel olarak birebir aynıdır. Eğer bu kullanım bir döngünün (loop) içinde ya da sıklıkla tetiklenen (invoked) bir metot içinde gerçekleşirse, milyonlarca gereksiz String örneği yaratılmış olur.

Bu metodun gelişmiş sürümü gayet şu şekildedir:

The statement creates a new String instance each time it is executed, and none of those object creations is necessary. The argument to the String constructor ("bikini") is itself a String instance, functionally identical to all of the objects created by the constructor. If this usage occurs in a loop or in a frequently invoked method, millions of String instances can be created needlessly.

The improved version is simply the following:

String s = "bikini";

Bu sürüm, her seferinde yeni bir tane oluşturmak yerine mevcut tekil bir String örneğini kullanır. Ayrıca aynı dize düzdeğerini (string literal) içeren, aynı Sanal Makine (Virtual Machine) üzerinde koşan herhangi bir başka kod varsa, o nesnenin aynen yeniden kullanılacağı kesinkes garanti edilir [JLS, 3.10.5].

İçlerinde hem statik yapıcıların hem de normal kurucuların (constructors) bulunduğu sınıflarda gereksiz nesne oluşturmalarını metot fabrikalarını (Madde 1) kullanarak ortadan kaldırabilirsiniz. Örneklemek gerekirse, fabrika metodu olan Boolean.valueOf(String) metodu, Java 9'da artık kullanımdan kaldırılmış (deprecated) Boolean(String) yapıcısına çok daha fazla tercih edilmelidir. Yapıcı metod çalıştırıldığı her an mecburen yeni bir obje fırlatmak zorundadır, ancak fabrika metodlarının böyle bir sorumluluğu olmadığından bunu pratikte asla yapmazlar. Ayrıca, sadece içeriği aynı olan değişmez nesneleri değil, değişebilir (mutable) ancak değişmeden (sabit) kalacağını bildiğiniz nesneleri de yeniden kullanabilirsiniz.

Bazı nesnelerin yaratılması diğerlerinden çok daha maliyetlidir (expensive). Eğer o böylesi bir "maliyetli nesneye" art arda sürekli ihtiyaç duyacaksanız, onu ileride tekrar kullanmak için tamponda tutmak (cache/önbelleklemek) daha akıllıca olabilir. Ne yazık ki, böyle bir nesneyi ne zaman yarattığınız her zaman aşikâr olmayabilir. Örneğin bir dize dizgesinin geçerli bir Romen rakamı olup olmadığını belirlemek için bir yöntem yazmak çabasına girelim. Bunu yapmanın bilinen en kolay yöntemi düzenli ifadeleri (regular expressions) kullanmaktır:

This version uses a single String instance, rather than creating a new one each time it is executed. Furthermore, it is guaranteed that the object will be reused by any other code running in the same virtual machine that happens to contain the same string literal [JLS, 3.10.5].

You can often avoid creating unnecessary objects by using static factory methods (Item 1) in preference to constructors on immutable classes that provide both. For example, the factory method Boolean.valueOf(String) is preferable to the constructor Boolean(String), which was deprecated in Java 9. The constructor must create a new object each time it’s called, while the factory method is never required to do so and won’t in practice. In addition to reusing immutable objects, you can also reuse mutable objects if you know they won’t be modified.

Some object creations are much more expensive than others. If you’re going to need such an “expensive object” repeatedly, it may be advisable to cache it for reuse. Unfortunately, it’s not always obvious when you’re creating such an object. Suppose you want to write a method to determine whether a string is a valid Roman numeral. Here’s the easiest way to do this using a regular expression:

// Performans devasa derecede iyileştirilebilir! // Performance can be greatly improved! static boolean isRomanNumeral(String s) { return s.matches("^(?=.)M*(C[MD]|D?C{0,3})" + "(X[CL]|L?X{0,3})(I[XV]|V?I{0,3})$"); }

🔍 Kavramlar: 🔍 Concepts:

String Pool (String Havuzu)

Java'da tırnak işareti (literal) ile oluşturulan tüm String değerler (örneğin "bikini") bellekte String Pool adı verilen özel bir alanda saklanır. Program genelinde aynı metne sahip olan tüm referanslar, bellekte bu tekil alanı işaret ederler.

In Java, all String literals (like "bikini") are stored in a special memory area called the String Pool. The JVM optimizes this: any code requiring the same text will always reference the exact same underlying object in the Pool.

✗ new String() Kullanımı (String Pool Atlaması)
// String Pool'daki "bikini" kopyalanır ve HEAP'te zorla yepyeni bir nesne yaratılır. String s1 = new String("bikini"); String s2 = new String("bikini"); System.out.println(s1 == s2); // false! Hafızada fuzuli fazladan 2 ayrı nesne var.
✓ Tırnak (Literal) Kullanımı
String s1 = "bikini"; String s2 = "bikini"; System.out.println(s1 == s2); // true! Havuzdaki tek bir objeyi gösterirler.
💡 Modern Java, derleme anında metin birleştirme operatörlerini ("a" + "b") bile havuzda tekil referans haline getirecek kadar akıllıdır. Mümkün olduğunca manuel new String() yapmaktan kaçının.
💡 The compiler automatically interns identical literals. AVOID using new String("...") in almost every conceivable application code.

Maliyetli (Expensive) Nesne Yaratımları

Birtakım nesneleri üretmek, salt bellek ayırmaktan ibaret değildir; ciddi oranda CPU zamanı çalabilirler (Ör: Veritabanı bağlantıları, XML ayrıştırıcılar, Pattern RegEx çözüleyiciler). Düzenli bir ifadeyi (RegEx) String.matches() aracılığı ile okumak ilk etapta basit görünse de, perde arkasında derleyici bu regex dizesini devasa ve karmaşık bir durumsal geçiş haritası olan sonlu durum makinesine (finite state machine) derler () Pattern.compile()) . Sonrasında ise metot çıkar çıkmaz çöp toplayıcıya terk eder. Değerli nesneyi yaratıp, kullanıp, fırlatıp atmak tam bir "performans cinayetidir".

Some objects aren't just blocks of memory—creating them burns heavy CPU cycles. Common examples include DB connections or Pattern (Regex compilers). A call to String.matches() sounds cheap, but internally it forces the Regex engine to parse the text string and construct a complex finite-state-machine representation, only to throw it away immediately.
