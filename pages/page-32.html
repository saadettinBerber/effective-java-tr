Daha önce söylediğimiz gibi, Room'un temizleyicisi yalnızca bir güvenlik ağı olarak kullanılır. İstemciler tüm Room oluşturmalarını try-with-resources bloklarına sardığında, otomatik temizleme asla gerekli olmayacaktır. Bu uslu (well-behaved) istemci bu davranışı sergiler:

As we said earlier, Room's cleaner is used only as a safety net. If clients surround all Room instantiations in try-with-resource blocks, automatic cleaning will never be required. This well-behaved client demonstrates that behavior:

// Uslu istemci — try-with-resources kullanıyor public class Adult { public static void main(String[] args) { try (Room myRoom = new Room(7)) { System.out.println("Goodbye"); } } }

Beklediğiniz gibi, Adult programını çalıştırdığınızda önce Goodbye, ardından Cleaning room basılır. Peki ya odasını asla temizlemeyen (never cleans its room) bu yaramaz (ill-behaved) program ne olur?

As you'd expect, running the Adult program prints Goodbye, followed by Cleaning room. But what about this ill-behaved program, which never cleans its room?

// Yaramaz istemci — close() çağırmıyor, try-with-resources kullanmıyor public class Teenager { public static void main(String[] args) { new Room(99); System.out.println("Peace out"); } }

Peace out yazılmasını, ardından Cleaning room basılmasını beklemiş olabilirsiniz; ancak benim makinemde Cleaning room asla basılmaz; program doğrudan çıkar. İşte daha önce bahsettiğimiz o öngörülemezlik tam da budur. Cleaner spesifikasyonu şöyle der: "System.exit sırasındaki temizleyici davranışı uygulamaya özgüdür (implementation specific). Temizleme eylemlerinin çağrılıp çağrılmayacağına dair hiçbir garanti verilmez." Spesifikasyon bunu söylemese de, aynı durum normal program çıkışı için de geçerlidir. Benim makinemde, Teenager'ın main metoduna System.gc() satırını eklemek, çıkıştan önce Cleaning room basılması için yeterlidir; ancak sizin makinenizde aynı davranışı göreceğinizin hiçbir garantisi yoktur.

Özetle, Java 9 öncesinde sonlandırıcıları veya temizleyicileri, bir güvenlik ağı olarak ya da kritik olmayan doğal kaynakları (noncritical native resources) sonlandırmak dışında kullanmayın. Ve bunu yapsanız bile, belirsizlik (indeterminacy) ve performans sonuçlarına (performance consequences) dikkat edin.

Madde 9: try-finally Yerine try-with-resources'ı Tercih Edin

Item 9: Prefer try-with-resources to try-finally

Java kütüphaneleri, bir close metodu çağrılarak elle kapatılması gereken birçok kaynak (resource) içerir. Örnekler arasında InputStream, OutputStream ve java.sql.Connection sayılabilir. Kaynakları kapatmak istemciler tarafından sık sık gözden kaçırılır ve bunun tahmin edilebilir korkunç performans sonuçları olur. Bu kaynakların birçoğu güvenlik ağı olarak sonlandırıcılar (finalizers) kullansa da, sonlandırıcılar pek de iyi çalışmazlar (Madde 8).

Tarihsel olarak, bir istisna (exception) veya dönüş (return) karşısında bile bir kaynağın düzgünce kapatılacağını garanti altına almanın en iyi yolu try-finally ifadesiydi:

You might expect it to print Peace out, followed by Cleaning room, but on my machine, it never prints Cleaning room; it just exits. This is the unpredictability we spoke of earlier. The Cleaner spec says, "The behavior of cleaners during System.exit is implementation specific. No guarantees are made relating to whether cleaning actions are invoked or not." While the spec does not say it, the same holds true for normal program exit. On my machine, adding the line System.gc() to Teenager's main method is enough to make it print Cleaning room prior to exit, but there's no guarantee that you'll see the same behavior on your machine.

In summary, don't use cleaners, or in releases prior to Java 9, finalizers, except as a safety net or to terminate noncritical native resources. Even then, beware the indeterminacy and performance consequences.

Item 9: Prefer try-with-resources to try-finally

The Java libraries include many resources that must be closed manually by invoking a close method. Examples include InputStream, OutputStream, and java.sql.Connection. Closing resources is often overlooked by clients, with predictably dire performance consequences. While many of these resources use finalizers as a safety net, finalizers don't work very well (Item 8).

Historically, a try-finally statement was the best way to guarantee that a resource would be closed properly, even in the face of an exception or return:

// try-finally — Artık kaynakları kapatmanın en iyi yolu DEĞİL! // try-finally - No longer the best way to close resources! static String firstLineOfFile(String path) throws IOException { BufferedReader br = new BufferedReader(new FileReader(path)); try { return br.readLine(); } finally { br.close(); } }

🔍 Kavramlar: 🔍 Concepts:

Cleaner Öngörülemezliği

Teenager örneği Cleaner'ların ne kadar güvenilmez olduğunun canlı kanıtıdır. System.exit() çağrıldığında veya normal program çıkışında, temizleme eylemlerinin çalıştırılıp çalıştırılmayacağı tamamen JVM uygulamasına bağlıdır. Bir JVM'de çalışan kod, başka bir JVM'de farklı davranabilir.

The Teenager example is living proof of Cleaner unreliability. On System.exit() or normal program exit, whether cleaning actions run is entirely JVM-implementation-dependent. Code that works on one JVM may behave differently on another.

💡 Güvenlik ağı olarak Cleaner kullanıyorsanız bile, asıl kaynak yönetimini her zaman try-with-resources ile yapın. Cleaner'a güvenmeyin, onu sadece "son çare sigortası" olarak düşünün.

Kaynak Yönetimi (Resource Management)

Java'da kaynak yönetimi paradigmaları tarihsel olarak evrilmiştir:

1. Elle yönetim (Java 1-6): try-finally ile close() çağrısı. Hatalara açık, iç içe geçmiş (nested) bloklarla çirkin kod.

2. try-with-resources (Java 7+): AutoCloseable arayüzü ile otomatik kapatma. Kısa, temiz, hata güvenli.

3. Cleaner/Finalizer: Yalnızca güvenlik ağı. Asla birincil kaynak yönetimi olarak kullanılmamalı.

Resource management paradigms in Java have evolved historically:

1. Manual (Java 1-6): try-finally with explicit close(). Error-prone, ugly with nested blocks.

2. try-with-resources (Java 7+): Automatic closing via AutoCloseable. Clean, concise, error-safe.

3. Cleaner/Finalizer: Safety net only. Never use as primary resource management.
