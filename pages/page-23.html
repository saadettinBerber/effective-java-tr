Chapter 2 — Item 6: Gereksiz nesneler yaratmaktan kaçının / Avoid creating unnecessary objects
↩ Önceki sayfadan devam — Madde 6 Regular Expressions performansı

Bu uygulamanın (implementation) asıl sorunu, String.matches metoduna dayanmasıdır. Bir dizenin belli bir düzenli ifadeyle (regular expression) eşleşip eşleşmediğini kontrol etmek için String.matches kullanmak en kolay yol olsa da, performansın kritik olduğu durumlarda tekrarlı olarak kullanılmaya uygun değildir. Sorun şudur ki; String sınıfı kendi iç yapısında (internally), sadece bir kez kullanılmak üzere bir Pattern örneği oluşturur, işini yapar ve sonrasında bu nesne doğrudan çöp (garbage collection) haline gelir. Düzenli ifadeyi bir sonlu durum makinesine (finite state machine) derlemek gerektiğinden ötürü Pattern örneği yaratmak oldukça maliyetli bir iştir.

Performansı iyileştirmek için, sınıf ilklendirmesinin (class initialization) bir parçası olarak düzenli ifadeyi açıkça derleyip (compile edip) ömrü boyunca değişmeyecek bir (immutable) Pattern örneği olarak çıkarın. Bunu tamponlayın (önbellekleyin) ve her isRomanNumeral metot çağrısında aynı örneği baştan yaratmak yerine tekrar tekrar onu çağırıp kullanın:

The problem with this implementation is that it relies on the String.matches method. While String.matches is the easiest way to check if a string matches a regular expression, it’s not suitable for repeated use in performance-critical situations. The problem is that it internally creates a Pattern instance for the regular expression and uses it only once, after which it becomes eligible for garbage collection. Creating a Pattern instance is expensive because it requires compiling the regular expression into a finite state machine.

To improve the performance, explicitly compile the regular expression into a Pattern instance (which is immutable) as part of class initialization, cache it, and reuse the same instance for every invocation of the isRomanNumeral method:

// Performans artışı için maliyetli nesneyi yeniden kullanmak // Reusing expensive object for improved performance public class RomanNumerals { private static final Pattern ROMAN = Pattern.compile( "^(?=.)M*(C[MD]|D?C{0,3})" + "(X[CL]|L?X{0,3})(I[XV]|V?I{0,3})$"); static boolean isRomanNumeral(String s) { return ROMAN.matcher(s).matches(); } }

Geliştirdiğimiz isRomanNumeral versiyonu, şayet sıklıkla tetiklenirse, hatrı sayılır performans kazanımları (significant performance gains) sağlar. Kendi makinemde, 8 karakter uzunluğunda bir dize üzerinden test yaptığımda orijinal sürüm 1.1 µs çalışma süresi talep ederken, gelişmiş (önbelleklenmiş Pattern modeli) sürüm sadece 0.17 µs almaktadır; ki bu da asıl koda kıyasla ortalama 6.5 kat daha hızlı demektir. Sadece performans iyileştirilmiş olmakla kalmamış; tartışmaya açık olmakla birlikte aynı zamanda daha net (clarity) hale gelmiştir. Normalde gözle görülmez olan Pattern yapısına final bir özellik (isim) biçip sabitlendirmek, bize kod kalitesi sağlamıştır ki bu "ROMAN" ismiyle değişkeni okumak doğrudan düzenli ifade silsilesini okumaktan (regular expression) çok ama çok daha okunabilirdir (readable).

Eğer ki yeni isRomanNumeral yöntemini içeren sınıf belleğe yüklenip ilklendirilir (initialized) ancak içindeki bu metot asla çağrılmazsa (invoked), ROMAN nesnesi bellekte fuzuli yere yer kaplayıp ilklendirilmiş (needlessly initialized) bir nesne olarak yatacaktır. Bunu engellemek ve isRomanNumeral ilk defa çağrılana dek bu ilklendirmeyi ertelemek yani tembel ilklendirme (lazy initialization) kullanmak (Madde 83) elbette mümkündür ama önerilmez. Hatta tembel (lazy) yaklaşımlarla çok sık karşılaşıldığı üzere; bu çözüm performansa gözle görülür herhangi bir tatmin veya iyileşme (measurable improvement) sunmayacağı gibi sadece kod mimarisini işin içinden çıkması daha da zor, karmaşık bir (complicate) yapıya doğru sürükler (Madde 67).

Bir nesnenin değişmez (immutable) olduğu durumlarda, güvenle yeniden kullanılabileceği çok belirgindir; ancak nesneyi yeniden kullanmanın tamamen o kadar da aşikâr olmadığı, hatta biraz sezgisel olmayan bazı farklı senaryolar da mevcuttur. Bunun örneklerinden biri olarak, gösterimler (views) olarak da bilinen bağdaştırıcıları (adapters) [Gamma95] düşünebiliriz. Bir adaptör, asıl işi kendisine destek olan (backing object) gerçek bir nesneye devrederek çalışan arayüz parçalarıdır. Adaptörler, kendilerine destek veren o asıl sınıfın sahip olduğu durumların (state) ötesinde farklı veya özel hiçbir durum ihtiva etmedikleri için, bir objenin üzerine uyarlanacak tek asıl adaptör türünden yalnızca bir örneğe (instance) sahip olmak çoğu zaman ziyadesiyle yeterlidir.

Örneğin, Map arayüzünün (interface) keySet metodu, haritanın barındırdığı tüm anahtarlardan meydana gelen bir Set görünümü (Set view) döndürür. Duruma safça bakarsak, sanırsınız ki keySet()'e yapılan her metot çağrısının her defasında gıcır gıcır yeni bir Set objesi yaratacağı var sayılır, ancak belirli bir Map objesinin üzerine yapılan tüm keySet() çağrıları gayetle de aynı Set görünüm objesini döndürür veya döndürebilir. Çoğu kez geriye döndürülen Set özellikleri bakımından değişebilir karakterdedir (mutable) olmasına rağmen, sonuç olarak geri dönen tüm Set objeleri aynı asıl Map verisinin sillesine dayandığından dolayı geri getirilenler (returned) fonksiyonel olarak hep özdeştir ve birebir (identical) aynılardır. Geri dönen tek bir Map elemanı değişirse tüm gösterimler de doğrudan o referansı göreceklerinden tüm gösterimler de bir bakıma anında değişmiş olurlar. keySet adaptörü kullanılarak birden fazla set gösterim örneğini ayakta tutmak zararsızmış gibi gözükse bile son derece gereksizdir ve hiç kimseye yarar veya ekstra fayda (benefits) getirmez.

Gereksiz yere nesneler yaratmanın yollarından bir diğeri ise otomatik boks etme (autoboxing) işlemidir. Bu işlem, programcının klasik Java ilkel tipleriyle (primitive types) Java nesneye dönüştürülmüş tiplerini (boxed primitive types) iç içe özgürce harmanlayıp kullanabilmesini, gerekli noktalarda arka planda sinsi paketleme ve ayıklama işlemleri yaparak... The improved version of isRomanNumeral provides significant performance gains if invoked frequently. On my machine, the original version takes 1.1 µs on an 8-character input string, while the improved version takes 0.17 µs, which is 6.5 times faster. Not only is the performance improved, but arguably, so is clarity. Making a static final field for the otherwise invisible Pattern instance allows us to give it a name, which is far more readable than the regular expression itself.

If the class containing the improved version of the isRomanNumeral method is initialized but the method is never invoked, the field ROMAN will be initialized needlessly. It would be possible to eliminate the initialization by lazily initializing the field (Item 83) the first time the isRomanNumeral method is invoked, but this is not recommended. As is often the case with lazy initialization, it would complicate the implementation with no measurable performance improvement (Item 67).

When an object is immutable, it is obvious it can be reused safely, but there are other situations where it is far less obvious, even counterintuitive. Consider the case of adapters [Gamma95], also known as views. An adapter is an object that delegates to a backing object, providing an alternative interface. Because an adapter has no state beyond that of its backing object, there’s no need to create more than one instance of a given adapter to a given object.

For example, the keySet method of the Map interface returns a Set view of the Map object, consisting of all the keys in the map. Naively, it would seem that every call to keySet would have to create a new Set instance, but every call to keySet on a given Map object may return the same Set instance. Although the returned Set instance is typically mutable, all of the returned objects are functionally identical: when one of the returned objects changes, so do all the others, because they’re all backed by the same Map instance. While it is largely harmless to create multiple instances of the keySet view object, it is unnecessary and has no benefits.

Pattern Önbellekleme / Regular Expression Caching

Herhangi bir metinsel ifadenin şablona uyup uymadığını kontrol ettiğimiz String.matches(regex) komutu arka planda Pattern.compile(regex) işletir. Fakat bu iş derleme (compile) işlemi içerdiğinden pahalıdır. Eğer regex ifadeniz statikse bunu bir sabite bağlayın.

Because regular expressions require compiling the text-based regex into a state machine before they can be ran, they are extremely heavy CPU-wise. Invoking String.matches repeatedly literally forces the app to recompile the regex every time.

💡 Regex kurallarınızı private static final Pattern sabiti olarak sınıfa bir kere compile olarak gömmek CPU yükünüzü çoğu senaryoda olağanüstü miktarda azaltacaktır.

Adapter & View (Gösterim) Prensibi

Kendi hafızasına/durumuna sahip bir işleyici (adapter) yoksa ve sadece diğer var olan devasa nesnenin kılıfı gibiyse (örn Java Collection Framework: Map.keySet(), Arrays.asList() vs), bu nesnelerin her çağrılışında yepyeni objee kopyaları fırlatmasına gerek yoktur.

Adapters (Views) do not carry state. They literally just translate input and forward it to the main collection (the backing map, for example). Hence, map.keySet() doesn't build a new list of keys, it simply hands you a reference proxy to the keys in the map.

Map<String, Integer> scores = new HashMap<>(); scores.put("Ali", 90); // Map içerisinden view alındı Set<String> keys1 = scores.keySet(); Set<String> keys2 = scores.keySet(); // Aslında ikisi de tam olarak AYNI BACKING MAP nesnesini kullanır. System.out.println(keys1 == keys2); // true olmasa bile (JVM impl bazında), ikisi de birebir map datasına bakar.

Autoboxing Sinsiliği Nedir?

C, C++ gibi dillerde int bir direkt donanımsal 32-bit sayıdır. Ama Java aynı zamanda her şeyi obje olarak kullanan koleksiyonlara sahip olduğu için, ona da obje formunda (Wrapper/Boks edilmiş form) olan Integer (Büyük I ile) sınıfını hediye etmiştir.

Java 5 ile gelen Autoboxing özelliği siz primitive (int) ile Wrapper objesini (Integer) birbirine denk eşlediğinizde kaputun altında birini gizlice diğerine dönüştürür. Ancak obje dönüştürme performanstan feda etmek anlamına gelir, özellikle döngüler (loops) içerisinde.

Autoboxing is the automatic conversion that the Java compiler makes between the primitive types and their corresponding object wrapper classes. For example, converting an int to an Integer. If you misuse this inside a loop, you end up silently creating thousands of Wrapper instance objects for basic numbers.
