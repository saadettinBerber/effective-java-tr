Chapter 2 — Item 4: private yapıcı metotlarla örneklenememeyi garanti altına alın / Enforce noninstantiability with a private constructor
↩ Önceki sayfadan devam — Madde 4'e giriş.

...insanlar bu yardımcı (utility) sınıfları nesne yönelimli düşünmekten kaçmak için suistimal ettikleri için kötü bir şöhrete sahip olsalar da, asıl kullanım amaçları geçerlidir. Tıpkı java.lang.Math veya java.util.Arrays gibi birbiriyle ilişkili metotları ilkel tipler (primitive values) üzerinde veya diziler üzerinde gruplandırmak için kullanılabilirler. Ya da java.util.Collections gibi, belirli bir arayüzü uygulayan nesneler için fabrika metotları (Madde 1) da dahil olmak üzere statik metotları gruplandırmak için kullanılabilirler. (Java 8'den itibaren, değişiklik hakkı sizdeyse bu tür metotları doğrudan arayüzün (interface) içine koyabilirsiniz.) Son olarak bu tür sınıflar, bir sınıf final olduğunda, yani ondan alt sınıf türetemediğinizde (subclassing yapılamıyorsa), o sınıf üzerindeki metotları gruplandırmak için kullanılabilir.

Bu tür yardımcı sınıflar örneklenmek (instantiated) için tasarlanmamıştır: bir örnek (instance) mantıksız olurdu. Ancak, açıkça belirtilmiş bir yapıcı metot (explicit constructor) bulunmadığı durumlarda, derleyici herkesin erişimine açık ve parametresiz varsayılan bir yapıcı metot (public default constructor) sağlar. Bir kullanıcı için, bu yapıcının diğer nesnelerin yapıcılarından ayırt edilmesi imkânsızdır. Piyasaya sürülmüş bazı API'lerde, kazara örneklenmeye müsait durumda bırakılmış (unintentionally instantiable) sınıflara rastlamak hiç de nadir değildir.

Bir sınıfı soyut (abstract) yaparak örneklenmesini (instantiability) engellemeye çalışmak işe yaramaz. Bu sınıfın alt sınıfı oluşturulabilir ve alt sınıf örneklenebilir. Üstelik bu durum, sınıfın bilakis kalıtım (inheritance) yoluyla kullanılmak üzere tasarlandığı yanılgısına düşürür (Madde 19). Ancak, örneklenememeyi (noninstantiability) garanti altına almanın çok basit bir deyimi (idiom) vardır. Derleyici, varsayılan bir yapıcı metodu sadece eğer sınıf içinde hiç açık yapıcı (explicit constructor) yoksa üretir. O halde, bir sınıfın içine private bir yapıcı metot eklendiğinde o sınıf örneklenemez hale gelir:

...people abuse them to avoid thinking in terms of objects, but they do have valid uses. They can be used to group related methods on primitive values or arrays, in the manner of java.lang.Math or java.util.Arrays. They can also be used to group static methods, including factories (Item 1), for objects that implement some interface, in the manner of java.util.Collections. (As of Java 8, you can also put such methods in the interface, assuming it’s yours to modify.) Lastly, such classes can be used to group methods on a final class, since you can’t put them in a subclass.

Such utility classes were not designed to be instantiated: an instance would be nonsensical. In the absence of explicit constructors, however, the compiler provides a public, parameterless default constructor. To a user, this constructor is indistinguishable from any other. It is not uncommon to see unintentionally instantiable classes in published APIs.

Attempting to enforce noninstantiability by making a class abstract does not work. The class can be subclassed and the subclass instantiated. Furthermore, it misleads the user into thinking the class was designed for inheritance (Item 19). There is, however, a simple idiom to ensure noninstantiability. A default constructor is generated only if a class contains no explicit constructors, so a class can be made noninstantiable by including a private constructor:

// Örneklenemeyen yardımcı sınıf (Noninstantiable utility class) public class UtilityClass { // Örneklenmeyi engellemek için varsayılan yapıcıyı gizle private UtilityClass() { throw new AssertionError(); } ... // Geri kalanı kırpıldı (Remainder omitted) }

Açık (explicit) yapıcı metot private olduğu için, sınıf dışından erişilemez. İçerisine yazılan AssertionError mutlak olarak zorunlu değildir, ancak yine de yapıcı metot sınıf içinden bile olsa yanlışlıkla çağrıldığında ekstra bir sigorta görevi görür. Bu, sınıfın her koşulda asla örneklendirilmeyeceğini (instantiated) garanti eder. Ancak bu deyim biraz sezgilere aykırıdır çünkü bilerek sadece hiç çağrılmamasını sağlamak adına bir yapıcı metot verilmiştir. Bu nedenle önceki örnekteki gibi bir açıklama satırı eklemek her zaman akıllıca olur.

Bu deyimin (idiom) bir yan etkisi olarak aynı zamanda sınıfın alt sınıf oluşturulması da engellenir (subclassed). Bütün yapıcı metotlar, açık (explicit) veya kapalı (implicit) olarak mutlaka üst sınıfın yapıcı metotlarından birini çağırmak (invoke) zorundadır. Ancak bu alt sınıfın çağırabileceği erişilebilir hiçbir üst sınıf yapıcısı bulunamaz.

Because the explicit constructor is private, it is inaccessible outside the class. The AssertionError isn’t strictly required, but it provides insurance in case the constructor is accidentally invoked from within the class. It guarantees the class will never be instantiated under any circumstances. This idiom is mildly counterintuitive because the constructor is provided expressly so that it cannot be invoked. It is therefore wise to include a comment, as shown earlier.

As a side effect, this idiom also prevents the class from being subclassed. All constructors must invoke a superclass constructor, explicitly or implicitly, and a subclass would have no accessible superclass constructor to invoke.

Utility Class (Yardımcı Sınıf) / Utility Class

Utility sınıfları, içinde nesne durumu tutmaya (state) gerek olmayan, yalnızca genel amaçlı static metot veya sabit değerler (constants) barındıran sınıflardır. Hiçbir zaman new komutuyla oluşturulmamalıdırlar. Eğer kurucularını gizlemezseniz API'nizi kullanan kişiler, hata yaparak onlardan nesne üretmeye çalışabilir.

Utility classes are classes that don't need any object state and only contain general-purpose static methods or constants. They should never be instantiated with the new keyword. If you don't hide their constructors, API consumers might instantiate them by mistake.

✗ KÖTÜ — İstenmeden yaratılabilen yararcı sınıf
public class StringUtils { // Derleyici buraya otomatik public StringUtils() koyar. public static String capitalize(String text) { ... } } // İstemci yanlışlıkla yapabilir: StringUtils utils = new StringUtils(); utils.capitalize("hello");
✓ İYİ — Örneklenemez (Noninstantiable) Sınıf
public final class StringUtils { private StringUtils() { throw new AssertionError("Örneklenemez yardımcı sınıf!"); } public static String capitalize(String text) { ... } } // İstemci doğrudan sınıfı kullanmak zorundadır: StringUtils.capitalize("hello");
💡 Aynı zamanda, Java 8 ile birlikte eğer yardımcı kodlarınız belli bir konsept veya interface etrafında toplanıyorsa, utility class yerine interface içersine static metotlar (static interface methods) deklare edebileceğinizi unutmayın.
💡 Also keep in mind that since Java 8, if your utility methods revolve around an interface concept, you can place them directly as static methods inside that interface instead of making a new utility class.

Abstract vs Private Constructor

Bazı geliştiriciler bir sınıfın örneklenmesini engellemek için sınıfı abstract (soyut) işaretlemenin yeterli olacağını düşünür. Ancak bu büyük bir hatadır.

Some developers assume that marking a class as abstract is sufficient to prevent it from being instantiated. However, this is a big mistake.

✗ KÖTÜ — Abstract kullanıldığında alt sınıfı yapılabilir
public abstract class DateUtils { public static String format(Date d) { ... } } // Kötü niyetli/bilgisiz istemci abstract'ı atlatır: public class MyDateUtils extends DateUtils { } // Artık örnek yaratılabilir! MyDateUtils utils = new MyDateUtils();

Ayrıca abstract sınıflar kullanıcılara "bu sınıf kalıtım için (inheritance) tasarlanmıştır, eksiklerini tamamlayıp alt sınıf oluşturmalısın" şeklinde yanlış bir mesaj verir. Private constructor deyimi (idiom) ise hiçbir constructor'ın çağrılamamasını güvence altına aldığı için otomatik olarak o sınıfın abstract veya subclass olmasını tamamen önler.
