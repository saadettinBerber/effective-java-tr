Item 2: Consider a builder when faced with many constructor parameters Madde 2: Çok Sayıda Yapıcı Parametresiyle Karşılaşınca Builder Kullanmayı Düşünün

← Bu sayfa, önceki sayfada başlayan NutritionFacts teleskopik yapıcı (telescoping constructor) örneğinin devamıdır. ← This page continues the NutritionFacts telescoping constructor example from the previous page.

Kod — NutritionFacts Teleskopik Yapıcı (devamı) Code — NutritionFacts Telescoping Constructor (continued) 
public class NutritionFacts {
    private final int servingSize;   // (mL)              zorunlu
    private final int servings;      // (per container)   zorunlu
    private final int calories;      // (per serving)     opsiyonel
    private final int fat;           // (g/serving)       opsiyonel
    private final int sodium;        // (mg/serving)      opsiyonel
    private final int carbohydrate;  // (g/serving)       opsiyonel

    public NutritionFacts(int servingSize, int servings) {
        this(servingSize, servings, 0);
    }
    public NutritionFacts(int servingSize, int servings, int calories) {
        this(servingSize, servings, calories, 0);
    }
    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat) {
        this(servingSize, servings, calories, fat, 0);
    }
    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat, int sodium) {
        this(servingSize, servings, calories, fat, sodium, 0);
    }
    public NutritionFacts(int servingSize, int servings,
                           int calories, int fat, int sodium,
                           int carbohydrate) {
        this.servingSize  = servingSize;
        this.servings     = servings;
        this.calories     = calories;
        this.fat          = fat;
        this.sodium       = sodium;
        this.carbohydrate = carbohydrate;
    }
}

Bir örnek oluşturmak istediğinizde, ayarlamak istediğiniz tüm parametreleri içeren en kısa parametre listesine sahip yapıcıyı kullanırsınız:

When you want to create an instance, you use the constructor with the shortest parameter list containing all the parameters you want to set: 

NutritionFacts cocaCola =
    new NutritionFacts(240, 8, 100, 0, 35, 27);

Genellikle bu yapıcı çağrısı, ayarlamak istemediğiniz ama yine de değer geçmek zorunda kaldığınız çok sayıda parametre içerir. Bu örnekte fat için 0 değerini geçtik. "Yalnızca" altı parametre olduğunda bu durum o kadar da kötü görünmeyebilir; ancak parametre sayısı arttıkça işler hızla kontrolden çıkar.

Typically this constructor invocation will require many parameters that you don't want to set, but you're forced to pass a value for them anyway. In this case, we passed a value of 0 for fat. With "only" six parameters this may not seem so bad, but it quickly gets out of hand as the number of parameters increases.

Kısaca ifade edilirse: teleskopik yapıcı kalıbı (telescoping constructor pattern) işe yarar; ancak çok sayıda parametre olduğunda istemci kodunu yazmak son derece güçtür ve okumak daha da zordur.

In short, the telescoping constructor pattern works, but it is hard to write client code when there are many parameters, and harder still to read it.

Kodu okuyan kişi bu değerlerin ne anlama geldiğini merak eder ve anlamak için parametreleri dikkatlice saymak zorunda kalır…

The reader is left wondering what all those values mean and must carefully count parameters to find out…

Zorla Geçilen Parametre Sorunu Forced Parameter Problem
Telescoping Constructor — Unwanted Zero/Null Values
Teleskopik yapıcılarda, ayarlamak istemediğiniz parametreler için bile değer geçmek zorundasınızdır. Bu genellikle anlamsız 0, false veya null değerlerin kod içine gömülmesine yol açar; hem okunabilirliği düşürür hem de mantık hatalarına davetiye çıkarır. With telescoping constructors, you're forced to pass values even for parameters you don't need. This leads to meaningless 0, false, or null values being embedded in the code, reducing readability and inviting logic errors.
Kötü Örnek (Before)Bad Example (Before)
public class HttpRequest {
    private final String url;        // zorunlu
    private final String method;     // zorunlu
    private final String body;       // opsiyonel
    private final int    timeout;    // opsiyonel
    private final boolean followRedirects; // opsiyonel

    public HttpRequest(String url, String method,
                        String body, int timeout,
                        boolean followRedirects) { ... }
}

// Sadece timeout istiyorum, body ve followRedirects yok
new HttpRequest("https://api.ornek.com", "GET",
               null, 5000, false); // null ve false anlamsız
Okuyucu 4. parametrenin null olduğunu saymadan anlayamaz. Bu tür hatalar sürüme girme riski taşır. A reader can't tell the 4th parameter is null without counting. This kind of error can slip into production.
İyi Örnek (After)Good Example (After)
// Builder ile sadece istenen parametreler
new HttpRequest.Builder("https://api.ornek.com", "GET")
    .timeout(5000)
    .build(); // body ve followRedirects varsayılan değerde
Yalnızca istenen parametre belirtildi. Gereksiz değer yok, kod kendi kendini açıklıyor. Only the needed parameter is specified. No unnecessary values — the code is self-documenting.
Pratik İpucu: Yapıcı çağrısında null, 0 veya false gibi "boş" değerlerin sayısı ikiden fazlaysa, Builder kalıbına geçme zamanı gelmiştir. Practical Tip: If a constructor call has more than two "empty" values like null, 0, or false, it's time to switch to the Builder pattern.
Teleskopik Yapıcının Ölçeklenme Sorunu Telescoping Constructor Scaling Problem
Why Telescoping Constructors Don't Scale
Her yeni opsiyonel parametre, yazmanız gereken yapıcı sayısını artırır. N opsiyonel parametre için farklı kombinasyonları desteklemek adına çok sayıda yapıcıya ihtiyaç duyulabilir — hem yazması hem bakımı hem de anlaşılması giderek zorlaşır. Each new optional parameter increases the number of constructors you need to write. Supporting different combinations for N optional parameters can require many constructors — writing, maintaining, and understanding them becomes progressively harder.
Kötü Örnek (Before)Bad Example (Before)
// 3 opsiyonel boolean → her kombinasyon için ayrı yapıcı
public class ReportConfig {
    private final String title;
    private final boolean header, footer, pageNums;

    public ReportConfig(String t) { this(t,false,false,false); }
    public ReportConfig(String t, boolean h) { this(t,h,false,false); }
    public ReportConfig(String t, boolean h, boolean f) { this(t,h,f,false); }
    public ReportConfig(String t, boolean h, boolean f, boolean p) {
        title=t; header=h; footer=f; pageNums=p;
    }
    // "header=true, footer=false, pageNums=true" kombinasyonu yok!
}
Parametreler sıralı olduğu için her kombinasyon desteklenemez. "Başlık ve sayfa numarası, alt bilgi yok" kombinasyonu için uygun yapıcı bulunmaz. Because parameters are positional, not all combinations can be supported. There's no constructor for "header and page numbers but no footer."
İyi Örnek (After)Good Example (After)
public class ReportConfig {
    private final String title;
    private final boolean header, footer, pageNums;

    public static class Builder {
        private final String title;
        private boolean header=false, footer=false, pageNums=false;

        public Builder(String title) { this.title = title; }
        public Builder header()   { header=true;   return this; }
        public Builder footer()   { footer=true;   return this; }
        public Builder pageNums(){ pageNums=true; return this; }
        public ReportConfig build() { return new ReportConfig(this); }
    }
    private ReportConfig(Builder b) {
        title=b.title; header=b.header; footer=b.footer; pageNums=b.pageNums;
    }
}

// İstenen kombinasyon — header ve pageNums, footer yok
ReportConfig cfg = new ReportConfig.Builder("Yıllık Rapor")
    .header().pageNums().build();
Her kombinasyon mümkün. Yeni bir özellik eklemek Builder'a tek metot eklemek demektir — mevcut kullanımlar bozulmaz. Every combination is possible. Adding a new feature means adding one method to Builder — existing usage is unaffected.
Pratik İpucu: Opsiyonel parametre sayısı 3'ü geçtiğinde veya parametreler birbirinden bağımsız kombinasyonlar oluşturabildiğinde Builder kalıbını tercih edin. Lombok'un @Builder ek açıklaması standart kalıp kodunu otomatik üretir. Practical Tip: When optional parameters exceed 3, or when they can form independent combinations, prefer the Builder pattern. Lombok's @Builder annotation auto-generates the boilerplate.
