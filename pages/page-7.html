Item 1: Consider static factory methods instead of constructors Madde 1: Yapıcı Metot Yerine Statik Fabrika Metotlarını Düşünün

Örneğin, Koleksiyonlar Çerçevesi'ndeki (Collections Framework) kolaylık uygulama sınıflarından herhangi birini alt sınıflamak (subclass) mümkün değildir. Bu durum tartışmalı bir şekilde kılık değiştirmiş bir nimet olabilir, çünkü programcıları kalıtım (inheritance) yerine bileşim (composition) kullanmaya teşvik eder (Madde 18) ve değişmez tipler (immutable types) için gereklidir (Madde 17).

For example, it is impossible to subclass any of the convenience implementation classes in the Collections Framework. Arguably this can be a blessing in disguise because it encourages programmers to use composition instead of inheritance (Item 18), and is required for immutable types (Item 17).

Statik fabrika metotlarının ikinci eksikliği, programcıların onları bulmakta zorlanmasıdır. API belgelerinde yapıcı metotların (constructors) öne çıktığı gibi öne çıkmazlar, bu yüzden yapıcı metotlar yerine statik fabrika metotları sunan bir sınıfın nasıl örnekleneceğini (instantiate) bulmak zor olabilir. Javadoc aracı belki bir gün statik fabrika metotlarına dikkat çekecektir. Bu arada, sınıf veya arayüz belgelerinde statik fabrikalara dikkat çekerek ve yaygın adlandırma kurallarına uyarak bu sorunu azaltabilirsiniz. İşte statik fabrika metotları için yaygın kullanılan isimlerden bazıları; bu liste kapsamlı olmaktan uzaktır:

A second shortcoming of static factory methods is that they are hard for programmers to find. They do not stand out in API documentation in the way that constructors do, so it can be difficult to figure out how to instantiate a class that provides static factory methods instead of constructors. The Javadoc tool may someday draw attention to static factory methods. In the meantime, you can reduce this problem by drawing attention to static factories in class or interface documentation and by adhering to common naming conventions. Here are some common names for static factory methods. This list is far from exhaustive:

from

Tek bir parametre alan ve bu tipin karşılık gelen örneğini döndüren bir tip dönüştürme metodu (type-conversion method). Örnek:

A type-conversion method that takes a single parameter and returns a corresponding instance of this type, for example: 

Date d = Date.from(instant);
of

Birden fazla parametre alan ve bunları birleştiren bir tipin örneğini döndüren bir toplama metodu (aggregation method). Örnek:

An aggregation method that takes multiple parameters and returns an instance of this type that incorporates them, for example: 

Set<Rank> faceCards = EnumSet.of(JACK, QUEEN, KING);
valueOf

from ve of'un daha ayrıntılı bir alternatifi. Örnek:

A more verbose alternative to from and of, for example: 

BigInteger prime = BigInteger.valueOf(Integer.MAX_VALUE);
instance veya getInstance

Parametreleri (varsa) tarafından tanımlanan bir örneği döndürür, ancak aynı değere sahip olduğu söylenemez. Örnek:

Returns an instance that is described by its parameters (if any) but cannot be said to have the same value, for example: 

StackWalker luke = StackWalker.getInstance(options);
create veya newInstance

instance veya getInstance gibidir, ancak metot her çağrıda yeni bir örnek döndürdüğünü garanti eder. Örnek:

Like instance or getInstance, except that the method guarantees that each call returns a new instance, for example: 

Object newArray = Array.newInstance(classObject, arrayLen);
getType

getInstance gibidir, ancak fabrika metodu farklı bir sınıftaysa kullanılır. Type, fabrika metodu tarafından döndürülen nesnenin tipidir. Örnek:

Like getInstance, but used if the factory method is in a different class. Type is the type of object returned by the factory method, for example: 

FileStore fs = Files.getFileStore(path);

Bileşim vs. Kalıtım Composition over Inheritance
Composition over Inheritance
Kalıtım (inheritance) yerine bileşim (composition) tercih etmek, nesne yönelimli programlamanın temel ilkelerinden biridir. Kalıtım sıkı bağımlılık (tight coupling) yaratır: üst sınıf değiştiğinde alt sınıflar kırılabilir. Bileşim ise bir nesneyi başka bir nesnenin içinde kullanarak aynı işlevselliği daha esnek bir şekilde sağlar. Statik fabrika metotları alt sınıflamayı engelleyerek programcıları dolaylı olarak bileşimi tercih etmeye yönlendirir. Preferring composition over inheritance is a core principle of object-oriented programming. Inheritance creates tight coupling: subclasses can break when the superclass changes. Composition achieves the same functionality more flexibly by using one object inside another. Static factory methods, by preventing subclassing, indirectly guide programmers toward preferring composition.
Kötü Örnek (Before) Bad Example (Before) 
// Kalıtım ile genişletme — kırılgan tasarım
public class LoggingList<E>
        extends ArrayList<E> {

    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
        // BUG: addAll dahili olarak add'ı çağırır
        // sayaç 2 kat artar!
    }
}
ArrayList'i kalıtım yoluyla genişletiyoruz. Ancak addAll dahili olarak add'ı çağırdığı için sayaç yanlış artıyor. Üst sınıfın iç uygulamasına bağımlıyız — uygulama değişirse kodumuz kırılır. We extend ArrayList via inheritance. But since addAll internally calls add, the counter increments incorrectly. We depend on the superclass's internal implementation — if it changes, our code breaks.
İyi Örnek (After) Good Example (After) 
// Bileşim ile sarmalama — sağlam tasarım
public class LoggingList<E>
        implements List<E> {

    private final List<E> delegate;
    private int addCount = 0;

    public LoggingList(List<E> delegate) {
        this.delegate = delegate;
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return delegate.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return delegate.addAll(c);
        // Doğru! delegate.addAll kendi add'ını çağırır,
        // bizim add'ımızı değil.
    }
    // ... diğer List metotları delegate'e yönlendirilir
}
Kalıtım yerine bileşim kullanıyoruz: List arayüzünü uygulayıp iç bir delegate nesnesine yönlendiriyoruz. addAll artık delegenin kendi add'ını çağırır, bizimkini değil. Üst sınıfın iç uygulamasından bağımsızız. We use composition instead of inheritance: we implement the List interface and forward to an internal delegate. addAll now calls the delegate's own add, not ours. We're independent of the superclass's internal implementation.
Pratik İpucu: "Bu sınıf gerçekten bir X midir?" sorusunu sorun. Eğer cevap "hayır, X'in davranışını kullanmak istiyor" ise kalıtım yerine bileşimi tercih edin. Guava'nın ForwardingList, ForwardingSet gibi sınıfları sarmalama yazmayı kolaylaştırır. Practical Tip: Ask "Is this class truly an X?" If the answer is "no, it wants to use X's behavior," prefer composition over inheritance. Guava's ForwardingList, ForwardingSet etc. make writing wrappers easy.
Fabrika Metodu Adlandırma Kuralları Factory Method Naming Conventions
Static Factory Method Naming Conventions
Statik fabrika metotları yapıcı metotlar gibi API belgelerinde otomatik öne çıkmaz. Bu nedenle iyi bilinen adlandırma kurallarına uymak, diğer geliştiricilerin API'nizi keşfetmesini kolaylaştırır. Her adlandırma kuralı farklı bir amaca hizmet eder: from (tip dönüşümü), of (toplama), valueOf (ayrıntılı dönüşüm), getInstance (paylaşılabilir), newInstance (her zaman yeni), getType (farklı sınıftan). Static factory methods don't automatically stand out in API docs like constructors do. Following well-known naming conventions makes it easier for other developers to discover your API. Each convention serves a different purpose: from (type conversion), of (aggregation), valueOf (verbose conversion), getInstance (shareable), newInstance (always new), getType (from different class).
Kötü Örnek (Before) Bad Example (Before) 
// Tutarsız ve kafa karıştıran adlandırma
public class Color {
    public static Color make(int r, int g, int b) { ... }
    public static Color build(String hex) { ... }
    public static Color getColor(int rgb) { ... }
    public static Color construct(float[] hsb) { ... }
}
Dört farklı fabrika metodu dört farklı fiil kullanıyor: make, build, getColor, construct. Hiçbiri standart Java adlandırma kurallarına uymuyor. Geliştirici Javadoc'a bakmadan hangi metodu kullanacağını tahmin edemez. Four factory methods use four different verbs: make, build, getColor, construct. None follows standard Java naming conventions. A developer can't guess which method to use without reading the Javadoc.
İyi Örnek (After) Good Example (After) 
// Standart adlandırma kurallarına uygun
public class Color {
    // of — birden fazla parametre, toplama
    public static Color of(int r, int g, int b) { ... }

    // from — tek parametre, tip dönüşümü
    public static Color from(String hex) { ... }

    // valueOf — ayrıntılı dönüşüm
    public static Color valueOf(int rgb) { ... }

    // from — tek parametre, farklı tip
    public static Color from(float[] hsb) { ... }
}
Her metot standart kurallarla adlandırılmış. Geliştirici of'un birden fazla parametre aldığını, from'un tip dönüşümü yaptığını, valueOf'un ayrıntılı bir dönüşüm olduğunu hemen anlayabilir. API'yi keşfetmek kolaylaşır. Each method follows standard conventions. A developer immediately understands that of takes multiple parameters, from does type conversion, and valueOf is a verbose conversion. The API becomes easy to discover.
Pratik İpucu: Yeni bir statik fabrika metodu yazarken şu karar ağacını takip edin: Tek parametre + tip dönüşümü → from. Çoklu parametre + birleştirme → of. Her çağrıda yeni nesne garantisi → create veya newInstance. Paylaşılabilir nesne → getInstance. Farklı sınıftan → getType veya newType. Practical Tip: When writing a new static factory method, follow this decision tree: Single parameter + type conversion → from. Multiple parameters + aggregation → of. New instance guaranteed → create or newInstance. Shareable instance → getInstance. From a different class → getType or newType.
