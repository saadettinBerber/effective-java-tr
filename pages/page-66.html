Madde 20: Soyut Sınıflar Yerine Arayüzleri Tercih Edin

Item 20: Prefer interfaces to abstract classes

Java'da çoklu tür tanımlamak için iki mekanizma vardır: arayüzler (interfaces) ve soyut sınıflar (abstract classes). Java 8'de arayüzlere varsayılan metotlar (default methods) eklendiğinden beri, her iki mekanizma da bazı uygulamaları içerebilir. Ana fark şudur: soyut sınıfı uygulamak için bir sınıf onun alt sınıfı olmalıdır (tek kalıtım kısıtı); arayüz ise herhangi bir sınıf tarafından uygulanabilir.

Arayüzlerin avantajları:

1. Mevcut sınıflar kolayca yeni arayüzler uygulayabilir — implements ekleyip metotları uygulayın. Soyut sınıf için ise sınıf hiyerarşisini değiştirmeniz gerekir.

2. Arayüzler karışımlara (mixins) izin verir — Comparable, Serializable gibi ek yetenekleri birden çok arayüzle ekleyebilirsiniz. Bir sınıf birden çok arayüzü uygulayabilir.

3. Arayüzler hiyerarşik olmayan tür çerçevelerine olanak tanır — Hem şarkıcı hem de söz yazarı olan bir sanatçı için Singer ve Songwriter arayüzlerini birlikte uygulayabilirsiniz.

Arayüzleri iskelet uygulamalarla (skeletal implementations) birleştirmek, her iki dünyanın en iyisini sunar. Arayüz türü tanımlar, varsayılan metotlar sağlar; iskelet uygulama (AbstractList, AbstractSet gibi) ise karmaşık metotları sağlar. Bu kalıba Şablon Metot deseni (Template Method pattern) denir.

Two mechanisms for multiple types: interfaces and abstract classes. Interfaces are preferred because: 1) Existing classes can easily implement new interfaces, 2) Allow mixins, 3) Enable nonhierarchical type frameworks. Combined with skeletal implementations (AbstractList, etc.), they offer the best of both worlds.

Madde 20 — Özet: Arayüzler genellikle birden çok uygulamaya izin veren türleri tanımlamanın en iyi yoludur. Karmaşık arayüzler için varsayılan metotlarla birlikte iskelet uygulamalar sağlamayı düşünün. İskelet uygulamalar genellikle Abstract ön ekiyle adlandırılır.
Item 20 — Summary: Interfaces are the best way to define types with multiple implementations. Provide skeletal implementations for complex interfaces.

Madde 21: Arayüzleri Sonrası İçin Tasarlayın

Item 21: Design interfaces for posterity

Java 8'den önce, mevcut uygulamaları bozmadan bir arayüze metot eklemek imkansızdı. Java 8'de varsayılan metot (default method) mekanizması eklendi — ancak bu sihirli bir çözüm değildir! Mevcut arayüze varsayılan metot eklemek mevcut uygulamaların bilgisi veya onayı olmadan yapılır.

Örnek: Collection arayüzüne Java 8'de eklenen removeIf metodu, Apache Commons'ın SynchronizedCollection sınıfıyla düzgün çalışmaz — senkronizasyon garantisi ihlal edilir! removeIf'in varsayılan uygulaması senkronizasyondan habersizdir.

Varsayılan metotlar mevcut arayüzlere metot eklemeyi mümkün kılsa da, bunu yapmanın büyük riskler taşıdığını ve kaçınılması gerektiğini unutmayın. Yeni arayüzler tasarlarken varsayılan metotlar harikadır — ancak arayüz yayınlandıktan sonra dokunmamaya özen gösterin.

Default methods let you add methods to existing interfaces, but it's risky. Example: removeIf on Collection broke SynchronizedCollection. Design interfaces carefully before release.

🔍 Kavramlar: 🔍 Concepts:

İskelet Uygulama (Skeletal Implementation)

İskelet uygulamalar, arayüzlerin ve soyut sınıfların güçlü yönlerini birleştirir:

• AbstractList, AbstractSet, AbstractMap — Java Collections Framework'ün temel taşları
• Arayüz türü tanımlar; iskelet uygulama karmaşık metotları sağlar
• İstemci iskelet uygulamayı genişletir veya "simulated multiple inheritance" kullanır

Skeletal implementations combine interfaces and abstract classes: AbstractList, AbstractSet, AbstractMap. The interface defines the type; the skeletal implementation provides complex methods.

Varsayılan Metot Riski

Varsayılan metotlar, mevcut uygulamaların haberi olmadan arayüze eklenir. Mevcut uygulamalar bu metotları ezemediği için:

• Çalışma zamanında hatalara neden olabilir
• İş parçacığı güvenlik sözleşmelerini ihlal edebilir
• Derleme zamanında hata vermez — sorunlar çalışma zamanında ortaya çıkar

Default methods are added without existing implementations' knowledge. Can cause runtime errors and break thread-safety contracts. No compile-time warning.
